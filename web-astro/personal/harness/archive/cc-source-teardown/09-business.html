第 09 章 · 看不见的那一半产品

遥测与远程控制：产品在你机器上的另一半

一个装在本地的 CLI，为什么能远程改行为？因为它在启动时拉配置、在运行中传事件、在紧急时接受开关。这一章把「遥测发了什么、能关吗、服务端能改什么」讲清楚 —— 顺便纠正一个流传很广的说法。

30 秒版

  1. 代码里有 659 个不同的 logEvent('tengu_…') 事件名（以 tengu_ 开头的字符串共 903 个，多出来的是灰度开关名），路由到 Datadog 与一方事件服务，是否发送还受采样与开关控制。
  2. 遥测可以关：DISABLE_TELEMETRY 关分析，CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC 关掉全部非必要流量（含自动更新）。二手文章说「无法退出」不准确。
  3. 服务端下发两类东西：策略（能不能用某功能）与托管设置（默认配置），后者支持会话中热更新。
  4. 远程开关能做到：禁用绕过权限模式、强制最低版本、在事故期间封顶版本、暂停某条遥测管道。
  5. 订阅限额在代码里是四个窗口：5 小时、7 天、7 天 Opus、7 天 Sonnet。

01遥测：发了什么，能不能关

事件统一走 logEvent(name, metadata)，元数据只允许布尔/数字/字符串，而且类型上做了个「防呆标记」：凡是字符串字段必须显式标注「我确认这不是代码或文件路径」。这是用类型系统防隐私事故的少见做法。

纠错：泄露后不少分析说「遥测无法关闭」。代码里明确有两条退出路径，而且最严格那档连自动更新都会停。真正的问题不是「不能关」，而是「默认开、且分散在多个开关里」。

04托管设置：缓存优先、后台轮询、热更新

企业配置不是「启动读一次文件」，而是「先用磁盘缓存，再拉远端，拉到就热更新」。这样启动不会被网络拖慢，运行中又能接受变更。

services/remoteManagedSettings/index.ts527-537 · 连 77ms 的等待都要省掉 —— 启动性能是产品指标
// Cache-first: if we have cached settings on disk, apply them and unblock
// waiters immediately. The fetch still runs below; notifyChange fires once,
// after the fetch, as before. Saves the ~77ms fetch-wait on print-mode startup.
if (getRemoteManagedSettingsSyncFromCache() && loadingCompleteResolve) {
  loadingCompleteResolve()
}

拉到新设置后，会触发 settingsChangeDetector.notifyChange('policySettings')，让环境变量、遥测、权限在下次读取时生效；拉取失败则 fail-open，继续用本地配置。

06这套设计的两面

看到的好的解释坏的解释
默认开遥测改进产品需要真实使用数据，且有明确退出开关默认值即立场，多数用户不会去读文档
远程改行为事故止损、企业合规、灰度实验本地工具的确定性被牺牲
版本闸门避免旧版本产生错误数据或安全漏洞用户失去「先不升级」的权利
模型代号保密未发布型号属于商业机密「隐身模式」让 AI 参与不可见（见第 08 章）
给产品经理的一句话：只要你做一个「装在使用者机器上」的 Agent，就一定会面对同一组取舍：默认遥测、远程配置、版本闸门。提前把「用户能不能关、关了之后功能降级到什么程度」写进 PRD，比事后解释便宜得多。
