第 05 章 · 记忆、压缩与预算

上下文：一台会自己整理行李的机器

上下文窗口是 Agent 最贵的资源。Claude Code 没有「超了就总结」这一招，而是排了一条五段流水线，从最便宜、最无损的处理开始，一级一级往下退。这一章讲清这条流水线的顺序、阈值和代价。

30 秒版

  1. 压缩按代价排序：工具结果预算 → snip → microcompact → context collapse → autocompact。能重取的就清，不能重取的才摘要。
  2. autocompact 的阈值不是百分比，是绝对 token：窗口 − 2 万（摘要预留）− 1.3 万（缓冲）。200k 的模型约在 167k 触发（≈93%）。
  3. microcompact 有两种触发：空闲 60 分钟后的「旧结果清空」，以及只改服务端缓存、不动本地消息的 cache editing。
  4. 摘要 prompt 固定九段，其中「所有用户消息」必须完整保留 —— 用户的每次纠正都是后续行为的约束。
  5. 压缩可能失败：连续 3 次失败就熔断，本会话不再尝试，避免「压缩 → 仍然超长 → 再压缩」的死循环。

01先看整体：五段流水线

每轮发请求前，消息数组会被这条流水线依次处理。注释里写得很清楚：能叠加，不互斥。

query.ts379-467 · 五个调用点，顺序硬编码
messagesForQuery = await applyToolResultBudget(...)   // 1 结果预算
...snipCompactIfNeeded(messagesForQuery)                 // 2 剪历史
...deps.microcompact(messagesForQuery, ...)              // 3 清旧工具结果
...contextCollapse.applyCollapsesIfNeeded(...)            // 4 折叠成摘要
...deps.autocompact(messagesForQuery, ...)                // 5 整段摘要
闸门触发保留什么丢掉什么代价
结果预算单条消息的结果总量超 20 万字符结构、路径、预览超大正文（落盘）几乎为零
snip历史累积到阈值（flag 控制）受保护尾部 + 可引用消息最早的历史片段低（可再生）
microcompact空闲 60 分钟 / 缓存编辑阈值最近 5 条结果 + 结构旧工具结果正文中（要重读）
context collapse有效窗口 90% 提交 / 95% 阻塞（仅注释可见）细粒度消息 + 阶段摘要中间一段原文中高
autocompact有效窗口 − 1.3 万摘要 + 最近若干条其余全部最高（不可逆）
数据来源说明：collapse 的 90% / 95% 只出现在 autoCompact.ts 的注释里 —— 它的实现模块不在本副本中，这两个百分比未经代码验证；其余四道闸门的阈值都能在实现里读到。
≈
像出差打包：先扔掉酒店一次性的东西（可重取的工具结果），再压缩衣服（折叠摘要），最后才考虑只带一套换洗（整段摘要）。顺序反了，就会把还要用的东西先扔了。

02顺序为什么不能换

  • 预算必须在 microcompact 之前：缓存编辑按 tool_use_id 记账，内容先被清空的话，「这条结果是否已经发过」的判断就和实际字节对不上。
  • snip 必须在 autocompact 之前，而且要把「省下多少」传下去：token 计数读的是尾部那条消息的 usage，snip 之后它没变，计数看不见节省；先压缩就会按虚高的数字触发，把刚剪完的会话又整体摘要一次。
  • collapse 必须在 autocompact 之前：collapse 若能压回阈值以下，autocompact 就成了空操作，于是保留了细粒度上下文而不是一条大摘要。
  • autocompact 在 collapse 开启时被主动禁用：两者都在 93% 附近抢触发，autocompact 会赢，然后把 collapse 正要保住的细节「核平」。
可迁移结论：压缩不是单一策略，而是一组有序的、代价递增的策略。先问「这份信息能不能重新拿到」，再问「能不能摘要」。

04microcompact：两种「清旧账」

这是最容易被误解的一环。本版本里它没有「按 token 阈值清空旧结果」的旧路径（源码直接写着 legacy 路径已删除），只剩两种：

模式什么时候改什么为什么省
时间触发距上一条回复 ≥ 60 分钟，且存在可清结果本地把旧结果正文换成 [Old tool result content cleared]缓存已过期，反正要重传，先把体积压小
cache editing工具调用数达阈值（flag 配置）不动本地消息，只发「删除这些缓存片段」的指令前缀字节不变，KV 缓存仍然命中
services/compact/microCompact.ts261-270
// 时间模式命中时短路返回，跳过 cached MC：
// editing assumes the cache is hot, and we just established it is cold.
换来什么长会话里工具输出占大头，清掉它们能撑很久，而且模型需要时可以重新读文件。
付出什么模型会看到一堆「已清空」的占位符，必须靠系统提示里那段说明才知道要重新读；清空时机判断错了（缓存还热）就白花一次全量重传。

05摘要 prompt：为什么固定九段

整段压缩不是「帮我总结一下」，而是一份带编号的结构化模板。九段固定，其中第 6 段要求列出所有用户消息。

services/compact/prompt.ts68-76
1. Primary Request and Intent: Capture all of the user's explicit requests and intents in detail
2. Key Technical Concepts: List all important technical concepts, technologies, and frameworks discussed.
3. Files and Code Sections: Enumerate specific files and code sections examined, modified, or created...
4. Errors and fixes: ...
5. Problem Solving: ...
6. All user messages: List ALL user messages that are not tool results...
7. Pending Tasks: ...
8. Current Work: ...
9. Optional Next Step: ...

先让模型写一段 <analysis> 草稿，再把草稿丢掉、只留 <summary>。这个「先想后写」的结构在压缩里同样有效：草稿提高了摘要的召回，但不占最终上下文。

为什么保留全部用户消息：用户在第三轮说过「不要用 emoji」，如果压缩时丢了，后面就会重犯。工具结果可以重取，用户的原话不能。

06记忆：三层文件 + 三个后台代理

CLAUDE.md 按「离代码越近越优先」加载，共四层：企业托管 → 用户 → 项目（含 .claude/rules/*.md）→ 本地（CLAUDE.local.md）。@include 支持嵌套，但有深度上限与防环集合。

机制谁在写什么时候跑产出
SessionMemoryforked 子代理每 1 万 token 初始化，之后每 5 千 token 且工具调用 ≥3 次会话级 markdown，压缩时优先用它代替整段摘要
extractMemoriesforked 子代理一轮正常结束后，按会话节流把值得记的偏好写进记忆目录
autoDreamforked 子代理距上次 ≥24 小时且新增 ≥5 个会话把散落记忆蒸馏回主题文件与 MEMORY.md

三个代理都只在主线程收尾时触发，且都被排除在「自动压缩」的适用对象之外 —— 否则它们压缩自己，会形成自锁。

4 层CLAUDE.md 优先级企业/用户/项目/本地

5 个单轮最多注入的相关记忆findRelevantMemories.ts:20

07附件：把「可能要用的」推迟到用的时候

每轮会并发收集一批「附件」：@ 提到的文件、IDE 里选中的代码、变更过的文件、诊断信息、待办提醒、技能列表……全部包在 maybe(label, fn) 里，单个失败不影响其他，整体 1 秒超时。

  • 去重：记忆文件用「已加载路径集合」判重，而不是靠 100 条 LRU 的文件读取缓存 —— 注释点名后者在忙会话里会掉条目，导致同一份 CLAUDE.md 被反复注入。
  • 预算：单个记忆文件最多 200 行 / 4KB（注释给算式：5 × 4KB ≈ 20KB/轮）；相关记忆全会话累计 60KB 就停止预取。
  • 延迟：相关记忆与技能发现改成「预取」，在模型流式输出时并行跑，等工具结束时再取结果 —— 不阻塞首字。
可迁移结论：上下文成本要按「每轮固定开销」算。一个 4KB 的 CLAUDE.md 看着不大，乘上 50 轮就是 200KB。

08失败模式：压缩本身也会翻车

失败代码里的防护数字
压缩后仍超限，反复压缩连续失败计数，达阈值熔断3 次（注释：1,279 个会话曾连续失败 50+ 次，每天浪费约 25 万次调用）
压缩请求自身过长（PTL）按报错的 token 缺口砍掉最旧的整轮，最多重试3 次
压缩流式中断有限重试，避免无限等待2 次
压缩把细节抹掉摘要写 transcriptPath，提示去读完整记录；保留段原样附在后面—
缓存失效被误报压缩后显式重置缓存检测基线—

// Stop trying autocompact after this many consecutive failures.

// in a single session, wasting ~250K API calls/day globally.
