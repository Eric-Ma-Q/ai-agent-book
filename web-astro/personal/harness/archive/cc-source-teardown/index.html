一个 Agent 产品，是怎么用 51 万行代码装起来的

§先说结论：五件事

1. 它是一个「运行时」而不是一个「提示词」

51 万行里，直接调用模型的那部分只有几千行。其余是工具执行、权限裁决、上下文预算、会话持久化、终端 UI —— 这些才是产品差异所在。

2. 长任务能力来自四道压缩闸门

snip → microcompact → context collapse → autocompact，按代价从低到高排队，先做无损的，再做有损的。这是「能连续干几小时」的真正原因。

3. 权限不是弹窗，是一条 11 步的裁决流水线

deny 规则、工具自检、只读分类、AI 分类器、用户询问、hook 覆盖，各有明确位置；连「连续被拒」都有熔断。

4. 泄露的代码不等于线上二进制

89 个 feature() 开关在打包时做常量折叠，164 个文件按 USER_TYPE 分支。你读到的是「所有分支的并集」，不是任何一台机器上跑的版本。

5. 最值得抄的是「约束」而不是「功能」

工具结果预算、并发安全标记、子 Agent 权限继承、压缩失败熔断 —— 这些不起眼的设计决定了 Agent 是玩具还是工具。

边界

本拆解只做产品与工程分析：不提供可运行的分支、不复制大段源码、不评价模型能力。代码片段均为评论性引用，每段不超过十余行。

§这份报告怎么来的

  • 一手材料：2026-03-31 泄露的 v2.1.88 源码副本，本地 git clone 后只读分析，共 1,932 个文件。
  • 取证方式：每一章的关键断言都配 文件:行号；数字用命令行现场数出来，不抄二手文章。
  • 交叉核对：外部事实（泄露时间、npm 版本、DMCA 数量、官方声明）走公开报道核对；与代码冲突时以代码为准，并记录冲突。
  • 不做什么：不把「代码里存在」说成「线上已开启」；不把「社区推断」写成「官方设计」。凡推断都标出来。
先说清楚一件事：这次泄露的是闭源软件被误发布的源码，不是开源。代码没有附任何开源许可证，复制、再分发、拿其中的提示词做产品都有法律风险。本报告引用片段属于评论与分析，读者不要把它当 MIT/Apache 代码用。
