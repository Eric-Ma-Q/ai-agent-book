第 07 章 · 分身的边界与代价

多 Agent：什么时候开分身，分身听谁的

「多 Agent」很容易被讲成架构图，但代码里它其实是三个不同的东西：一次性的子 Agent、可后台运行的任务、以及共享一个终端的队友。三者的隔离程度、权限来源、失败方式都不一样。

30 秒版

  1. Agent 工具的输入只有五个参数：说明、提示词、子类型、模型、是否后台。默认子类型是通用型。
  2. 任务系统有七种类型：本地命令、本地 Agent、远端 Agent、进程内队友、本地工作流、MCP 监控、Dream（记忆整理）。
  3. 子 Agent 可以继承父级上下文（fork），也可以全新开始；工具集按定义裁剪，权限模式跟随父级或 Agent 定义。
  4. swarm（队友）不是「多线程」，而是真的开终端窗格：支持进程内、tmux、iTerm2 三种后端，靠文件邮箱通信。
  5. 协调者模式与 fork 互斥：协调者会换掉整套内置 Agent 名单，自己当调度员。

01三个东西，别混为一谈

形态怎么起活多久上下文典型用途
子 AgentAgent 工具一次调用内全新或 fork 父对话搜索、探索、独立验证
后台任务run_in_background跨轮次，可断线恢复独立长命令、远端跑批
队友（swarm）TeamCreate + 窗格整个团队会话共享团队目录与邮箱并行改不同模块
≈
外包、夜班、和开分部：外包干完就交付（子 Agent）；夜班明天还在（后台任务）；开分部要租办公室、拉专线、还要同步权限（swarm）。

内置 Agent职责工具边界
general-purpose默认子类型，什么都能干继承父级可用工具
explore只读探索代码库，对外默认用 haiku禁用 Edit / Write / NotebookEdit
plan出方案，不动手复用 explore 的工具集

可迁移结论：给子 Agent 定义「角色 + 工具禁用清单 + 模型档位」，比在 prompt 里写「你是一个只读的探索者」可靠得多。注意它的只读是靠 disallowedTools 实现的，而不是靠权限模式；对外用户的探索 Agent 还会降级到 haiku —— 用便宜模型干搜索，是成本设计的一部分。

03隔离：继承什么，不继承什么

这里最容易出安全事故，而代码的答案比想象中复杂：上下文可以继承，工具池会被重新组装，deny 规则照旧，但 Agent 定义可以自带更高的权限模式。

  • 上下文：fork 模式下子 Agent 继承父级完整对话与逐字节相同的系统提示；普通子 Agent 只拿到 prompt 与必要附件。
  • 工具：不是父级工具池的子集，而是用 assembleToolPool() 重新组装 —— 注释明说它「不受父级工具限制影响」。
  • 权限：规则（deny / ask / allow）随权限上下文继承，deny 仍在第一步生效；但模式取 agent.permissionMode ?? 'acceptEdits'。
  • 结果：回灌的是子 Agent 的最终文本全文，不是摘要；过程消息不进父级上下文。
tools/AgentTool/AgentTool.tsx568-577 · 父级当前能用的工具不继承，但规则继承
assembleToolPool({
  ...parentContext.toolPermissionContext,
  mode: agent.permissionMode ?? 'acceptEdits',
})
// 注释原文：subagents "aren't affected by the parent's tool restrictions"
一个真实的安全边界：Agent 定义的 frontmatter 可以写 permissionMode: bypassPermissions，子 Agent 就会以绕过模式启动。deny 规则仍然拦得住，但「父级当前是 default、子级却是 bypass」这件事在设计上是被允许的 —— 使用第三方 Agent 定义前必须读它这一行。
换来什么子 Agent 的过程不占父级上下文：一个「找代码」任务可能读 20 个文件，父级只收到最终结论全文。
付出什么最终文本可能很长且丢细节；父级无法审计子 Agent 读过什么，除非翻它的 transcript；权限模式可被定义抬高。

04任务系统：七种类型，五个状态

Task.ts8-21
export type TaskType =
  | 'local_bash'
  | 'local_agent'
  | 'remote_agent'
  | 'in_process_teammate'
  | 'local_workflow'
  | 'monitor_mcp'
  | 'dream'

export type TaskStatus = 'pending' | 'running' | 'completed' | 'failed' | 'killed'

把「任务」抽成统一类型，带来三个直接好处：UI 只需要一套任务面板；TaskOutput 可以增量读任意任务的输出；进程重启后能按 transcript 恢复未完成的任务。这也是为什么长任务不会因为关掉终端就全丢。

remote_agent在远端环境跑 Agent云会话 / RemoteTrigger
in_process_teammate同进程里的队友TeamCreate（进程内后端）
local_workflow多步工作流脚本Workflow 工具（flag）
monitor_mcp监控 MCP 事件Monitor 工具（flag）
dream后台整理记忆autoDream

05swarm：真的开窗格

队友模式的实现比想象中「土」但有效：它真的调 tmux 或 iTerm2 开窗格，每个队友是一个独立的 Claude 进程，靠文件邮箱通信。没有消息总线，没有共享内存。

export const TEAM_LEAD_NAME = 'team-lead'
export const SWARM_SESSION_NAME = 'claude-swarm'
export const SWARM_VIEW_WINDOW_NAME = 'swarm-view'
export const TMUX_COMMAND = 'tmux'
...
export function getSwarmSocketName(): string {
  return `claude-swarm-${process.pid}`
}
后端怎么跑优点限制
进程内同一进程里起 runner快、无终端依赖不能开后台 Agent；权限要回问 leader
tmux开 tmux 窗格独立进程、可观察需要 tmux；窗口管理麻烦
iTerm2开 iTerm2 分屏macOS 体验好仅 macOS + iTerm2

权限是这里最微妙的部分：进程内队友遇到需要审批的操作，会把请求发到 leader 的邮箱，然后每 500ms 轮询自己的邮箱等答复。leader 不在或界面不可用时，还有一条降级路径。

utils/swarm/inProcessRunner.ts124-126
* Falls back to the mailbox system when the bridge is unavailable:
 * sends a permission request to the leader's inbox, waits for the response
 * in the teammate's own mailbox.
一个实现缺口：tasks.ts 的注册表没有登记 in_process_teammate，所以 TaskStop 对队友会返回 unsupported_type；界面上的「停」是绕过注册表直接调 kill() 的。这类不一致正是「先有 UI 后有统一模型」的痕迹。

06协调者模式：换一套班子

协调者模式（COORDINATOR_MODE）不是「多一个 Agent」，而是换掉内置 Agent 名单：开启后 getBuiltInAgents() 返回的是协调者专用的 worker 集合，主 Agent 变成调度员。它与 fork 互斥 —— 两者都想当「唯一的编排者」。

tools/AgentTool/builtInAgents.ts38-46 · 用一个环境变量切换整套班子
// Use lazy require inside the function body to avoid circular dependency
// issues at module init time. The coordinatorMode module depends on tools
if (feature('COORDINATOR_MODE')) {
  if (isEnvTruthy(process.env.CLAUDE_CODE_COORDINATOR_MODE)) {
    const { getCoordinatorAgents } = require('../../coordinator/workerAgent.js')

与它相对的 fork 模式则相反：不换班子，而是让子 Agent 继承父级完整消息、逐字节相同的系统提示与工具表，权限模式用 bubble（把审批冒泡回父终端），默认 maxTurns: 200。为了让缓存命中，fork 会把父级所有未完成的 tool_use 统一回一个占位结果。

产品视角：「多 Agent」不是越多越好。协调者模式存在的理由，是把「拆任务、分派、汇总」从主循环里拿出来，交给一个专职角色 —— 代价是多一层上下文传递；fork 的代价则是上下文翻倍。
