第 03 章 · 一次会话的发动机

主循环：一个不肯结束的生成器

query.ts 里不到 1,500 行的 queryLoop，是整份代码里最值钱的部分。它要同时处理流式输出、并行工具、用户打断、上下文压缩、API 报错和「什么时候该停」。这一章把它拆成五段来看。

30 秒版

  1. 循环是 async function*：边跑边 yield 消息，界面才能实时渲染、用户才能随时打断。
  2. 它的返回值只有十来个「终止原因」，每一个都对应产品上一种收场方式（完成、超轮次、被打断、上下文爆了、hook 拦下）。
  3. 一轮里的步骤顺序是硬约束：先算工具结果预算 → snip → microcompact → collapse → autocompact → 发请求。顺序换了就会多花一次全量请求。
  4. 工具并发不是「全并行」：标记为并发安全的可以并行，不安全的必须独占，而且会堵住后面的队列。
  5. 报错不是异常退出：输出被截断会先升到 64k 重试，再不行注入「接着写」的恢复消息，最多 3 次。

01为什么是 async generator

普通函数只能「跑完返回」。而 Agent 的一轮里，模型是流式的、工具是渐进的、用户随时可能按 Esc。用生成器把状态挂在函数栈上，就能做到：产出即渲染、随时 return 收场、调用方 break 也能立刻停。

query.ts219-231 · 返回类型 Terminal，产出类型是五类消息
export async function* query(
  params: QueryParams,
): AsyncGenerator<
  | StreamEvent
  | RequestStartEvent
  | Message
  | TombstoneMessage
  | ToolUseSummaryMessage,
  Terminal
> {
  const consumedCommandUuids: string[] = []
  const terminal = yield* queryLoop(params, consumedCommandUuids)

注意第二个类型参数 Terminal：生成器的「返回值」不是消息，而是一个终止原因对象。调用方既能消费过程，也能拿到结局。

≈
像看直播而不是等录播：主播（模型）边说，你边看，还能中途发弹幕打断；导演（循环）最后给你一张「本场结束原因」的单子。

02状态机：7 个转移点，一套状态

循环体不是靠嵌套 if 推进的，而是「每轮开头解构一份 State，需要重来时整体换一份新 State 再 continue」。这样所有恢复路径长得一样，测试也好写。

query.ts203-218
type State = {
  messages: Message[]
  toolUseContext: ToolUseContext
  autoCompactTracking: AutoCompactTrackingState | undefined
  maxOutputTokensRecoveryCount: number
  hasAttemptedReactiveCompact: boolean
  maxOutputTokensOverride: number | undefined
  pendingToolUseSummary: Promise<ToolUseSummaryMessage | null> | undefined
  stopHookActive: boolean | undefined
  turnCount: number
  transition: Continue | undefined

transition 字段记录了「上一轮为什么继续」，只给测试与埋点用，但它是理解这套状态机的钥匙。全库只有 7 个转移点：6 处显式 continue，加上循环末尾落空重入的普通下一轮。

继续原因触发场景产品含义
next_turn本轮有工具调用，结果已回灌正常干活（落空重入，无显式 continue）
collapse_drain_retry服务端报 413，先排空 collapse 队列先撞墙再补票
reactive_compact_retry排空后仍超限，触发被动压缩最后一次补救

token_budget_continuation预算续跑长任务的燃料补给
stop_hook_blockingStop hook 判定「还没干完」外部脚本可以否决「结束」

03一轮的五段：顺序是硬约束

每轮开头到发请求之间，有一段固定的流水线。注释里写明了为什么必须这个顺序：先做便宜的、无损的，再做贵的、有损的。

query.ts412-444
// Apply microcompact before autocompact
queryCheckpoint('query_microcompact_start')
const microcompactResult = await deps.microcompact(
  messagesForQuery,
  toolUseContext,
  querySource,
)
...
// Project the collapsed context view and maybe commit more collapses.
// Runs BEFORE autocompact so that if collapse gets us under the
// autocompact threshold, autocompact is a no-op and we keep granular
// context instead of a single summary.
  • 工具结果预算：按字符/ token 上限替换超大结果（落盘 + 引用），不动对话结构；
  • snip：剪掉最早的历史片段（有损但便宜）；
  • microcompact：只清「可重取」的工具结果（读文件、跑命令的输出），保留结构；
  • context collapse：把中间一段折叠成摘要，但保留原始历史用于回放；
  • autocompact：真正的「把整段历史压成一份摘要」，最贵、信息损失最大，所以放最后。
这条顺序为什么值钱：很多 Agent 一超限就直接总结，结果把「刚才读过的文件内容」也总结没了。Claude Code 的做法是先用「可重取的结果」腾地方 —— 文件还能再读，摘要就回不来了。

04工具并发：三种状态，一条规则

模型一次可以吐出多个 tool_use。执行器把它们排进队列，用一条规则决定谁能跑：

services/tools/StreamingToolExecutor.ts124-131
private canExecuteTool(isConcurrencySafe: boolean): boolean {
  const executingTools = this.tools.filter(t => t.status === 'executing')
  return (
    executingTools.length === 0 ||
    (isConcurrencySafe && executingTools.every(t => t.isConcurrencySafe))
  )
}

翻译成人话：没有人在跑 → 谁都能跑；有人在跑 → 只有「并发安全」的能插队，且正在跑的全部也得是并发安全的。一旦遇到不安全的工具（比如写文件、跑命令），队列后面的全部等着 —— 因为顺序本身就是语义。

非流式路径（关闭流式执行时）走另一套编排：先把连续的安全调用合并成批，批内并发（默认上限 10），批与批之间串行。判定失败一律按「不安全」处理 —— fail-closed。

services/tools/StreamingToolExecutor.ts44-48
* Executes tools as they stream in with concurrency control.
 * - Concurrent-safe tools can execute in parallel with other concurrent-safe tools
 * - Non-concurrent tools must execute alone (exclusive access)
 * - Results are buffered and emitted in the order tools were received
换来什么读文件、搜索这类操作可以几个一起跑，等模型说完时结果已经回来了，感知延迟接近「并行」。
付出什么写操作必须独占，长任务里会出现「一个慢命令堵住后面所有工具」；所以它把 Bash 放进后台任务来绕开（见第 07 章）。

05被打断时怎么收场

用户按 Esc 时，abortController 触发。麻烦在于：模型可能已经吐出 3 个 tool_use，但一个 tool_result 都还没回。如果直接退出，下一轮请求会因为「tool_use 没有配对的 tool_result」被 API 拒绝。

query.ts1015-1026
if (toolUseContext.abortController.signal.aborted) {
  if (streamingToolExecutor) {
    // Consume remaining results - executor generates synthetic tool_results for
    // aborted tools since it checks the abort signal in executeTool()
    for await (const update of streamingToolExecutor.getRemainingResults()) {
      if (update.message) {
        yield update.message
      }
    }
  } else {
    yield* yieldMissingToolResultBlocks(assistantMessages, 'Interrupted by user')
  }

做法是补齐：给每个没跑完的工具造一条错误结果（user_interrupted / sibling_error / streaming_fallback 三种理由），保证消息序列永远合法。还有一个细节：工具可以声明自己被中断时的行为是 cancel 还是 block —— 后者允许「先让我把这个命令跑完」。

中断来源谁触发的工具结果的写法用户看到什么
user_interrupted用户 Esc / 新消息抢占REJECT_MESSAGE「User rejected tool use」
sibling_error同批某个工具报错「Cancelled: parallel tool call X errored」其余工具一起取消
streaming_fallback流式失败切备用模型「tool execution discarded」这一批作废重来

07十种收场方式

Terminal 的取值就是产品行为的清单。把它列全，你会发现「结束」远不止一种：

reason含义谁会看到
completed正常完成（模型不再调用工具）所有人
max_turns达到轮次上限脚本 / SDK 调用方
aborted_streaming流式阶段被打断按 Esc 的用户
aborted_tools工具执行阶段被打断同上
hook_stoppedhook 主动终止配置了 hook 的团队
stop_hook_preventedStop hook 不允许结束同上
prompt_too_long压缩后仍然超限所有人（罕见）
model_errorAPI 错误重试耗尽所有人
blocking_limit上下文到硬上限所有人
image_error图片处理失败贴图的用户
产品视角：这份清单可以直接当「Agent 会话状态机」的需求文档用。大多数自研 Agent 只有「成功 / 报错」两态，所以一断线就只剩重开。
