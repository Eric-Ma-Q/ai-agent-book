Super-agent 结构图把 Session 变成实现细节

四个特征（连续 / 高效 / 主动 / 持久）由五个模块承担。Router 持有全局连续性与记忆，只分派不干活；Worker 上下文隔离、并行执行、不对外说话；事件驱动先把噪音挡在模型之外；计算 / 状态 / 环境拆开，Loop 上云、状态入库、环境留在原处；Watchdog 是主系统之外的控制回路。下面按「一条事件从进入到变成结果」的顺序画。

双层架构 事件驱动 · 两级过滤 订阅直通 · 投机执行 Inline & Spill · 链式召回 异步 ReAct 存算分离 · BYOM Watchdog
01输入：环境事件取代提示词 Trigger 是主输入，人键入的提示词降为辅助；同一 PR / 同一 IM 话题 / 同一封邮件串下的连续事件构成可订阅的 Thread

IM 群聊 低打扰 · 短消息

有人反馈缺陷、讨论方案，往往不 @ 任何人。信息密度低、打扰成本高，输出侧因此只给结论。

GitHub PR / issue 评审评论 · CI

代码评审评论、CI 运行结果；按 PR 归并成 Thread，后续评论可直接直通已订阅的 Worker。

邮件 · 日程 结构化为先

邀约、待办与往来邮件串。个人助手场景的主要入口，天然带结构化字段与时间约束。

事件载荷：来源 · 群组 / 仓库 · 发起人 · thread id · 摘要 · 引用对象 id。thread id 是后面订阅表与链式召回的共同主键。
所有事件先进入准入层
02准入：两级过滤，程序挡噪音、模型做判断 真实环境是「高噪音、低触发率」；每条消息都问一次模型，成本与延迟都撑不住

FAST PATH · 程序层 确定性 · 不调模型

按来源、群组范围、人 / 机器人白名单做快速准入：明确请求、候选事件、直接忽略三档。绝大多数消息在这里被丢掉。

SLOW PATH · 语义层 需要理解才交给模型

通过程序层的候选交给 LLM，按提示词策略与上下文判断「是否值得处理」。策略可随时开关、新增，是面向人的扩展点。

只有同时通过两层的候选才可能变成新任务；被程序层挡掉的事件不进入任何会话，也不产生 token。
通过两层的候选才值得处理
03Router 层 · 常驻 全局序点、协调点、记忆；只处理人机交互与分派，不执行具体任务，甚至可以不配 Bash

一个常驻会话，承接所有入口的人类交互 跨任务的信息与决策都在这里汇总；因为只做轻量分派，较轻的模型就能兼顾速度与效果

全局记忆

跨任务共享的事实与决策。先在 IM 说方案 A、后在 PR 改成 B，它知道是同一条线。

订阅表

Thread ⇄ Worker 多对多。有表才能让已归属的事件绕开 Router 直通执行者。

批处理

上一轮推理期间到达的事件积压，下一轮一并注入，在 prefill 阶段并行算。

分派与协调

新任务开 Worker；跨任务协同由 Router 中转；同层不点对点通信。

唯一出口

Worker 只汇报状态，对外只有 Router 说话，避免多会话各自回复造成混乱。

与 Agent Team 的分工：Team Lead 要在单任务内部拆步骤、高频协调，推理负载重；Router 只处理任务之间的高层关联。把 Team Lead 用提示词约束成「不亲自执行、只对外交互与分派」，也可视为这种双层——双层是职责划分，不要求每层只有一个会话。
新任务 → 分派 Slow · Router 判断并建 Worker
已订阅 Thread → 直通 Fast · 不经 Router 转发
04Worker 层 · 隔离执行 独立上下文、完整工具、通常配最强模型；直接决定任务结果与代码质量，但不直接对用户说话
Worker A 隔离上下文
  • 只订阅自己负责的 Thread
  • 复现 → 定位 → 提 PR
  • 关键结论回 Router
Worker B 完整工具
  • 内部可再开 Subagent
  • 推理与工具调用不外泄
  • 可自判事件是否仍在范围内
Worker C 可嵌套
  • 本身可以是一个 Agent Team
  • 嵌套细节对 Router 透明
  • 共享环境下自行发现冲突
冲突靠订阅解，不靠通信：多个 Worker 订阅同一 Thread，同一工作环境（如一个 PR）里的新事件同时直通给所有订阅者，它们不必点对点协商就有机会看到彼此的操作；少数跨任务协同由 Router 中转。扩展：单 Router 不够用时，层内加多层过滤或水平切分为多个 Router——切得越细，吞吐越高，跨片记忆与连续性越低。
05三个支撑机制：上下文、交互、提前行动 都挂在上面两层上，不新增层；每一条都在替人省一次手动操作
AInline & Spill

把窗口当缓存管：只给 id 与摘要 → 按局部性内联相邻内容（前后消息、相邻评论、正文前 50 字）→ 超预算就截断、留续读入口，需要全文再调工具。

ID + 摘要→内联相邻→Spill 留引用
B链式召回

每类对象带唯一 id，注入时内联下一跳 id，对象之间连成引用图；模型从当前事件逐跳展开，每次召回同样遵守 Inline & Spill。

当前消息→Thread→Worker 会话→另一 Thread
C投机执行

还不确定结果会不会被采用时，先按环境信号在后台试：会前备好日程冲突、背景与草稿；群里静默复现并找修复。有价值就交付，没价值就丢掉。

门槛：「确认问题」且「简单修复」同时成立才出声，放宽任一条就变成抢答。

D异步 ReAct Loop

run() 阻塞整个会话 → 改成 start() 立即返回 Started，后台继续跑；期间前台可接新指令；结果作为一条新事件回到会话；过长可调 stop()。新输入在当前推理步结束后即被处理，不等后台工具完成。

start()→后台执行→结果入队为事件→暂停 / stop()
E多信道输出

推理与工具调用留在 Worker 内部，对外只有 Router，再按信道带宽定制：IM 只问直接问题、给短结论（单次不超过 100 词）；GitHub / 邮件按规范写清背景、改动与验证，做成结构化异步交付。

Loop 要长期在线：把三件绑在一起的事拆开
06计算 / 状态 / 环境分离 顺序不能换：先分计算与状态，再分 Loop 与执行环境

云端无状态 Loop 可水平扩展

推进 Agent Loop 的计算不保存状态，放进云端弹性容器，可重启、可替换、可扩缩。Agent 由此摆脱单台设备的生命周期。

会话状态入库 连续性

Session 等状态写进数据库。容器换了，上下文还在；连续性由持久化存储保障，而不是由某个进程活着保障。

端侧瘦 daemon BYOM

重状态的执行环境留在原地：未提交修改、私有凭据、内网依赖、特定硬件。端侧只跑一个不保存会话状态的 daemon，执行命令、返回结果。

为什么不让环境上云：沙箱重建要同步本地修改、凭据与内网服务，成本高又容易漏；要求用户迁到云端则迁移成本太高。收益：一个 Agent 可用多台机器；个人设备重新上线后，云端可自动触发需要在该设备上完成的任务。对照脑手分离：共同点是 harness 无状态、日志外置；差别在场景（可重建沙箱 vs 不可重建的日常机器）与主要风险（沙箱逃逸 vs 云端 Loop 与全部端侧设备之间的信任边界）。
07Watchdog · 主系统之外 独立控制回路，定时驱动；不是一个监控脚本，而是一个完整的 Agent 会话
探活不够，要看进展

多数异常不是进程崩溃，而是陷入无效循环或偏离目标。因此既要盯基础设施存活，也要盯任务本身有没有实质进展。

它修什么

接口报错、状态恢复失败等基础设施故障；外部偶发故障则持续复查直到恢复。

运维接口变对话

自身带完整工具，维护者可用自然语言问故障原因，也可让它在线改提示词、调触发规则。

它的失败模式

与被监控系统同源（同批模型、同套提示词与工具），可能共享盲区，却握有改主系统的权限。原文未讨论。
