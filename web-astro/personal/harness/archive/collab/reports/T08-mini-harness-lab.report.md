## 摘要

1. 用 1,290 行标准库 Python 把 08–14 分册的六个机制做成了可运行、可测、离线可复现的实验；
   验收命令 `python3 -m unittest discover labs/mini-harness/tests` 34 个测试全部通过（2026-10-04 实跑）。
2. **压缩边界的坑（动手才发现）**：compaction 的切分边界不能落在 `tool` 消息上——它必须跟在同一条
   assistant(tool_calls) 之后，拆散了 OpenAI 兼容接口直接报错；实现里专门有一段边界回退逻辑
   （`compaction.py::compact_messages`），并有专门测试覆盖。
3. **FakeModel 需要"主对话 / 压缩"双脚本队列**：压缩是不带 tools 的隐藏系统调用（呼应 08 §3.3
   OpenCode"隐藏系统代理"的设计），分队列后"第 N 步触发压缩"的时序才可在测试中精确表达。
4. **落盘与截断是互补而非二选一**：落盘（2k 字符，保留全貌+路径引用）优先，硬截断（10k，安全网）
   兜底；`read_file` 走自己的按行分页。复合顺序已在 README"设计取舍"里作为显式决策写出正反两面。
5. **ask 的无人值守语义**：默认"拒绝并写明原因"而非挂起（挂起=死锁），真交互通过 `on_ask` 回调注入，
   CLI `--interactive` 已接。
6. **测试反推出真 bug 两次**：(a) RuleEngine 全不命中时漏用 `default` 兜底，已修；
   (b) S4 单元测试曾用 `workspace="."`，从仓库根跑测试把 artifact 写进了仓库根的 `.harness/`——
   正是"工具输出必须锚定工作区"的活例证，已修复测试并删除误生成目录，加了"不污染 CWD"断言防回归。
7. **判分器自身被测**：S6 测试故意喂错误答案与缺失答案文件，验证可执行判分器会判 FAIL
   （对应 13 §4.2"判分器漏洞"意识）；假模型 eval 5/5 通过证明机制正确（不代表模型能力）。
8. **真模型 eval 未跑成**：`localhost:8080` 确有 OpenAI 兼容服务（lsof 显示为 opencode 进程），
   但要求本地 API key（401 "invalid local API key"），会话环境 `HARNESS_API_KEY` 未设置、
   配置与日志中均不可得；按任务单约定改附假模型输出，并另用标准库 mock server 离线验证了
   OpenAICompatModel 的请求格式、tool_calls 解析与 401 错误路径。审核者带 key 的复跑命令在 README 附录 3。
