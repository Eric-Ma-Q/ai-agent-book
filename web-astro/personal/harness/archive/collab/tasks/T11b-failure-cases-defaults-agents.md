`ai-failure-casebook.html` 已有 15 个案例。本任务再收集 **8–9 个**新案例，主题是"产品决策层面的失败"：AI 功能的默认开启与数据条款、捆绑涨价、AI 硬件形态、编码 agent 与开发者工具出事、AI 代用户操作与平台的冲突。每个案例按现有五段式拆解，写成 Markdown，之后由审核者另派任务并入 HTML。

## 每个案例的写法（字段与 casebook 一致）
```
### N. <产品>：<一句话标题>
- 公司 · 产品 / 时间（YYYY-MM）/ 失败类型（2–4 字标签，与已有 15 例的标签不重复为佳）
**一句话定性**：…
**产品假设**：团队押注了什么　**成功指标**：用什么判断成功
**时间线**：MM-DD 发布/信号/响应/修复 + 事件（每条带出处）
**最先发现**：谁　**暴露耗时**：…　**止血耗时**：…
**为什么内部没拦住**：3–4 条（基于公开资料的分析标【推断】）
**根因分层**：① 症状 ② 机制 ③ 产品决策 ④ 流程与组织
**止血 / 修复 / 制度化**：各 1–3 条
**做对了什么 / 还欠缺什么**：各 1–2 句
**如果你是这个产品的 PM**：3–5 条可执行做法
**来源**：编号列表，[官方]/[二手] + 标题 + URL + 日期
```

## 文档结构
1. 开头 `> 调研日期 / 方法 / 检索规模 / 对象界定`
2. 横向对比表：案例 | 失败类型 | 谁先发现 | 暴露耗时 | 止血手段 | 最终修在哪一层（与 casebook 同列）
3. 案例详解（按上面字段）
4. 跨案例规律：3–5 条，说明哪些是对已有 15 例"十条结论"的补充、哪些与之冲突
5. **对 harness 设计的启示**（3–5 条，例如"agent 扩展的发布管线""质量漂移的线上探针"）
6. 新增上线检查项：5–10 条，不与 casebook 已有 35 项重复
7. 参考资料
