# T12 · 失败案例集并入：把续集 A/B/C 的 27 个案例并进 ai-failure-casebook.html

**模块**：案例库扩充　**类型**：HTML 页面整合　**优先级**：高

## 目标
`ai-failure-casebook.html` 现有 15 个案例。T11a/T11b/T11c 三份调研稿各 9 例、已审核通过。本任务把这 27 例并进同一个页面，变成 **42 例**的案例集，同时合并规律和检查清单。页面的交互、样式和口吻保持不变。

## 必读上下文
- `collab/PROTOCOL.md`
- `ai-failure-casebook.html` 全文：先搞清结构（hero 统计、01 分析框架、02 横向对比表、03 案例 tab、跨案例规律、上线检查清单、选例说明）和每个案例 `<article class="panel">` 的字段
- `research/15-ai-failure-cases-a.md`、`research/16-ai-failure-cases-b.md`、`research/17-ai-failure-cases-c.md`（内容来源，**只搬运和压缩，不新增事实**）
- 三份审核意见：`collab/reviews/T11a-*.review.md`、`T11b-*.review.md`、`T11c-*.review.md`，各自"留给并入 HTML 的任务"一节要一并处理

## 要做的事
1. **案例 tab**：按主题重新分组（建议：模型 / 平台层；AI 替公司说话；默认值与商业化；Agent 与开发者工具；专业流程；陪伴与未成年人；硬件与形态——可调整，但每组名称要让读者一眼看懂）。已有 15 例归入新分组，不改它们的正文；新 27 例按现有 panel 的字段写：一句话定性、产品假设与成功指标、时间线、最先发现 / 暴露耗时 / 止血耗时、为什么内部没拦住、根因分层、止血 / 修复 / 制度化、做对了什么 / 还欠缺什么、如果你是这个产品的 PM（压到 3–5 条）、来源（保留 2–4 条最关键的链接）。id 形如 `case-aircanada`，全页唯一。
2. **横向对比表**：合并成一张 42 行的表，按同样的分组分段，每行能跳到对应案例。
3. **hero 统计**：更新案例数、"由外部最先发现"的比例（按三份调研稿的"谁先发现"列重新数）、检查项数。
4. **跨案例规律**：现有十条不改编号；T11a 规律 A–E、T11b 规律 1–5、T11c 规律 F–J 去重合并后，作为"续集补充规律"一节追加（建议 8–12 条）。明确标出哪几条是对原十条的**修正**（如 T11a 规律 E 修正原规律 4、T11c 规律 I 修正原规律 7、T11b 规律 2 修正原规律 2）。
5. **上线检查清单**：35 项不动；三份稿的新增项（9 + 10 + 10）去重后按生命周期归入现有分组或新开分组，编号顺延。
6. **选例说明与资料口径**：补一段说明续集的来源、三批的主题划分、落选候选及理由、仍未取得原文的来源（各审核意见和报告"待决问题"里列的）。页脚日期更新为 2026-10-07。
7. 把三份审核意见里"留给并入 HTML 的任务"逐条处理（时间线阶段标签、压缩 PM 条目等）。
8. `index.html` 中 casebook 卡片的描述与数字同步更新（只改这张卡片）。

## 红线
- **不新增事实**：所有数字、日期、引语、链接都来自三份调研稿，写不下就删，不要改写成调研稿里没有的说法。Gemini CLI 案不要写成"删库"，Amazon Q 案以"已分发、因语法错误未执行"为准。
- 单文件、离线可用；不引入新的外部依赖；保持白天 / 黑夜主题、键盘 ← → 切换、`#case-xxx` 深链可用。
- 手机 375px 宽度下整页无横向滚动（宽表格收在可滚动容器里）。
- 不改其他页面（`index.html` 只改 casebook 卡片）。

## 验收（报告里附实际输出）
1. HTML 结构检查：标签闭合、id 全页唯一、每个 tab 的 `aria-controls` 都有对应 panel、对比表每个 `data-case` 都能找到 panel。
2. 本地起 `python3 -m http.server` 用 Chrome 打开（参照 T09b 报告的做法）：控制台无报错；逐个点击 42 个 tab 都能显示；随机 3 个 `#case-xxx` 深链能直接定位；375px 视口 `scrollWidth == clientWidth`；暗色模式下新内容可读。
3. 抽 5 个新案例，对照调研稿核对数字和日期没有在搬运中出错。
