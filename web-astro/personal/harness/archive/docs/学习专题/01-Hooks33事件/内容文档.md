# Hooks33 事件内容文档

## 一、学习目标

- 能对着任意一个 hook 事件说出：何时触发、能不能拦截、允许哪些执行器、能不能配 matcher 与 `if`。
- 能写出一份不误用的 `settings.json`，并解释每条配置为什么必须放在这个事件上。
- 遇到"hook 没生效"时，能先判断是事件选错、能力用错，还是配置写错，而不是先怀疑脚本。

## 二、目标读者

- 已用 Claude Code 写过代码，想把"靠提示词提醒"换成确定性约束的工程师。
- 需要给团队做 hooks 评审、培训或配置收口的人。

## 三、知识边界

- 只讲 hooks 事件与配置；权限模式、MCP 服务、插件与 SDK 不在本专题。
- 不追版本差异：事件表以 2026-10 的官方文档为准；Claude Code 升级后先核对官方能力表再改页面。
- 页面里的 `.mjs` 脚本是场景示意，不是可直接上生产的安全实现；落地时要替换仓库路径、命令与超时。
- 不讨论"用 hook 替代全部流程"：hook 只适合确定性的拦截、注入与观测，复杂判断仍应放在编排层。

## 四、来源与核实

- 官方能力表：`code.claude.com/docs/en/hooks`（2026-10）。`build.py` 顶部把能力表转写为 `ALL_EVENTS`、`NO_MATCHER`、`NO_DECISION`、`T5`/`T4_NO_AGENT`/`T3`/`T2`、`TOOL_EVENTS`。
- 33 条事件数据：`hooks-33/build.py` 中的 `hook(...)` 调用；阶段划分见 `PHASES`。
- 页面数字（20 可干预 / 4 仅注入 / 9 仅观测，5/4/3/2 类执行器）由构建脚本按数据计算并打印，与页面注入值一致。
- 新增或修改事件时，先改 `hook(...)` 数据，再跑构建；断言会拦住与官方能力表冲突的写法。

## 五、可延展的设想

- 版本差异表：记录事件增删、字段变化与废弃项，避免页面随 Claude Code 升级悄悄过期。
- 按场景拆最小模板：CI 冷启动、大规模迁移、安全审计各一套配置，减少读者从 33 条里自己挑。
- 真实排查记录：补"hook 配了但静默不生效"的案例，把事件选错、matcher 写错、能力被丢弃区分开。
