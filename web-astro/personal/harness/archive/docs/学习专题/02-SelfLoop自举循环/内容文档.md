# SelfLoop 自举循环内容文档

## 一、学习目标

- 能解释"循环只有几十行、价值在验证器"这句话，并说出最少需要哪几道闸门才敢相信一次提升。
- 能区分三个状态：分数变高、候选被接受、整轮 verified；知道它们为什么不能互相替代。
- 能跑一轮模拟，读懂分数曲线、候选 diff、闸门明细与停机原因。
- 能说出 canary 与完整性检查分别防什么，以及为什么隐藏用例不能喂给模型。

## 二、目标读者

- 做过评测或 agent 项目，想理解"自改进闭环"到底靠什么成立的人。
- 需要判断"模型说自己变好了"是否可信的产品与工程人员。
- 会读 Python、愿意动手跑一轮的读者。

## 三、知识边界

- 不教模型训练与微调；这里改进的是被验证的代码，不是模型权重。
- 不是通用 agent 框架，也不提供生产部署、多租户、权限隔离方案。
- 只实现一个任务（`intervalkit`）的闭环；换任务需要按 `tasks.py` 的契约补参考实现与用例。
- 真实模型模式可选，需要自备 key 与费用；默认模拟模式已足够看懂机制。

## 四、来源与核实

- 代码与 [README](../../../labs/selfloop/README.md) 是事实源；本专题的数字与流程均按当前代码核对。
- 自改进背景见 [research/05](../../../research/05-frontier-models-tech.md)：公开层面尚无产品化的自我改进闭环，本实验是机制演示，不外推为产品结论。
- 评测、闸门与"通过率不等于能力"的讨论见 [research/13](../../../research/13-agent-evals.md)。
- 分数、成本、停机阈值都来自代码默认值；改代码后要同步本专题与 README。

## 五、可延展的设想

- 多任务：再补一两个有参考实现的任务，观察 proposer 的泛化差异。
- 失败样本回放：从归档里挑被拒候选，分析是提议问题还是验证器覆盖不足。
- 成本曲线：把每轮 token 与费用画进报告，比较"更贵的提议"是否真的更快收敛。
- 反事实检查：故意放宽某道闸门，演示分数通胀如何发生。
