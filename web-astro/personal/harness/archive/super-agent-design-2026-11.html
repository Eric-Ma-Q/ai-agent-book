先统一九个词：Super-agent、Router、Worker、Trigger、Thread、Inline & Spill、链式召回、Watchdog、BYOM
Super-agent
跨会话保持上下文、同时推进多项任务且互不干扰的连续实体；不只是"一个更长的会话"。
Router 层
常驻的全局路由层，承接所有入口的人类交互，负责分派与全局记忆，不执行具体任务。
Worker 层
上下文隔离的执行会话，挂完整工具，通常用最强模型；不直接对用户说话。
Trigger
环境事件：群聊消息、邮件与日程提醒、代码评审评论、CI 运行结果。它取代提示词成为主要输入。
Thread
同一 PR、同一 IM 话题或同一封往来邮件串下的连续 Trigger 构成的流，是可订阅的单位。
Inline & Spill
把近期大概率用到的信息直接塞进窗口；把超预算或低频的完整内容留在窗口外，只留引用与摘要。
链式召回
每个对象带唯一 ID，注入时内联下一跳 ID，模型顺着引用图逐跳展开上下文。
Watchdog
主系统之外的独立监控会话，定时驱动，判断有没有实质进展、方向是否偏离，并能在线上修。
BYOM
Bring Your Own Machine：把日常开发机或个人电脑接入云端 Agent，而不是把环境搬到云上。

01

三分钟结论

如果只记一段话：这篇原文真正的论点不是"再做一个 Agent 产品"，而是"把会话管理从用户身上拿走"。它给的五个模块，每一个都在替人承担一件原本要手动做的事——记上下文、切任务、盯事件、守时在线、发现跑偏。

一句话

Session 是系统的实现细节，不是用户的认知负担；瓶颈从模型的执行能力转向人的注意力。原文用一组对照说明这件事：单任务的上限取决于模型能力，多任务的上限取决于人的注意力。[1]

01 / 判断

连续性不是"更长的上下文"

跨信道连续靠的是 Router 持有全局记忆，而不是把所有历史塞进一个窗口。上下文隔离的 Worker 各自干活，只有决策与结论回到 Router。[1]

02 / 判断

并发不是"多开几个会话"

并发靠的是上下文隔离 + 事件路由：已归属的后续事件由程序直通 Worker，全局节点只处理新任务与跨任务协调。[1]

03 / 判断

主动不是"定时任务"

主动性的前提是两级过滤：程序层挡掉大部分噪音，语义层才调用模型。没有这层，每条群消息都问一次模型，成本和延迟都撑不住。

04 / 判断

数字只能当量级

7.1 是合成负载、约 300 条消息、5 次重复、工作时长按 1/4 缩放；7.2 的 Worker 还是 Mock 模型。作者自己写"结果仅作为初步参考"。[1]

02

为什么单会话 + CLI/MCP 扩展不够

原文的起点不是技术偏好，而是一个已经发生的变化：以 Coding Agent 为代表的单任务 Agent 已经证明"模型 + 工具"能解决复杂问题，人越来越少需要逐步干预。人的角色上移到决策与验收——于是瓶颈换了位置。

近期个人助手集中涌现，直接接入消息、日程、邮件与工作平台，持续观察信息流。这种"持续在线、事件驱动"的模式并不只属于个人场景，它在软件开发等商业场景里同样成立。但主流 Agent 的工作单位仍是单一 Session，Session 之间彼此独立。[1]

死结 A

切换成本落在人身上

并行推进多项工作时，用户必须手动切换并记住各个 Session 的上下文。据原文观察，一个人通常只能同时跟进 3 到 5 个活跃 Session。

死结 B

同步阻塞

经典 ReAct Loop 里，一次工具调用会阻塞整个会话。任务在跑的时候，新指令进不来；多开对话又会让同一个任务的后续消息散落在不同窗口。

死结 C

离线即停

计算、会话状态、执行环境绑在同一台设备上。设备休眠或断网，Agent 就停止；换台机器，环境和凭据又都不在。

原文对"在单会话 Agent 上加 CLI、MCP 或外部连接器"这条路的评价很直接：能接外部消息，但仍受制于单会话同步阻塞、多任务上下文混乱、本地设备离线即停，需要大量人工维护。[1] 这三条正好对应上面的三个死结。

03

四个特征，五个模块

原文先把目标写成四个形容词，再倒推模块。这个顺序很重要：先问"要什么样的行为"，再问"要什么结构"。倒过来做，很容易变成"我们有了一个 Router，所以需要一个理由"。

连续

像始终只有一个 Agent

用户可以在 IM、GitHub 评论等熟悉界面交互，不需要想"Session X 里有没有 Y 信息"。先在 IM 说用方案 A、后在 PR 评论改成方案 B，它能理解并调整方向。

  • 承担：双层架构 + 面向人的交互
  • 反例：每个信道一个独立会话，用户自己同步结论
高效

不等上一步完成

交互响应快，同时能并行、高质量完成多个复杂任务；不必等上一条命令或任务结束就能接新指令。

  • 承担：双层架构 + 异步 ReAct Loop
  • 反例：一个循环串行处理所有事件，队列越排越长
主动

不需要的时候保持安静

持续观察环境事件，主动推进值得处理的事项；不需要介入时不出声。注意"安静"是特征的一部分，不是省事。

  • 承担：事件驱动（两级过滤 + 订阅直通）
  • 反例：每条消息都回一句"收到，我来看看"
持久

长期在线并自愈

始终在线、直接接入真实工作环境，长期运行遇到异常时自动恢复。恢复不只是重启进程，还包括发现"在跑但没进展"。

  • 承担：存算分离 + Watchdog
  • 反例：靠人看见报错再去点重启

04

双层架构：连续性与吞吐量的拆分

这是全文的枢纽。两个诉求天然冲突：要连续就得让所有事件看见同一份上下文；要吞吐就不能让它们排队进同一个循环。原文的解法不是折中，而是分层——把"维护全局连续性"和"高并发执行"分别交给两层。

方案 A

所有事件进同一个 Session

上下文最连续，但受单个 ReAct Loop 串行执行的速度上限约束，任务完成耗时长、吞吐低；多任务的中间细节还会混在一起，影响完成效果。

方案 B

每条事件新开独立 Session

并发吞吐最高，但任务之间并不总是独立；缺全局上下文会让结果彼此割裂，多个会话各自向用户响应也会造成交互混乱。

Router 层：为什么它敢不干活

Router 是常驻的全局路由层，承接所有入口的人类交互；跨任务的信息与决策都在这里汇总，它充当全局的序点、协调点和记忆。[1] 关键设计约束有两条：

不做具体任务，避免成为瓶颈

Router 不执行具体任务，只负责人机交互与任务分派，甚至可以不配备 Bash 工具。原文的实践结论是：Router 的任务常常没有想象中复杂，较轻量的模型就能兼顾速度与效果。

与 Agent Team 的分工不同

常见 Agent Team 用于单个复杂任务内部的步骤拆解，Team Lead 需要深入细节、规划子任务、高频协调，自身推理负载很重。Router 只处理任务之间的高层关联与分派，不介入单任务内部拆解。

可复用的等价形式

原文给了一个很实用的观察：如果用提示词约束一个 Agent Team 的主会话不亲自执行、只负责对外交互与分派，那么它也可以视为这种双层架构。也就是说，双层是职责划分，不要求两层各自只有一个会话。[1]

批处理：单个常驻会话为什么没有被压垮

问题很自然：所有交互都走一个常驻 Session，它不就是新的瓶颈吗？原文的答案是批处理——上一轮推理期间到达的事件会积压，在下一轮一并注入。Router 只做轻量交互与分派，每步通常是长输入、短输出；把积压的多条 Trigger 合并进一次调用，在 Prefill 阶段并行计算，单次请求耗时的增长远慢于批处理大小。

于是出现一个反直觉的区间：在一定范围内，积压越多，单个决定分摊的推理时间越低。上限取决于上下文长度，以及模型在一轮里能准确处理多少条 Trigger。

Worker 层：隔离、不越权、可嵌套

上下文隔离 + 最强模型

每个 Worker 在独立上下文中专注完成单一任务，挂载完整执行工具。因为直接决定任务结果与代码质量，通常配能力最强的模型。

不直接对用户

Worker 的推理过程与工具调用不输出到外部信道，只向 Router 汇报状态，由 Router 统一回复——这是"多个会话各自回复造成混乱"的解法。

同层不点对点通信

多个 Worker 的交集通常发生在同一个 PR 等共享环境；只要都订阅了对应 Thread，就会收到相同事件，有机会自行发现并解决冲突，少数跨任务协同由 Router 中转。

原文还特别说明了两点"透明性"：Worker 内部可以再创建 Subagent，也可以本身就是一个 Agent Team，这些对上层的 Router 保持透明。个人助手场景同理——界面上只有一个聊天页维持连续，底层可以为每个话题分别分派 Worker，并行推进任务、起草回复。

规模再大怎么办

当单个 Router 会话确实不够用时，原文给出的方向是层内再设计：多层过滤结构，或水平切分为多个会话。这又回到同一个权衡——切分粒度越细，Router 的并发吞吐越高，但分片之间的记忆与上下文连续性越低；在全局记忆问题被解决之前，这个权衡始终存在。

05

事件驱动：从"等人说话"到"看环境说话"

主动性的代价是噪音。真实的群聊与代码平台是"高噪音、低触发率"：绝大多数消息不需要 Agent 介入。如果每条都调一次模型，延迟和成本都不可承受。原文的解法是把计算机系统里的 Fast Path / Slow Path 搬进来。

第一步：两级过滤

FAST PATH · 程序层

确定性条件用代码挡

按事件来源、群组范围、用户或机器人白名单做快速准入，例如对不同来源分别设置"仅响应明确请求""作为候选事件""直接忽略"。在调用模型前滤掉大部分无关消息。

SLOW PATH · 语义层

需要理解的才交给模型

通过程序层准入的候选交给 LLM，由它根据提示词策略与上下文判断是否需要行动。语义层同时是面向人的自然语言扩展点：随时开关或新增策略。

第二步：订阅与直通

Router 创建 Worker 之后，如果把每个后续事件都转一次，全局节点会重新变成瓶颈。于是路由也套用同一思路：同一个 PR、同一个 IM 话题或同一封往来邮件串下的连续事件构成一条 Thread，Worker 直接订阅它。

订阅是多对多的：一个 Worker 可以订阅多个 Thread，一个 Thread 也可以被多个 Worker 订阅。多个 Worker 在同一个工作环境里发生交集时，Thread 下的新事件会同时直通给所有订阅者——它们不需要点对点通信，也有机会获知彼此的操作并自行解决冲突。输出侧仍然收口到 Router：Worker 汇报关键结论，Router 统一回复并同步全局记忆。

第三步：投机执行

最后一层是提前行动。借鉴投机执行的思想，Agent 可以在还不确定结果是否被采用时，先根据环境信号在后台尝试，用额外算力换人的等待时间；结果有价值就交付，没价值就丢弃。原文给了两个例子：

个人助手：会前先备好

收到会议邀约或待办消息时，先在后台核对日程冲突、搜集背景资料、备好回复草稿；用户过目后直接确认发出。

研发群：静默复现并修复

群里有人反馈问题或讨论改动方案时，先在后台尝试复现并找修复方案；确认问题且找到简单修复才交付，否则全程保持安静。

这条最容易被做坏

"静默复现并修复"的门槛是"确认 + 简单修复"两个条件同时成立。只放宽其中一个，就会变成在群里抢答、或者提一堆没人要的 PR。原文把它当策略写在提示词里，说明它靠的是判断力而不是流程。

06

上下文组织：把窗口当缓存管

事件驱动把输入从"有限的人类提示词"换成了"环境持续产生的半结构化事件"。注入过多会挤占窗口、稀释注意力；注入过少会逼模型反复调工具。原文用一句话概括取舍：浪费上下文窗口，就是浪费模型的智能。

做法是把窗口当 Cache 管理，只用两个基本操作：Inline 把近期很可能用到的信息直接内联进窗口，省掉工具往返；Spill 把超出预算或低频的完整内容留在窗口外，只保留引用或摘要。

STEP 1

从最少信息开始

最初只提供当前对象的 ID 和内容摘要。模型的第一次判断不需要全文。

STEP 2

按局部性逐步 Inline

先附紧密关联对象的 ID，再附时空相邻内容：正文前 50 字、IM 消息的前后相邻消息与所回复的消息、代码评论所在讨论的相邻评论。

STEP 3

超出上限就 Spill

对无法全部 Inline 的长内容设较小长度上限，超出部分截断并保留续读入口；模型需要完整内容时再调工具读取。

同一件事，三种注入深度

窗口内容是示意，结构照原文三步

链式召回：一张可以逐跳展开的引用图

长期运行后，Router 既放不下所有任务的全量历史，又要在用户跨信道提起旧任务时找回上下文。原文把 Inline & Spill 一致地应用到各类对象上，得到按需展开的多跳检索：为 Trigger、Thread、Worker Session 等对象赋唯一 ID，注入时内联紧密关联对象的 ID，使这些对象在底层构成一张引用图。

由于每一次工具召回返回的对象本身也遵循 Inline & Spill，结果里又会带上下一跳的摘要与 ID——模型于是可以从当前事件出发，顺着引用关系逐步召回。原文的例子是：从一条当前消息读到所在 Thread，再从 Thread 内联的 ID 追到相关 Worker Session，进而找到该 Worker 关联的另一个代码评审 Thread。

本页判断

这套机制本质是把"该给模型什么"从一次性决定改成一串小决定，每一跳都可以由模型按需触发。代价是可能多出几次工具调用；省下的窗口要靠调用次数换回来。原文只给了机制，没有给"多跳召回的总延迟"数据，这一点在评估时要自己补。

站内延伸：第 2 章 · 上下文工程 讲 KV Cache 友好设计、压缩与动态提示；这一节补的是"事件流场景下的注入策略"。[6]

07

面向人的交互：取消阻塞，按信道说话

双层解决了上下文层面的连续，但交互层还有两个具体问题：工具调用会阻塞会话；不同信道的带宽差异极大。原文对这两个问题各给了一个改法。

4.1 异步 ReAct Loop：把 run() 换成 start() / stop()

经典 ReAct Loop 里，模型发起一次同步的 run() 工具调用后循环阻塞，直到工具返回；在此期间会话无法响应任何新输入。改法是把它变成全双工：

表 3 · 同步与异步的差别
环节经典 ReAct Loop异步 ReAct Loop
发起run() 阻塞等待start() 立即返回「已启动（Started）」
执行期间会话无法接收新输入前台对话继续，可随时接新指令
结果回传作为工具返回值作为一条新的事件消息投递进会话
中断无内建手段模型可按上下文调用 stop() 终止过长的后台命令
新输入排队到本轮结束之后在当前推理步结束后即被处理，不等后台工具完成
原文自述

这套异步任务机制已经在 DeepSeek Harness 中实现，但尚未默认开启。[1] 读这句要小心：机制存在，不等于线上默认行为是这样。

4.2 多信道：输出要匹配带宽

把面向单人终端的交互方式直接搬进群聊，把冗长的推理与密集的工具调用原样输出，在多人协作里就是信息过载。双层已经隔离了大部分噪音——推理与工具调用都留在 Worker 内部，对外只有 Router。在此基础上，原文按信道定制规范：

高打扰成本

IM 等即时通讯

低打扰的轻量沟通：像人类同事一样只在需要决策或验收时发通知，只问直接问题、给简短结论。原文验证过一条硬规定：单次回复不超过 100 词。

高信息密度

GitHub、邮件与文档

结构化异步交付：建或更新 PR 时按项目规范写清问题背景、改动说明与验证结果；个人助手场景下直接起草结构化邮件与文档摘要。

站内延伸：第 6 章 · 交互：观察与动作空间的扩展 讨论输入输出模态与任务时间结构；这一节补的是"同一 Agent 在多种信道上的输出规范"。[7]

08

计算、状态与环境的分离

持久在线要解决的不是"别关机"，而是三件被绑在一起的事：推进 Loop 的计算、要长期保存的会话状态、代码仓库与本地工具链等执行环境。原文分两步拆，顺序不能换。

第一步：计算与状态分离

推进 Loop 的计算可以做成无状态的，需要持久保存的只是会话状态。于是把计算放进云端无状态弹性容器，把 Session 等状态存进数据库：容器可以水平扩展、重启或替换，连续性由持久化存储保障。Agent 由此摆脱单台设备的生命周期。

第二步：Loop 与执行环境分离

常见两种思路都有硬伤：一种是在云端起沙箱、拉代码、重建环境——但真实工作环境含未提交的本地修改、私有凭据、内网服务依赖、特定硬件或工具链，同步成本高且容易漏；另一种是要求用户放弃本地环境迁到云端——迁移成本太高。

原文的关键一句

既然难以复制和同步的是环境本身，就不必让执行环境跟着 Agent Loop 上云。让 Loop 在云端运行，让重状态的执行环境留在原地，只在端侧部署一个不保存会话状态的轻量 daemon，只负责执行命令与返回结果。

支持 BYOM

把用户日常使用的开发机或个人电脑接入云端 Agent；也支持云端托管机器或按需创建的计算环境。一个 Agent 不再受限于单台机器。

支持间歇在线

某台个人设备重新上线后，云端 Agent 可以自动触发并完成需要在该设备上执行的任务。这条对"笔记本 + 台式机"的人是刚需。

09

Watchdog：把运维也交给模型

持久在线的分布式系统很难只靠主系统内部逻辑长期可靠运行，需要在主系统之外引入独立的控制回路。原文的特别之处是：这个回路不是一个监控脚本，而是一个完整的 Agent Session。

为什么探活不够

许多异常并不是进程崩溃，而是模型在执行中陷入无效循环或偏离目标。所以长期运行的 Agent 系统不仅需要监控基础设施存活，还需要监控任务本身的进展。

它具体做什么

处理接口报错、状态恢复失败等基础设施故障；由模型判断各 Worker 是否有实质进展、方向是否偏离整体目标；发现异常及时介入，遇到外部偶发故障则持续复查直到恢复。

因为它本身也具备完整工具能力，维护者可以用自然语言向它询问故障原因，也可以让它在线修正主系统的行为，例如增删提示词、调整触发规则。这是一个很容易被忽略的设计选择：把"运维接口"从命令变成对话。

本页的质疑

原文没有讨论 Watchdog 自己的失败模式。它和被监控系统往往同源——同一批模型、同一套提示词、同一套工具，很可能共享同样的盲区；而它手里又有修改主系统提示词与触发规则的权力。第 11 节的第 3 条会接着说这件事。

10

实验与数字：能读出什么，不能读出什么

原文给了两组实验。7.1 用端到端场景对比四种方案，7.2 单独压测 Router。作者自己写明：实验基于合成负载与简化环境，部分设置还可以更严谨，结果仅作初步参考。[1]

7.1 消融：四种方案，同一批消息

设定如下：用群聊和 GitHub CI 消息流同时驱动四种方案；单次实验约 300 条消息，其中约 20 条是工作请求，其余是闲聊、跟进、叫停与 CI 消息；编码工作用一个只消耗时间的工具代替，因此衡量的是调度与协作能力，而不是单个任务的执行能力；每种方案重复 5 次；消息间隔与工作时长按 1/4 缩放，模型调用耗时为真实值。

四方案对照

三个结论值得单独拎出来：

结论 1

提示词决定不了分工

带 Subagent 工具的单会话在中性提示下，5 次运行里一次都没调用 Subagent，所有工作都在主会话里被新消息不断打断，p95 达到 29.5 分钟。改成"优先委派"后 4/5 次委派，仍慢于双层。

结论 2

架构比提示词稳

双层让 Router 不执行具体工作、Worker 只接收所订阅 Thread 的消息，把"要不要分工"从模型的临场判断变成系统结构。剩下那 1 次模型自判"工作很小"，就是长尾。

结论 3

直通买的是成本

去掉直通后完成时间基本一致，但 Router 需要做的决定多了约 30%，读缓存 token 从 2323 万涨到 3177 万（+37%）。直通不提升质量与速度，它省的是全局节点的开销。

代价也说清了

原文承认 Super-agent 单次实验的读缓存 token 高于单会话方案：它是用更多 token 换更短、更稳定的完成时间。这是一个明码标价的取舍，不是免费的架构升级。

7.2 压测：Router 会积压，但积压有收益

Router 调真实模型、Worker 用 Mock 模型，把需要决定的 Trigger 到达速率从每分钟约 1 条逐步升到约 40 条：平均 batch 从 1.0 升到 2.8，单次请求耗时只从 2.5 秒升到 3.9 秒，单个决定分摊的推理时间从 6.4 秒降到 1.6 秒。

这条曲线解释了两件事：一是为什么 7.1 里即便去掉直通、Router 峰值负载增加，也没触及单 Router 的吞吐瓶颈；二是为什么原文认为在当前团队规模下，不必过早对 Router 做水平切分而牺牲全局上下文的连续性。

六个限制

① 合成负载，不是真实团队流量；② 编码工作被替换成纯耗时工具，测的是调度不是执行质量；③ 只有 5 次重复；④ 消息间隔与工作时长按 1/4 缩放；⑤ 7.2 的 Worker 是 Mock；⑥ 全部数据来自同一团队自评，无第三方复现。任何"成本降低 X%"式的转述，都必须带上这几条。

11

开放问题：原作者自己没解决的部分

第 8 节的四条限制，比前面五个模块更值得产品经理读。它们决定了这套架构现在能在哪用、不能在哪用。

8.1

双层怎么扩展

单 Router + 订阅直通 + Worker 不直接通信，是"当前规模够用"的组合。任务变大、耦合变高时，Router 何时水平切分、粒度怎么划、同层 Worker 何时需要直接通信与什么拓扑，都还没有定论。另外提到系统与模型的协同设计：针对事件判别、批量分派、上下文召回做专项训练。

8.1 续

长程记忆是下一个瓶颈

常驻 Router 加基于引用图的链式召回，解决的是"近期任务与会话历史"的按需检索。运行周期拉长到跨月，长程记忆就成为可扩展性的主要瓶颈。

8.2

脱离 Session 之后怎么协作

把底层多会话对用户隐藏之后，"怎么向用户呈现任务、提供自然的交互与项目管理"成了新问题。原文认为以聊天窗口为中心是路径依赖，交互可以更多发生在领域特化界面里（例如直接在 Issue 与 PR 中工作）。过渡期内还需要"用户随时介入、接管或实时协同"。

8.3

上下文边界与 A2A

组织决定怎么配备 Super-agent，本质是在划上下文共享与隔离的边界：需要共享的共用实例，需要隔离的各自独立。一旦存在多个互不共享上下文的实例，跨边界的协同就是 A2A；在权限边界各异的前提下如何安全可靠地通信，仍需探索。

8.4

安全与隐私

事件驱动扩大了不可信输入的接触面。云端 Loop 持续接入外部事件、端侧又存有私有代码与凭据时，一旦云端被入侵或提示词注入攻破，它连接的全部端侧设备都面临被控制的风险。即便云端未被攻破，凭据进入上下文也有泄露风险，需要设计"Agent 不接触凭据本身也能使用凭据"的机制。

本页补充

三个原文没展开的风险

① Watchdog 与被监控系统同源，可能共享盲区，且它有权改主系统；② 全文没有成本侧写——多会话 + 常驻 Router 的账单结构没有给出；③ 多 Worker 订阅同一 Thread 的"自行发现冲突"缺少失败案例。

安全条目值得单独记住

8.4 是全文唯一一条作者用"隐患"来形容的设计后果。任何"云端 Agent + 端侧 daemon"的方案评审，都应该先回答两个问题：云端被注入后能对端侧做什么？凭据会不会进入模型上下文？

不能照抄的三条

前提 A

“单个 Router 够用”

这是原文在自己团队规模下的结论，并且依赖批处理把积压转成吞吐。团队更大、事件更杂时，先测 Router 的决定数与上下文占用，再决定要不要分层或切分。

“3–5 个活跃 Session”

“去掉直通也差不多”
