任务队列Agent 的第二条时间线

Agent 只有一条执行时间线：当前这一步；用户却常常已经想到下三步。任务队列就是这两条时间线的接口。 它看起来只是输入框旁边一列灰色的待办；真正决定的是三件事：用户能不能在 Agent 工作时继续表达，任务能不能跨会话活下来，崩溃之后会不会重复执行。 本文把 Claude Code、Cursor、Codex、Devin 与 Temporal、SQS 放在同一张图上，拆出四条车道、六个契约、九个状态，再给出一套从 Postgres 表到 worker 循环的最小实现。

一句话结论

任务队列不是把用户输入排成队，而是把「什么时候生效」写成一份可验证的契约。产品上说不清生效点，工程上就会用丢消息、重复执行和幽灵写入来买单。

  • 队列的单位是承诺，不是消息。steer 承诺「下一个安全边界生效」，follow-up 承诺「下一轮」，task 承诺「最终会跑」，approval 承诺「人来决定」。四种承诺的生命周期不同，不能用一条 FIFO 装。
  • 产品上最难的不是排队，是分诊。同一条输入，按按键、按设置、按内容还是按类型分流，会得到完全不同的可预测性。最差的做法是系统猜了，却不告诉用户它猜成了什么。
  • 工程上最难的不是并发，是状态。谁持有租约、谁有权写结果、崩溃后谁负责重试；这三件事决定队列会不会变成重复扣款机。
  • 体验上最难的不是进度，是解释。用户要知道「为什么在等、还要等多久、下一步会发生什么」，而不是只看到一个转圈。

01四条车道：不要用一条 FIFO 装四种承诺

先把「队列」拆开。Agent 产品里至少有四种东西在排队，它们的生效点、持久化要求和失败语义完全不同。把它们塞进同一条 FIFO，短期能跑，长期一定出问题：审批排在一小时的任务后面，取消排在十条补丁后面，转向被当成下一轮任务。

Lane 1 · Steer

改方向，不换任务

用户看到 Agent 走偏，想补一句约束、换一个文件、停止某个方向。它应该落在下一个安全边界，而不是打断正在进行的工具调用。

典型
「先别改前端，只修 API」「用 pnpm，不要 npm」
生效
下一次模型调用前 / 工具返回后
持久
否，可合并；运行结束前有效
失败
丢弃并告知，或降级为 follow-up
Lane 2 · Follow-up

下一轮再做

用户把后续工作交给同一个会话。它不该打断当前任务，但要保证在当前 turn 或当前 task 结束后按顺序执行。

典型
「跑完测试后把失败的三个用例修了」
生效
当前 turn / task 结束
持久
是，至少跨界面切换
失败
作为新 run 重试，保留原顺序
Lane 3 · Task

独立工作单元

一件可以独立调度、独立失败、独立重试的工作。它有自己的生命周期，不需要绑定在某次对话的当前轮次上。

典型
「给这 20 个仓库补 LICENSE」「每晚跑一次回归」
生效
调度器领取时
持久
是，跨重启、跨机器
失败
至少一次 + 退避重试 + 死信
Lane 4 · Approval

人来决定

Agent 已经跑到一个需要授权的点。它不是「待办」，而是一个阻塞中的等待状态；人不做决定，任务不能继续，也不该被自动重试。

典型
「允许删除这 12 个文件吗」「允许推送这个分支吗」
生效
决定到达时
持久
是，带 TTL 与审计
失败
超时拒绝 / 取消，不自动放行
四条车道的语义差异
车道用户意图生效点持久化顺序失败语义
Steer改变当前任务的方向下一个安全边界否，可合并按到达，允许覆盖丢弃并告知，或降级为 follow-up
Follow-up把后续工作交给同一会话当前 turn / task 结束是会话内 FIFO作为新 run 重试
Task独立、可调度的工作调度器领取是优先级 + 公平至少一次，退避 + 死信

分诊机制本身是产品设计

四条车道不会自己分类。用户按下回车的那一刻，产品必须决定这条输入进哪条道。这个决定可以由按键、设置、内容或类型触发；四种方式没有绝对优劣，但必须满足三条：可预测、可覆盖、可解释。

设计建议

默认值可以智能，但发送前要显示「这条会排队 / 会转向 / 会立即执行」，并允许一键改。用户不需要理解队列实现，但必须能预测自己按下回车后会发生什么。

02六个契约：队列到底向用户承诺了什么

队列不是数据结构，是一组承诺。下面六个契约，任何一个说不清，都会在某个边界变成 bug。产品文档里应该逐条写出来，接口和测试才有依据。

六个契约与对应的失败
契约要回答的问题说不清的样子
准入什么能进队列？谁有权进？满了怎么办？队列无限增长；非法命令在运行时才报错；重复提交生成两条任务
排序谁先跑？能不能改？改了之后原来的位置怎么办？拖动排序后序号冲突；跨租户严格 FIFO 导致大客户饥饿
生效什么时候从「排队」变成「生效」？用户以为任务结束才跑，系统在中间轮次就放行
取消取消的是排队项、运行中的任务，还是已经产生的副作用？取消后子进程还在跑；取消被当成删除，审计缺失
持久化刷新、切会话、关应用、崩溃之后，什么还在？切个聊天队列就消失；重启后重复执行
可见性用户怎么知道它在等什么、下一步是什么？只有一个转圈；状态与真实执行不一致

2.1 准入：在入队时拒绝，不要等到运行时

准入要回答三件事：能不能进、进多少、重复了怎么办。Claude Code 把一部分命令做成「发送即执行」，例如 /status、/model 这类改变设置或查询状态的命令；它们不进入队列，因为排队会让用户以为设置已经生效。[1] Cursor 的 Cloud Agents API 在 steer 请求里只允许 prompt 与 delivery，带 model、mode 等字段会直接返回 400，避免「转向」偷偷变成「新任务」。[3] Devin 的自动化则给每次运行设了条目上限、调用频率与 ACU 预算，超出上限的条目不会被静默执行，而是留给下一次脚本运行重新发出。[8]

工程上，准入检查应该发生在 API 层，而不是 worker 里：参数是否合法、权限是否明显不足、队列是否已满、幂等键是否重复。运行时再检查一次权限，是为了防止「入队时允许、执行时策略已变」。

2.2 排序：FIFO 是默认值，不是全部

会话内最符合直觉的是 FIFO：用户按顺序输入，就按顺序执行。Claude Code 明确说，turn 结束时仍未处理的消息「按输入顺序」发出。[1] Cursor 允许拖动排序，说明队列顺序是用户可见、可编辑的状态，而不是内部实现细节。[2]

跨会话、跨租户就不能只有 FIFO。Temporal 的 Task Queue 默认有 4 个分区；单分区「几乎总是 FIFO」，多分区时任务被随机分配到分区，严格顺序不再成立。[9] 这不是缺陷，而是吞吐与顺序的取舍。产品要明确：你承诺的是会话内顺序，还是全局顺序？前者便宜，后者昂贵，而且通常不需要。

2.3 生效：把「什么时候」写成一个枚举

这是整个队列最重要的一个字段。用户看到的「排队中」至少有五种不同含义：

立即执行不排队，例如 /status、切换模型。用户期待设置马上生效，排队反而制造误解。
下一个工具边界steer 的典型语义。不打断在途工具，等它返回后把新指令注入上下文。Cursor 的 steer 明确说「在 Agent 的下一个工具调用时送达」。
当前 turn 结束Claude Code 的命令与 shell 命令；普通消息在工具调用结束后就进入模型，turn 结束时仍未处理的消息按顺序发出。
当前 task / goal 完成Cursor 的队列「等当前任务完成后依次处理」；Codex 的 Queue 设计意图是「当前任务完成后作为下一轮发送」。
人工决定审批。没有决定就不继续，超时按拒绝或取消处理，不自动放行。

Codex 的缺陷报告正好说明这条契约有多脆：用户把 Follow-up behavior 设为 Queue，期待「任务彻底完成后再执行」，实际却在某个中间内部轮次就被放行。报告里写得很清楚：「Queue 看起来是『下一个内部轮次』，而不是『任务完成之后』，但 UI 没有说清这个区别。」[4] 这不是调度器写错了，而是生效点没有被建模、没有被显示、也没有被测试。

2.4 取消：取消不是删除

取消要分三层：排队项取消（还没开始，直接从队列移除并记一笔）、运行中取消（发协作式取消信号，在下一个安全检查点退出，必要时终止子进程）、副作用取消（已经发出的工具调用、已经写入的外部系统，通常不能撤销，只能补偿）。

Claude Code 的 Esc 会打断当前 turn，但保留已排队的内容并立刻发送；后台任务在退出时会清理，macOS / Linux 上还会处理 setsid 这类脱离 shell 的进程。[1] 这说明取消是一个有状态、有清理、有审计的动作，不是把数组元素删掉。

2.5 持久化：队列必须比界面活得久

Claude Code 的队列会随会话进入后台，用户可以在后台会话里继续处理；但命令、! shell 命令和带 IDE 选区的消息不能跟着走，产品会明确阻止「带着它们后台化」。[1] 这是好的设计：不能持久化的东西，提前说不能。

反例是 Codex App 的缺陷：队列在切换聊天后从 UI 消失。用户预期「排队项应该一直可见，直到执行、取消或删除」，实际却只存在于当前视图。[5] 这提醒我们：队列的 source of truth 必须在服务端或本地数据库，UI 只是投影；切换视图不能重建队列。

2.6 可见性：每个等待都要有原因和下一步

「排队中」不是一种状态，至少是「等当前任务」「等审批」「等重试」「等容量」四种。用户看到的应该是一个原因 + 下一步 + 可做的动作，而不是一个转圈。Cursor 的 Cloud Agents API 把 steer 的结果明确分成 steered（已进入当前 run）和 queued（没有活跃 run，转为下一次 follow-up），并返回对应的 runId 或省略。[3] 这就是可见性契约的接口化：不要只说「收到了」，要说「它在哪条车道、什么时候生效」。

03界面与状态机：九个状态，七个零件

状态机的价值不是画得漂亮，而是让 UI、接口和测试说同一种语言。下面九个状态覆盖了从入队到终态的主路径；任何一条「状态之外的临时标志」都会让排查变难，所以取消、审批、重试都要落到明确状态或明确字段上。

running →retry_wait→ queued；running →failed/cancelled/dead

七条界面规则

  1. 队列跟着会话走。切换聊天、进入后台、重新打开，队列都应该还在；否则它不是队列，只是当前视图的草稿。
  2. 未处理的消息灰显。Claude Code 用灰色区分「已发送但还没开始处理」和「已经被模型读到」，这个细节能显著降低「它到底看没看见」的焦虑。[1]
  3. 顺序可编辑，但要有稳定 id。Cursor 允许拖动排序；拖动后要更新服务端序号，不能只改 DOM。[2]
  4. 能取回，就能编辑。Claude Code 在输入框第一行按 Up 可以把排队内容取回输入框，编辑后重新入队。[1]
  5. 不能带走的，提前禁用。命令、shell 命令、带 IDE 选区的消息不能进入后台会话，Claude Code 会阻止后台化并提示先处理它们。[1]
  6. 「立即发送」与「排队」必须能互相覆盖。Cursor 用 Cmd/Ctrl+Enter 绕过队列；Claude Code 用 Ctrl+Enter 立即发送，旧终端不支持时用 Ctrl+X Ctrl+S。[1][2]
  7. 状态文案要写「下一步」，不要只写「排队中」。「将在当前任务完成后执行」比「queued」有用一百倍。

04产品对照：六种实现，三类承诺

同样叫 queue，不同产品解决的不是同一个问题。交互队列解决「什么时候听用户的」，任务队列解决「什么时候跑哪件事」，分发队列解决「哪台机器来跑」。把它们混为一谈，就会拿 Temporal 的语义去要求一个输入框。

Claude Code 的粒度最细：它把「消息」和「命令 / shell」分开，因为两者的权限、执行位置和持久化能力不同。[1] Cursor 把「排队」和「转向」做成两个明确的动作，并用按键区分；Cloud Agents API 进一步把 steer 的结果分成 steered 与 queued，并规定每个 agent 同时只能有一个活跃 run，重复创建会返回 409 agent_busy。[3] Codex 把选择放进全局设置，Queue 与 Steer 二选一；官方 CLI 文档把 steer 描述为「引导当前 turn，同时把后续工作留在同一会话」，但并没有规定它在第几个内部步骤生效。[7] 它的缺陷报告显示，Queue 的实际生效点曾漂移到「下一个内部轮次」，而且队列在切换聊天后会从 UI 消失。[4][5]

一个反直觉的细节

Codex 社区里有人观察到，Steer 并不总是「立刻插入当前思考」，而更像「当前 turn 结束后再消费的 follow-up」。这说明转向的语义不能靠名字暗示，必须在接口和 UI 里写清楚：是插入当前上下文，还是排到当前 turn 之后。[6]

4.2 任务与分发队列：Devin、Temporal、SQS

任务队列与分发队列
系统队列单位领取方式顺序失败处理关键限制

Devin 的自动化把「队列」做成了产品可见的限制：条目有 id 去重、每次运行有上限、失败会释放、频率和 ACU 有预算。[8] Temporal 的 Task Queue 是 worker 的分发机制，不是用户任务的 backlog；任务持久化在 workflow history 里，队列本身是轻量、按需创建的。[9] SQS 的可见性超时本质上是一个租约：消费者拿到消息后，消息对其他消费者暂时不可见；处理完要删除，超时未删就会重新出现，多次失败进入死信队列。[10]

选型提示

如果你的「队列」需要回答「用户这条消息什么时候生效」，先做产品语义，不要先选 broker；如果你需要回答「哪台机器跑这个工具调用」，再考虑 Temporal / SQS。两者可以叠在一起，但不能互相替代。

05十二个失败模式：队列是怎么坏掉的

队列的 bug 很少是「队列本身」坏了。更多时候是语义没写清、状态没落库、租约没 fencing、或者 UI 把服务端状态抄了一份。下面十二个模式，多数有真实产品或工程证据，个别是设计推论。

失败模式、根因与修法
#症状根因修法证据

最贵的一类 bug

不是「任务没跑」，而是「任务跑了两次，而且第二次没人知道」。重复执行的代价通常不是算力，而是外部副作用：重复发邮件、重复扣款、重复开 PR、重复删文件。队列设计的第一优先级不是吞吐，而是让重复可检测、让副作用可幂等。

06数据模型：三张表，九个状态

不要用一张表同时存任务、信号和日志。它们的保留期、写入频率、查询方式和一致性要求都不同。一个够用的最小模型是三张表：agent_tasks 存承诺，run_signals 存转向，task_events 存审计。

6.1 任务表

PostgreSQL · 任务与状态最小字段集
create table agent_tasks (
  id               uuid primary key,
  tenant_id        text not null,
  agent_id         text not null,
  session_id       text not null,
  kind             text not null check (kind in ('follow_up', 'task', 'approval')),
  state            text not null check (state in (
                     'queued', 'claimed', 'running', 'waiting',
                     'retry_wait', 'succeeded', 'failed', 'cancelled', 'dead')),
  priority         int  not null default 0,
  seq              bigint generated always as identity,
  position         numeric not null default 0,
  drain_policy     text not null check (drain_policy in (
                     'next_tool', 'turn_end', 'task_end', 'human')),
  payload          jsonb not null,
  idempotency_key  text not null,
  attempts         int  not null default 0,
  max_attempts     int  not null default 3,
  available_at     timestamptz not null default now(),
  lease_owner      text,
  lease_epoch      bigint not null default 0,
  lease_until      timestamptz,
  cancel_requested_at timestamptz,
  created_at       timestamptz not null default now(),
  started_at       timestamptz,
  finished_at      timestamptz,
  result           jsonb,
  error            jsonb,
  unique (tenant_id, idempotency_key)
);

create index agent_tasks_claim_idx
  on agent_tasks (state, available_at, priority desc, position, seq);

-- 每个 agent 同时只有一个活跃 run；并行靠多个 agent，而不是同一个 agent 并发
create unique index agent_tasks_one_active
  on agent_tasks (agent_id)
  where state in ('claimed', 'running', 'waiting');

几个字段的用意：

  • seq 是不可变的创建顺序，position 是可变的展示顺序。拖动排序只改 position，不重写历史；建议用稀疏数值（1024、2048……），插入时取相邻两条的中点，避免整表重排。
  • drain_policy 把「什么时候生效」从实现细节变成数据。worker 不在运行时猜，UI 也能直接显示。
  • lease_epoch 是 fencing token。每次领取加一，完成时带着它写回；旧 worker 的写回会命中 0 行。
  • idempotency_key 防重复提交；payload 只存引用，不存几 MB 的对话历史。

6.2 信号表

PostgreSQL · steer / cancel 信号短生命周期
create table run_signals (
  id          bigserial primary key,
  task_id     uuid not null references agent_tasks(id) on delete cascade,
  seq         bigint not null,
  kind        text not null check (kind in ('steer', 'cancel')),
  body        jsonb not null,
  client_key  text,

  on run_signals (task_id, seq)
  where consumed_at is null;

信号与任务分开，是因为它们的生命周期完全不同：任务可能活几小时，信号通常只活一个 turn；任务要审计，信号可以合并；任务失败要重试，信号丢了通常只需要告诉用户「没送到」。把 steer 塞进任务表，会让「任务」这个概念同时承担「工作单元」和「对话事件」两种职责。

6.3 事件表

PostgreSQL · 追加写审计只 insert，不 update
create table task_events (
  id         bigserial primary key,
  task_id    uuid not null,
  event      text not null,
  from_state text,
  to_state   text,
  actor      text not null,
  at         timestamptz not null default now(),
  detail     jsonb
);

create index task_events_task_idx on task_events (task_id, at);

事件表负责三件事：审计（谁在什么时候改了什么）、回放（事故后重建状态）、度量（等待、重试、取消的分布）。它不应该被用来做「当前状态」查询；当前状态永远以 agent_tasks.state 为准。

6.4 六条不变量

  1. 一个 agent 同时只有一个活跃 run。用部分唯一索引兜底；并发靠多个 agent、多个会话，而不是同一个会话里并行改文件。
  2. 终态不可回退。要重做就新建一条任务，保留原任务的审计记录；否则「失败后悄悄复活」会破坏所有统计。
  3. 每次领取递增 epoch。完成、失败、心跳都必须带 lease_owner + lease_epoch；否则旧 worker 会变成幽灵。
  4. 队列顺序只由服务端决定。前端拖动只发「把 X 移到 Y 之后」的意图，服务端重算 position 并记录事件。
  5. 幂等键在租户内唯一。同一件事重复提交返回原任务，不新建；不同租户可以复用一个键。
  6. payload 有上限。大文本、图片、文件放对象存储，表里只存 URI 与哈希；否则队列会变成第二个数据库。

07领取与租约：不要在一次 Agent 运行里持有事务

数据库队列最常见的错误，是把「领取」写成「开事务 → 锁行 → 跑 Agent → 提交」。Agent 可能跑十分钟，事务会一直持有锁，连接池很快耗尽，其他 worker 只能排队。正确做法是：领取是一个短事务，提交后靠租约维持所有权；完成是另一个短事务，用 epoch 做 fencing。

7.1 原子领取

PostgreSQL · claim一条语句完成选行、加锁、改状态
with candidate as (
  select id
  from agent_tasks
  where state = 'queued'
    and available_at <= now()
    and cancel_requested_at is null
  order by priority desc, position, seq
  for update skip locked
  limit 1
)
update agent_tasks t
set state       = 'claimed',
    lease_owner = $1,
    lease_epoch = t.lease_epoch + 1,
    lease_until = now() + interval '30 seconds',
    attempts    = t.attempts + 1,
    started_at  = coalesce(t.started_at, now())
from candidate c
where t.id = c.id
returning t.*;

FOR UPDATE SKIP LOCKED 让并发的 worker 跳过已被别人锁住的行，而不是排队等锁；它把「选一行」和「锁一行」合成一个原子动作，避免两个 worker 同时选中同一条任务。[11] 这个锁只在领取事务里有效，提交后就释放；真正的所有权由 lease_until 维持。

7.2 心跳与完成

PostgreSQL · heartbeat / complete两者都必须带 epoch
-- 每 10 秒续一次；租约 30 秒，留两次重试空间
update agent_tasks
set lease_until = now() + interval '30 seconds'
where id = $1
  and lease_owner = $2
  and lease_epoch = $3
  and state in ('claimed', 'running', 'waiting');

-- 完成时校验 owner + epoch；0 行说明租约已经丢了
update agent_tasks
set state = 'succeeded',
    finished_at = now(),
    result = $4,
    lease_owner = null,
    lease_until = null
where id = $1
  and lease_owner = $2
  and lease_epoch = $3
  and state in ('running', 'waiting');

如果完成语句返回 0 行，worker 不应该重试写回，而应该丢弃结果并记录「lease lost」。因为这意味着另一个 worker 已经接手；再写一次就会覆盖新结果，甚至产生两次副作用。SQS 的可见性超时是同一个思路：消息在处理期间对其他消费者不可见，超时未删除就重新出现。[10]

7.3 回收过期租约

PostgreSQL · reaper由独立进程或定时任务执行
update agent_tasks
set state = case
      when attempts >= max_attempts then 'dead'
      else 'retry_wait'
    end,
    available_at = now() + make_interval(
      secs => least(300, (power(2, attempts)::int * 2))
    ),
    lease_owner = null,
    lease_until = null
where state in ('claimed', 'running', 'waiting')
  and lease_until < now();

退避时间要有上限和抖动，否则大量任务会在同一秒重试，形成二次雪崩。SQS 的可见性超时最长 12 小时，超过这个尺度的任务应该拆成多个步骤或改用 durable execution，而不是无限延长租约。[10] 对 Agent 来说，更现实的做法是：每个工具调用是一个可检查点，长任务在每个检查点续租；一旦进程崩溃，从最后一个检查点恢复，而不是从头重跑。

一句话记住

事务负责「谁拿到」，租约负责「谁还活着」，epoch 负责「谁有资格写」。三件事分开，崩溃恢复才不会变成数据污染。

08排序、公平与背压：队列的三种社会契约

调度不是「谁先来谁先跑」这么简单。它同时在分配三种稀缺资源：用户的等待时间、系统的并发容量、以及不同租户之间的公平性。下面五件事，决定了队列在负载下是「慢」还是「坏」。

8.1 会话内 FIFO，跨会话再谈优先级

同一个会话里，顺序是用户心智模型的一部分：他按 A、B、C 输入，就期待 A、B、C 执行。跨会话时，严格 FIFO 会让一个批量任务挡住所有交互请求，所以需要优先级或公平调度。一个简单的分层是：会话内按 position, seq；跨会话按 priority 与租户配额。

8.2 公平：不要让一个大客户吃掉所有 worker

常见调度策略
策略适合代价 / 风险
严格 FIFO单租户、顺序敏感队头阻塞；大任务挡住小请求
严格优先级交互流量必须优先低优先级饥饿；优先级被滥用
按租户轮转多租户 SaaS实现复杂；顺序不再全局
加权公平不同套餐 / 不同配额需要持续测量与调参
预留容量交互与批处理混跑容量利用率下降

Temporal 的 Task Queue 用分区提升吞吐，代价是多分区下不保证严格顺序；这是典型的「用顺序换并发」。[9] 产品侧也可以用同样的思路：交互队列单独一组 worker，批处理另一组；两组共享总容量，但交互组有最低保留。

8.3 背压：有界队列，早拒绝

没有上限的队列不是队列，是内存泄漏。准入层至少要设四道闸：每 agent 最大深度（防止一个会话刷爆）、每租户最大深度（防止一个客户占满）、全局最大深度（保护数据库）、预算上限（防止一个任务烧掉一个月成本）。

拒绝要同步、要可解释、要给下一步：429 Too Many Requests + Retry-After + 「当前队列 120 条，预计 8 分钟后可提交」。Devin 的做法是把上限做成产品可见的配置：每次运行最多处理多少条、每小时最多触发多少次、单个会话最多消耗多少 ACU。[8] 这比在后台静默丢弃诚实得多。

8.4 长任务：心跳、检查点、拆步

Agent 任务经常跨小时。租约不能无限长，所以要把长任务拆成可检查点的步骤：每次模型调用、每次工具调用、每次压缩之后都可以续租；进程崩溃后从最后一个检查点恢复。Anthropic 的长任务 harness 用 claude-progress.txt、功能清单和 git 历史把「跨上下文窗口的进度」外化，本质上也是把一个大任务拆成可恢复的小步。[13]

8.5 并发：一个 agent 串行，多个 agent 并行

Cursor 的 Cloud Agents API 明确规定：每个 agent 同时只能有一个活跃 run；在 run 处于 CREATING、RUNNING 或 WAITING_FOR_BACKGROUND_WORK 时再发普通 follow-up 会返回 409 agent_busy，除非用 delivery: "steer"。[3] 这个约束不是性能限制，而是产品选择：同一个工作区里并发改文件，合并冲突和上下文交错会让人无法理解。要并行，就开多个 agent、多个 worktree、多个会话。

09两条旁路：Steering 与审批

队列再完整，也不能让所有事情都排队。转向要绕过队列，审批要绕过队列，取消也要绕过队列。它们是队列的旁路，不是队列的普通元素。

9.1 Steering：在安全边界插入，不在工具中间打断

Steering 的接口要回答三件事：送到哪、什么时候生效、没送到怎么办。Cursor 的 Cloud Agents API 把结果分成 steered 与 queued：有活跃 run 时进入当前 run，在下一次安全步骤送达；没有活跃 run 时转为下一次 follow-up。[3] 这比笼统返回 202 Accepted 有用得多，因为客户端可以据此更新 UI。

Steering 的接口语义
字段 / 状态含义客户端该做什么
delivery: "steer"请求进入当前 run，不新建任务显示「将在下一步生效」；不要重复提交
delivery: "steered"当前 run 已接受，返回 runId把消息挂到该 run 的时间线
delivery: "queued"没有活跃 run，转为下一次 follow-up显示「已排队，等下一轮」；不要显示「已插入」
client_key客户端幂等键重试时复用；服务端去重
运行结束前未消费信号没有赶上当前 run按产品策略降级为 follow-up，或明确告知未送达

实现上，Agent 循环在每个安全边界检查一次信号表：模型调用前、工具返回后、压缩之后。不要在处理工具调用的中途强行改上下文，否则工具参数和模型意图会错位。

            raise Cancelled("user")

        for signal in await queue.drain_signals(task):
            messages.append({"role": "user", "content": signal.body})

        action = await model(messages)
        if not action.tool_call:
            return action.text

        result = await tools.run(
            action.tool_call,
            idempotency_key=f"{task.id}:{step}",
        )
        messages.append(result)

    raise MaxSteps("step budget exhausted")

两个细节：工具调用要带幂等键，因为重试可能发生在工具已经成功、但结果还没写回的窗口；信号消费要在一个短事务里标记 consumed_at，否则重试会重复注入同一条 steer。

9.2 审批：阻塞状态，不是普通任务

审批和任务的关键区别是：审批的推进者是人，不是 worker。它应该进入 waiting 状态，带 approval_id、expires_at、风险等级和可选的「本次 / 本任务 / 本会话」授权范围。超时默认拒绝或取消，不能自动放行；审批通过后，任务从 waiting 回到 running，而不是新建一条任务。

审批卡的最小字段
字段作用
动作要执行什么命令 / 改哪些文件 / 推到哪个分支
原因Agent 为什么需要这一步；不做会怎样
风险不可逆、影响范围、涉及的数据
范围仅本次 / 本任务 / 本会话；默认最小
过期什么时候失效；过期后任务怎么处理
审计谁批的、什么时候、依据是什么

书本第 6 章的三档分流可以作为审批之外的默认策略：INTERRUPT 走取消，IMMEDIATE 走立即回应（不打断后台任务），DEFERRED 走排队。[14] 审批是第四档，因为它的推进条件不是「什么时候有空」，而是「人什么时候做决定」。

旁路原则

取消、转向、审批都不应该排在「待办」后面。它们要能打断等待，但不能打断正在写文件的工具调用；它们要能改变任务的下一步，但不能改变已经发生的事实。

10.2 worker 循环

Python · worker领取、心跳、完成 / 失败
import asyncio

class Cancelled(Exception):
    pass

class LeaseLost(Exception):
    pass

async def worker(pool, agent, worker_id: str):
    while not pool.stopping:
        task = await pool.claim(worker_id)
        if task is None:
            await asyncio.sleep(0.2)
            continue

        heartbeat = asyncio.create_task(pool.heartbeat(task))
        try:
            result = await agent.run(task, pool)
            await pool.complete(task, result)
        except Cancelled:
            await pool.cancel(task, reason="user")
        except LeaseLost:
            # 另一个 worker 已经接手；丢弃结果，不要重写
            pool.log.warning("lease lost: %s", task.id)
        except Exception as exc:
            await pool.fail(task, exc)
        finally:
            heartbeat.cancel()

这段代码的顺序很重要：先领取，后启动心跳；先完成，后取消心跳；任何写回都带 epoch。如果把心跳放在 agent.run 里面，工具调用卡住时租约就会过期；如果把完成放在 finally 里，失败也可能被写成成功。

10.3 Agent 循环里的三个检查点

async def run_agent(task, queue, model, tools):
    for step in range(task.max_steps):
        if await queue.cancel_requested(task):
            raise Cancelled("user")

        for signal in await queue.drain_signals(task):
            messages.append({"role": "user", "content": signal.body})

        action = await model(messages)
        if not action.tool_call:
            return action.text

        result = await tools.run(
            action.tool_call,
            idempotency_key=f"{task.id}:{step}",
        )
        messages.append(result)

    raise MaxSteps("step budget exhausted")

三个检查点分别对应三种失败：取消（用户改了主意）、转向（用户补了约束）、重试（工具已经成功但结果没写回）。工具幂等键用 task.id + step，同一个步骤重试不会产生第二次副作用；如果工具本身不支持幂等，就在工具外面包一层「先查后写」的补偿逻辑。

实现边界

这段骨架假设「一个 agent 同时一个 run」。如果你要做多 agent 并行，不要去掉这个约束；复制 agent，给每个 agent 独立的队列与工作区。共享同一个 agent id 的并发 run 会让 one_active 索引直接拒绝，这是保护，不是障碍。

12设计原则与取舍

最后压缩成十二条。它们不是互斥的教条，而是一组检查表：做队列评审时，逐条问「我们选了什么，代价是什么」。

  1. 先定义生效点，再写队列。没有 drain_policy 的队列，迟早会在「下一轮」和「任务结束」之间漂移。
  2. 一条队列只承载一种承诺。steer、follow-up、task、approval 分开；混在一起，失败语义一定互相污染。
  3. 队列是持久状态，UI 只是投影。切会话、刷新、换设备都不能重建队列；队列的 source of truth 在服务端或本地库。
  4. 每个 agent 一个活跃 run，并行靠多 agent。同一个工作区并发改文件，冲突成本高于并行收益。
  5. 至少一次执行，副作用必须幂等。不要承诺 exactly-once；承诺「重复可检测、重复无副作用」。
  6. 取消是一等状态，不是删除。保留审计、清理子进程、记录已发生的副作用。
  7. Steer 只落在安全边界。工具调用中间不插入新指令；否则参数和意图会错位。
  8. 公平性是产品功能。多租户下，严格 FIFO 或严格优先级都会制造饥饿；预留容量或轮转是必须的。
  9. 有界队列，早拒绝。队列满时同步拒绝、给原因和重试时间；静默丢弃比报错更伤信任。
  10. 看年龄，不看深度。深度是瞬时量；最老任务的等待时间才是「堵没堵」的证据。
  11. 租约必须带 fencing。没有 epoch 的完成写回，迟早会覆盖别人的结果。
  12. 跨端共享一套语义。CLI、App、Cloud 可以有不同交互，但不能有不同 delivery 含义。
