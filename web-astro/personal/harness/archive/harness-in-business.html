01

先看结论

六个判断，后面每个都有案例和来源支撑。

落地的不是“通用助手”，是窄而深的岗位流程

淘宝的“AI 店长 + 6 个 AI 员工”、京东的“客服 / 导购 / 跟单 / 分析”、美团的“意图匹配 + 可拖拽 TaskFlow”、沃尔玛的排班与翻译工具，都是把一件事拆到可验收，而不是给员工一个万能聊天框。

见案例 01、02、03、08

harness 的重心在“业务状态”，不在提示词

能办理退款、改价、建工单、发素材，才算工具；验收看订单、工单、数据库状态，而不是看模型说自己做完了。τ-bench 直接把“对话结束时的数据库状态”作为判分依据。

见案例 06、07 与论文 [11]

“知识运营”正在变成正式岗位

Fin 设 knowledge manager 与 conversation designer；Anthropic 客服每周复盘未回答问题、每季度做内容冲刺；京东让商家把任意格式文件拖进知识中心自动结构化。更关键的是“谁来维护”：美团把外呼、地图、API 组件化，让业务运营拖拽编排 TaskFlow，模型只做意图匹配与调度。

见案例 02、03、06、07

人审不是失败，是设计变量

京东京小智把“转人工率下降 18%”当成绩，而不是追求 0；抖音生活服务把触发条件写成“回复不精准 + 用户有情绪”；浦发银行更狠，把审核从对话级上移到发布级——1026 个智能体只有 24 个通过合规闸门进入生产。

见案例 02、11、12

Klarna 回聘人工、麦当劳终止得来速 AI、Air Canada 为聊天机器人错误担责：分别是质量维度缺验证、复杂环境缺纠正、对外承诺缺约束与责任边界。

02

什么算 harness

沿用《深入理解 AI Agent》的边界：harness 是 Agent 边界内、模型之外的运行与治理层。它不是“模型之外的一切”，环境本身（订单库、设计文件、网页）不算。

Agent = Model + Harness ； Harness = 上下文 + 工具 + 约束 + 验证 + 纠正
Layer 1

上下文

把业务知识、用户状态、历史轨迹组装成模型此刻能用的信息。

案例里：商品知识中心、CLAUDE.md、未回答问题清单
Layer 2

工具

不只查询，还要能改变业务状态：退款、建单、改价、发布素材。

案例里：Meta Ads MCP、售后系统、Figma 插件、排班系统
Layer 3

约束

权限、金额、角色、合规、品牌规范，以及“哪些动作必须人批”。

案例里：店铺权限绑定、金融合规 guardrails、字符上限
Layer 4

验证

检查“做对没有”：对账业务状态、A/B、抽检、离线评测集。

案例里：数据库终态比对、点击率 A/B、CX Score
Layer 5

纠正

错了怎么补救：重试、回滚、转人工、下线、补知识。

案例里：checkpoint 回滚、转人工阈值、回聘人工
收录标准一：有公司名能指到具体企业，不接受“某头部品牌”。
收录标准二：有自用证据公司自己、客户案例页、官方发布或可靠媒体；只有产品发布不算。
收录标准三：能拆出 harness至少能说清上下文、工具、约束、验证、纠正中的三项。

01

淘宝：把“店长的一天”拆成 1+6 个 agent

电商运营 / 素材设计 · 2025 双 11 · 500 万商家
运营设计

2025 年双 11，淘宝把商家后台“生意管家”升级为“1 个 AI 店长 + 6 个 AI 员工”的组合。AI 店长「大促小助理」按大促阶段读店铺经营数据，给实时解读、流失诊断和机会点；6 个员工覆盖数据分析、订单等场景；AIGC 负责商品图与视频；客服由“店小蜜”承接。官方口径：AI 店长生成 500 万条经营策略，平均帮商家省 30% 工作量，效率提升 1.5 倍；AI 数据分析师覆盖 90% 中小商家的核心分析场景。2025 年 9 月，店小蜜 5.0 以“Agent 原生”形态发布，测试阶段转人工率降低 20% 以上、店铺成交转化率提升 35% 以上。

上下文
店铺经营数据、订单、商品信息、平台大促规则；按阶段切换“看什么”。
工具
数据分析、策略生成、素材生成（万相营造）、售后系统自动处理。
约束
平台规则与店铺权限；AI 给建议，商家拍板，不替商家做最终经营决定。
验证
AIGC 素材做 A/B，商品点击率 +10%；经营指标前后对比。
纠正
商家驳回策略、改素材；复杂问题转人工客服。
500 万
商家使用；效率 1.5 倍；AIGC 累计生成 1.5 亿个图片与视频素材；店小蜜在双 11 服务 3 亿人次，其中 1 亿人次全自动承接，约一半售后问题自动解决。
可复用点：别做一个“万能店长”，把店长的一天拆成班次——谁看数据、谁出素材、谁接客服，最后商家只做拍板。A/B 是这套系统里最关键的验证件。
来源 [2] 官方发布经媒体转述、[21] 亿邦动力
02

京东：四个“数字员工”与一个知识中心

客服 / 导购 / 跟单 · 2025-04 · 80 万商家
客服运营

京小智 5.0 一次推出四个 agent：客服、导购、跟单、VOC 分析，基于言犀与 DeepSeek 双模型。最值得看的是两个设计：一是知识中心，商家把任意格式文件拖进去，模型自动解析成结构化知识，不需要手工配问答；二是导购做成了多 agent 流水线——需求探明 → 推荐理由 → 商品推荐 → 商品答疑，彼此交接。跟单覆盖售前、售中、售后 30 多个服务节点。

上下文
京东域内知识、泛零售行业知识、品牌自有知识；京造场景下 2.5 万 SKU、900 余品类。
工具
业务查询、操作办理、主动跟单、VOC 分析模板；工具直接接平台业务系统。
约束
商家知识边界与平台规则；转人工规则由商家配置。
验证
内测对比转人工率、满意度、咨询转化率，而不是只看回答“像不像人”。
纠正
转人工兜底；知识缺口的补录；按品类调整搭售策略。
-18% / +21%
内测期间转人工率整体下降 18%，满意度反而提升 21%，咨询转化率提升 2%；京造用其做低客单与高客单的差异化搭售，客服渠道转化率提升 300% 以上。同属京东体系的海信，把国补咨询做成“区域划分 → 资格识别 → 申领 → 下单”一站式服务，打通营销、物流、价保、订单、发票；2024 年，回复过的会话 7 天下单转化率比未回复高六成，应答准确率超过 90%。
可复用点：知识不是写 prompt，是把文件变成结构化知识；复杂任务不是让一个 agent 全做，而是让多个窄 agent 接力，每一棒都有明确输入输出。

03

美团：把 harness 的可编辑层交给运营

客服 / 商家助手 · 2021-09 · 在线咨询占比 85%+
客服运营

美团智能客服服务 6.3 亿年交易用户、770 万生活服务商家，在线咨询占比 85% 以上。技术博客里最值得抄的不是模型，而是分工：意图体系、Task 流程、订单查询接口“主要由各业务的运营团队来维护”；对话系统只做两件事——把用户输入匹配到标准问，以及完成多轮交互里的调度。为此他们把外呼、地图、API 组件化，提供可视化 TaskFlow 编辑器，业务运营拖拽就能改流程；底层用 Bayes Network 把规则与概率结合起来。意图置信度不高时，系统不硬答，而是给出业务列表让用户自己澄清。

上下文
意图体系、标准问、各业务 Task 流程、订单查询接口，均由业务运营维护。
工具
外呼、地图、API 全部组件化，拖拽进流程；座席侧有话术推荐与会话摘要。
约束
业务规则写进 Task 流程；低置信度不硬答，转为澄清。
验证
不满意度与转人工率衡量机器人；ATT / ACW 衡量人工辅助。
纠正
用户澄清、转人工、运营直接改流程与话术。
<80% → 90%
意图识别准确率的提升；更重要的是流程维护权在运营手里，改一个业务规则不需要发版等工程排期。
可复用点：别把流程写死在代码里。把工具组件化、流程可视化，让最懂业务的人维护 harness；模型只负责匹配与调度。
来源 [22] · 美团技术团队（官方）

Anthropic 增长营销：一个人的投放团队

投放素材 / 广告文案 · 2025-06 · 团队规模 1 人
运营

Anthropic 的增长营销是一个非技术背景的“一人团队”。他们用 Claude Code 搭了三条流水线：读 Google Ads 的 CSV，找出表现差的广告，按 30 字符标题 / 90 字符描述的限制生成新变体，标题和描述各由一个子代理负责，几分钟产出数百条；写了一个 Figma 插件，识别画框、替换标题与描述，一批生成最多 100 个素材变体；用 Meta Ads 的 MCP server 在 Claude 里直接查投放与花费。还做了个粗糙的“实验记忆”，把历史假设和结果带回上下文。

上下文
历史广告与表现数据、平台字符限制、过往实验假设与结果。
工具
CSV 读取、两个子代理、Figma 插件、Meta Ads MCP server。
约束
Google Ads 的字符上限与素材规格；品牌口径。
验证
投放表现回流，低效广告进入下一轮迭代；实验记忆避免重复试错。
纠正
按数据淘汰变体、重写；人工决定最终投放组合。
2h → 15min
单条广告文案创作时间；素材产能约 10 倍；Figma 插件把“几小时复制粘贴”压到每批 0.5 秒。
可复用点：增长团队的 harness 核心是“数据回流”：投放表现进入下一轮上下文，实验记忆防止重复试错。模型换了，这套流水线仍然成立。

Anthropic 产品设计：从画图到直接改代码

界面走查 / 原型 / 文案合规 · 2025-06 · 非工程背景设计师
设计产品

产品设计团队支持 Claude Code、Claude.ai 与 API。过去改字体、颜色、间距要写设计文档、和工程师来回几轮；现在设计师直接用 Claude Code 改前端，甚至做“通常不会让设计师碰”的大范围状态管理改动。他们把 mockup 截图贴进去，生成工程师能直接跑的原型；用 GitHub 集成把 issue 变成代码建议；用 agent 梳理错误态、逻辑流和系统状态，把边界情况提前到设计阶段发现。一次全站去掉“research preview”字样的文案修改，设计与法务实时协同，两次 30 分钟会议完成，而过去要一周来回。

上下文
设计稿截图、现有代码库、组件与状态、法务文案要求。
工具
代码编辑与运行、GitHub Actions / issue、原型运行环境。
约束
工程规范与代码评审；法务合规；发布权限仍在工程侧。
验证
原型能跑、工程师 review、边界状态可复现；不再靠静态图“讲解”。
纠正
PR 迭代；checkpoint 回滚；review 打回。

跨案例的五个规律

把十三个案例的五层表横过来看，真正拉开差距的不是模型选型，而是五件事。

Pattern 01 / 上下文

从“写提示词”到“养知识资产”

Fin 设了 knowledge manager，把帮助中心经理转成“为 agent 优化内容”的角色；Anthropic 客服每周复盘未回答问题、每季度做内容冲刺；京小智让商家把任意格式文件拖进知识中心，自动结构化成知识；美团更进一步，把意图体系、Task 流程、订单接口的维护权交给业务运营。

更进一步的做法规避了“文档 RAG”：沃尔玛为采购助手建语义层理解自有数据，Shopify 给每个主题一套 design contract、pattern 库与 eval 数据——领域约束被编译进系统，而不是塞进提示词。共同点：上下文有 owner、有节奏、有验收。

证据：[6] Anthropic × Fin；[22] 美团；[41] Walmart Wally；[39] Shopify
Pattern 02 / 工具

从“能查询”到“能办理”

Klarna 的 agent 能处理退款退货；SoFi 的 agent 直连内部 API；Airtable 的 agent 在对话里带客户完成操作；沃尔玛的任务工具直接改排班；1688 把“核价”封成一个报价 skill，把一两天压到一小时。

“能办理”意味着工具必须接到有状态、有权限的业务系统。只读工具只能做问答，不能做运营。

证据：[4] Klarna；[8] SoFi；[7] Airtable；[28] 1688
Pattern 03 / 验证

从“像不像人”到“对不对账”

τ-bench 直接比对对话结束时的数据库状态；淘宝用 A/B 看点击率；沃尔玛用试点门店前后对比；美团图灵把评测拆成结果、过程、效率、风险四层，再用人人一致率与人机一致率校准评分标准。

验证对象是业务状态，不是语言质量。语言质量可以抽样，业务状态必须全量对账。Morgan Stanley 的做法更接近制度：每个用例部署前跑 eval，顾问按 accuracy / coherence 打分，Debrief 用多种会议类型的数据集测行动项抽取，还有每日回归题集。

证据：[11] τ-bench；[23] 美团图灵；[42] Morgan Stanley
Pattern 04 / 纠正

从“重试一次”到“回滚 + 人审”

Anthropic 的工程团队用 checkpoint 与频繁提交，失败就回滚；京小智把转人工率当核心指标；抖音生活服务把触发条件写成“回复不精准 + 用户有情绪”；Klarna 的回退最贵——用回聘人工补流程缺口。

纠正能力决定系统能不能“带着错误运行”。没有回滚和人审，agent 只能做低风险建议。

证据：[1] Claude Code；[3] 京小智；[26] 抖音生活服务；[5] Klarna
Pattern 05 / 组织

把“人审”从对话级上移到发布级

浦发银行把智能体生命周期拆成开发态、发布态、运行态：1026 个智能体只有 24 个通过合规校验进入生产；抖音用“有效干预率”同时评估模型与纠正的人；腾讯企点把知识隔离、内容安全审核、检索阈值做成产品能力。

当 agent 数量从几个涨到上千个，逐个对话盯人是不可能的。真正的闸门在发布：谁允许它上线、允许它碰哪些系统、出了事怎么下线。Notion 则把人工审核精确卡在两个“最难撤销”的时点：批准修改范围前、写入发布系统前。

证据：[24] 浦发；[25] 抖音电商；[40] Notion Academy；[17] Salesforce

学术证据：能演示，不等于能上岗

论文给的数字不好看，但正好解释了为什么企业案例都在做 harness，而不是等下一代模型。

WorkArena：GPT-4o，精简配置20.0%
ServiceNow 企业平台上的 33 个知识工作任务
WorkArena：同一模型，完整脚手架42.7%
只改 harness，不改模型，成功率翻倍
WorkArena：删掉 thinking（或动作历史）8.5%
同一模型，少两项上下文管理，掉到不足一成
τ-bench：零售场景 pass^8< 25%
同一任务连续 8 次都成功，考验稳定性而非单次运气
TheAgentCompany：自主完成任务30.3%
模拟软件公司，平均 27 步、单任务成本超过 4 美元

同一模型，换一套 harness，成功率可以从 8.5% 到 42.7%——相差 5 倍。

WorkArena 的消融是“harness 决定成败”最干净的一组数：同一个 GPT-4o，只改动作与观察空间、上下文历史管理，成功率从 20.0% 升到 42.7%；反过来删掉 thinking 或动作历史中的一项，掉到 8.5%。这不是模型能力变化，是脚手架变化。

τ-bench 的方法值得所有做业务 agent 的人抄：它不让模型“自评”，而是把对话结束时的数据库状态与目标状态比对，再用 pass^k 衡量多次运行的一致性。这正好对应 harness 的“验证”层：看业务状态，不看措辞。

生产界的现实更保守。MAP 访谈了 86 名来自已部署系统的从业者（另有 20 个深度案例），结果显示：68% 的 agent 在需要人介入前最多执行 10 步，70% 直接用现成模型而非微调，74% 主要靠人工评估。TheAgentCompany 里最强 agent 自主完成 30.3%，平均 27 步、单任务成本超过 4 美元。能自主跑完的长流程，仍然是少数。

这些数字解释了一个现象：企业案例里真正跑出结果的，都是把任务切窄、把工具接深、把验证做实的场景；反过来，凡是宣称“端到端替代岗位”的，大多在一年内回退。

来源：[31] WorkArena（2024）；[11] τ-bench（2024）；[12] TheAgentCompany（2024-12）；[32] MAP（2025/2026）；[23] 美团图灵（2026-08）。

从业者的一线经验

不是公司案例，但三条经验分别对应 harness 的验证、工具与约束层。

工程博客 · Three Dots Labs

先验证，再解释

给编程学习平台做 AI Mentor 时，他们让 agent 先跑测试、修用户代码，再给提示；修不动就明说“不知道”。同一任务并行跑多个 agent，成功即停；eval 单次上下文常超 10 万 token，所以只把便宜快的用例放进 CI。

[43]
工程博客 · Anthropic

工具是“契约”，不是函数

工具是确定性系统与非确定性 agent 之间的契约。写法是：原型 → 用 agent 生成几十条真实任务做 eval → 与 agent 一起迭代工具。上下文不是越多越好，token 越多召回越差（context rot）。

[44]
个人博客 · Simon Willison

安全边界放在工具出口

当 agent 同时具备私有数据、不可信内容、对外通信三个条件，攻击者可以稳定窃取数据——“lethal trifecta”。防线应放在工具权限与出口（谁能读、能发到哪），而不是在系统提示里写“不要听网页的话”。

给三类岗位的落地清单

不是“学提示词”，而是按 harness 的五层，检查自己手里的流程缺哪一层。

运营

OPS
  1. 选流程：高频、有明确状态、错了能回滚。客服退款、商品上架、活动素材、闲时直播都符合。
  2. 建台账：把商品知识、活动规则、话术、历史工单整理成可更新的知识源，指定 owner；能可视化编排的流程，维护权尽量留在运营。
  3. 定阈值：写清哪些问题必须转人工（金额、投诉、合规、情绪），把转人工率当设计指标，不是失败。
  4. 换指标：用解决率、转化率、复购、返工率验收，不要只看“回答得像不像人”。
  5. 留后手：每个自动化动作都要有撤销/回滚路径，先小流量灰度。

设计

DESIGN
  1. 喂规范：把设计系统、品牌语气、组件库、可访问性要求变成 agent 能读的上下文，而不是口头交代。
  2. 要原型：让 agent 产出可运行的原型，而不是更多静态图；评审时跑起来看，而不是看图说话。
  3. 设检查：把品牌合规、法务文案、响应式断点做成检查清单，发布前自动过一遍。
  4. 人审前移：设计师审“方向与边界”，工程审“实现与风险”，不要让 agent 直接面对发布按钮。
  5. 记返工：统计“设计→工程”的往返次数与返工原因，这是 harness 改进的依据。

产品

PRODUCT
  1. 先写规格：在写 PRD 前先写 harness 规格——上下文从哪来、工具能做什么、什么必须人批、怎么验收。
  2. 建评测集：50–100 条真实任务，包含边界与对抗样本；每次换模型、改提示、加工具都跑一遍。
  3. 分开评估：模型升级与 harness 升级分开上线、分开归因；评分标准先做二元化，再谈自动化。
  4. 设闸门：把“允许上线”和“允许调什么工具”分开管；agent 数量上来后，发布态审核比逐条对话人审更可行。
  5. 定责任：对外承诺、价格、合规口径必须有硬约束与人工兜底；agent 说错，公司担责。

方法与局限

这份简报是检索与整理，不是审计。读数字之前，先看它属于哪一类来源。

检索与筛选

  • 时间：2026-10-19；覆盖 2023–2026 的公开资料。
  • 渠道：公司官网与案例页、官方 PDF、新闻稿、arXiv、主流媒体；中文案例补充发布会报道与行业媒体；从业者经验取自工程博客与论坛（HN 等），只作方法旁证，不计入案例数。
  • 筛选：必须有公司名、有自用证据、能拆出至少三层 harness；只有“发布平台”没有自用证据的，不收录。
  • 排除：无法核验的匿名案例、纯厂商愿景稿、把“用了 ChatGPT”当“agent 落地”的案例。
  • 平台型产品（Salesforce Agentforce、美团 CatPaw）只作为“harness 产品化”的形态参考，不单独计入业务案例。[17][30]
  • 行业背景参照 McKinsey 2025 年的调研：agent 仍处早期，规模化收益尚未普遍兑现；本简报不引用其具体比例，只用于校准预期。[20]

口径与局限

  • 厂商案例：由服务商撰写、客户署名，数字未经独立审计，倾向展示最佳结果。
  • 企业自述：如 Anthropic 的 PDF，细节可信度高，但仍是自我选择后的样本。
  • 媒体转述：中文案例多来自发布会与厂商稿，数字需按“厂商口径”理解。
  • 不可横向相加：解决率、转人工率、NPS 的定义各公司不同；本简报只做机制对照，不做排名。
  • containment ≠ resolution：Ada 的旧版产品做到 70% containment，实际解决率只有 30%；两个指标混用会把“没转人工”当成“问题解决”。跨厂商比较前先对齐定义。[37]
  • 幸存者偏差：失败案例的公开信息远少于成功案例，本文只收录了有明确报道的四个。
