01 / PRIMER一分钟的 harness 入门

Harness 的本义是马具：马提供动力，挽具决定动力往哪使、能不能被控制。软件工程早年借走这个词造了 test harness（测试脚手架）；AI 时代它指包裹在模型外面、把"预测能力"转化为"工作成果"的整套运行框架。一个编程智能体的核心循环长这样：

while True:
    context = build_context(system_prompt, memory, history, tools)  # ① 组装上下文
    response = model(context)            # ② 模型决定下一步
    action = parse(response)              # ③ 解析：文字回复，还是工具调用？
    if action.is_tool_call:
        result = sandbox.run(action, permissions)  # ④ 权限+沙箱执行
        history.append(result)                 # ⑤ 结果喂回，继续循环
    elif action.says_done and budget_ok:
        break

这份报告关心的问题只有一个：这个循环外面的每一行代码，应该怎么写？Anthropic 的五份报告，恰好是这个问题在不同阶段的答案。

2.1《Building Effective Agents》：给整个领域定坐标系

报告 012024-12-19anthropic.com/research

Building Effective Agents ↗

定位：领域原则宣言。它定义了后来所有报告共用的语言。

这份报告最持久的贡献是一个区分：workflow 是"LLM 和工具走预定义代码路径"，agent 是"LLM 动态主导自己的流程和工具使用"。后者的一句话定义后来被引用无数次——agent 就是在循环中根据环境反馈使用工具的 LLM[1]。对照 01 节的示意图你会发现：这个循环本身，就是 harness。

报告给出了从简到繁的五种 workflow 模式（提示链、路由、并行化、编排者-工作者、评估者-优化者），但真正值得划线的是它对复杂度的态度：

  • 能用单次 LLM 调用加检索解决的，就不要上 agent——agentic 系统用延迟和成本换表现，错误会累积；
  • 三大原则：保持简洁、优先透明、精心打造 ACI（agent-computer interface）；
  • 一个常被忽视的自白：作者在 SWE-bench 项目上，花在优化工具上的时间超过了整体提示词。

一句话 takeaway：这份报告把"工具接口设计"提到了与提示词工程同级的地位——为后面四份报告里 harness 工程的每一项技术埋下了伏笔。

2.2《Writing Effective Tools for Agents》：工具是给不确定的调用者写的契约

报告 022025-09-11anthropic.com/engineering

Writing Effective Tools for Agents — with Agents ↗

定位：ACI 的方法论落地。回答"为模型设计接口"到底意味着什么。

报告开头给工具下了一个精确定义：工具是确定性系统与非确定性 agent 之间的契约[2]。人类开发者面对同一个 API 只会以一种方式调用；agent 面对同一个任务却可能调工具、凭通用知识硬答、反问澄清，甚至幻觉出一个调用。所以工具文档不能再按"给开发者写 API 文档"的标准写。

  • 方法论是评估驱动的闭环：快速原型 → 生成真实评估任务 → 程序化跑评估 → 用 Claude Code 分析执行轨迹并自动重构工具 → 循环。这份报告的建议本身大多来自这个过程。
  • 命名空间：像 asana_projects_search 这样的前缀帮 agent 选对工具；文档坦承前缀还是后缀更好"对评估结果有非平凡影响"，要靠自己的评测决定。
  • 返回有意义的上下文：避免 uuid、mime_type 这类技术标识符，优先自然语言名称；提供 ResponseFormat 枚举让 agent 自选详略。
  • token 效率有实锤：Slack 工具的返回从 detailed（206 tokens）改出 concise 档（72 tokens），用量降到约三分之一；Claude Code 默认对工具结果做 25,000 token 截断。
  • 工具描述也要做提示词工程：他们发现 Claude 搜索时会在 query 后多余地追加年份"2025"导致结果偏移，改工具描述就纠正了；对工具描述的精细调整帮 Sonnet 3.5 在 SWE-bench Verified 达到当时 SOTA，且优化后的工具在 held-out 测试上超过了“专家”手写版本。

一句话 takeaway：工具不是 API 的包装，而是被评测驱动的独立工程对象——"改工具"和"改提示词"一样，是提升 agent 成绩的一等公民手段。

2.3《Effective Context Engineering for AI Agents》：上下文是会腐烂的稀缺资源

报告 032025-09-29anthropic.com/engineering

Effective Context Engineering for AI Agents ↗

定位：harness 核心职责之一——上下文管理——的专论。

这份报告把上下文定义为有限资源，并给出"context rot"（上下文腐烂）概念：token 越多，模型准确回忆和利用信息的能力越差[3]。机理在注意力预算——transformer 中每个 token 与其他 token 形成 n² 个成对关系，而训练数据以短序列为主，长上下文能力天然被稀释。指导原则因此是：找到最小的高信号 token 集合。

对长时程任务，报告开出三副药，并明确给出选择标准：

技术怎么做适用场景
Compaction 压缩接近窗口上限时把对话总结后重启新窗口：保留架构决策、未解决 bug、实现细节，丢弃冗余工具输出，续跑时附带最近访问的 5 个文件需要大量来回对话的任务
结构化笔记定期把状态写到上下文窗口之外（to-do 列表、NOTES.md），需要时取回有清晰里程碑的迭代开发
Sub-agent 子代理子代理用干净窗口执行聚焦任务，可消耗数万 token，只把约 1,000–2,000 token 的浓缩摘要交回主 agent需要并行探索的复杂研究分析

报告里最有传播力的案例是 Claude 玩《宝可梦》：不给任何记忆结构提示，agent 自己发展出精确计数（"过去 1,234 步在 1 号路训练，皮卡丘已从目标 10 级升到 8 级"）、绘制已探索地图、记录战斗策略，并在上下文重置后继续训练数小时。这证明了结构化笔记是模型可以自发使用的机制——前提是 harness 给了它"窗口外的存储"。

一句话 takeaway：上下文工程的本质是策展而非堆砌——"上下文腐烂"意味着 harness 必须主动决定什么不进窗口，这后来成为所有长任务 harness 的第一设计约束。

2.4《Effective Harnesses for Long-Running Agents》：第一份以 harness 命名的报告

报告 042025-11-26anthropic.com/engineering

Effective Harnesses for Long-Running Agents ↗

定位："harness" 一词首次成为标题本身。一份诚实的失败报告。

实验设置很狠：让 Opus 4.5 在 Claude Agent SDK 上自主循环运行，只给一句"做一个 claude.ai 的克隆"[4]。结论是——模型能力完全够，但失败方式极有规律，且全部出在 harness 层：

  • 失败模式一：一次性硬做——agent 试图一口气实现整个应用，中途耗尽上下文，下个会话面对无文档的半成品；
  • 失败模式二：过早宣告完成——后接手的会话看到已有进展，就倾向于宣布"项目已完成"。

对应的 harness 解法构成了一份可以直接抄的施工图：

失败模式（模型视角）解法（harness 视角）
一次性硬做、中途断档每个会话只做一个功能；结束时小步 git 提交 + 维护进度文件，代码库始终处于"可合并"状态
过早宣告完成把用户需求展开为结构化 JSON 功能清单（这个克隆被拆成 200+ 项功能，初始全部 passes: false）逐项验收；特意用 JSON 而非 Markdown，因为模型更不容易篡改 JSON，并用强措辞禁止改动测试项本身
未验证就标"完成"强制自我验证闭环：用浏览器自动化像真实用户一样操作，验证通过才允许把功能标为 passing（也如实记录了局限：模型看不到浏览器原生 alert 弹窗）
新会话不知如何接手init.sh 一键启动脚本 + 规定"会话启动仪式"：确认目录 → 读 git log → 读进度文件 → 读功能清单 → 冒烟测试确认环境没坏

一个耐人寻味的细节：文末脚注写明，"初始化 agent"和"编码 agent"只是初始提示词不同——系统提示、工具和 harness 完全一致。分歧巨大的行为差异完全由 harness 内的提示词编排产生。

一句话 takeaway：四种失败没有一种是"模型不够聪明"，解法也没有一种是"等下一代模型"——这是 Anthropic 第一次系统性论证：长任务的瓶颈在 harness。

2.5《Scaling Managed Agents》：harness 成为基础设施

报告 052026-04-08anthropic.com/engineering

Scaling Managed Agents: Decoupling the Brain from the Hands ↗

定位：把 harness 从"一段代码"提升为"一种可虚拟化的基础设施角色"。

这份报告有一个清醒到近乎尖锐的出发点：harness 里写满了关于"模型做不到什么"的假设，而这些假设会随模型进步过时[5]。他们的真实案例：Sonnet 4.5 有"上下文焦虑"（临近窗口上限就提前收工），团队用 context reset 治好了它；换成 Opus 4.5 后这个行为消失了，reset 反而成了累赘。为一个模型缺陷设计的 harness 补丁，在下一代模型上变成了负担。

解法借用操作系统哲学——为"尚未被设想出的程序"而设计。Managed Agents 把 agent 系统拆成三个可独立替换的虚拟化组件：

  • Session：一切发生之事的只追加日志，存活于上下文窗口之外，大脑可以用 getEvents() 按位置切片回读——从上次停止处续读、回看前因、重读某动作前的上下文；
  • Harness：调用 Claude、把工具调用路由到基础设施的循环本身——它也是“牛”而非“宠物”，崩溃后新实例凭 wake(sessionId) 从日志断点续跑，不留任何本地状态；
  • Sandbox：模型干活的执行环境，对 harness 而言只是一个统一接口 execute(name, input) → string，可以是容器、手机甚至游戏模拟器。

把大脑与双手解耦后，报告给出两组实打实的工程收益：

p50 TTFT −60%
推理与执行环境分离后，会话接受任务到产出首个响应 token 的中位等待时间下降约六成[5]
p95 TTFT −90%+
尾部延迟几乎消失——扩容只需启动更多无状态 harness 实例
结构性安全
token 被架构性地置于沙箱代码不可触及之处：git 用 access token 在初始化时接入，自定义工具走 MCP + OAuth vault，harness 全程接触不到凭据

报告对自身的定位也值得原文记录：Managed Agents 是 meta-harness——"对具体 harness 不持立场，只对接口有主见"。Claude Code 是优秀 harness，领域专用 harness 也能被容纳。

一句话 takeaway：这份报告宣告 harness 的成熟形态是"抽象稳定的接口 + 可自由替换的实现"——正如操作系统的 read() 不关心磁盘是 1970 年代的还是 SSD 的，大脑也不应该关心"手"长什么样。

3.1 OpenAI《Harness Engineering》：团队级的对照实验

业界回应 012026-02openai.com

Harness Engineering: Leveraging Codex in an Agent-First World ↗

定位：OpenAI 的正面回应。把 harness 工程写到"整个工程团队重构工作方式"的尺度。

OpenAI 用一个极端实验切入：五个月、从空 git 仓库开始，0 行手写代码——应用逻辑、测试、CI、文档、内部工具全部由 Codex 写成，共约 100 万行，人力成本约为手工的十分之一。起初 3 名、后来扩到 7 名工程师，驱动约 1,500 个 PR 合入，人均 3.5 PR/天，团队核心哲学被写成一句口号：Humans steer. Agents execute.[7]

与 Anthropic 报告逐条呼应的是这些发现：

  • 瓶颈不在模型在环境：早期进展慢于预期，"不是因为 Codex 不行，而是环境欠规格"。工程师的修复几乎从来不是"再试试"，而是问：缺什么能力？怎么让它对 agent 可读、可执行？——这与报告 04 的结论完全同构。
  • 给地图，不给千页说明书：他们试过"一个大号 AGENTS.md"，失败方式很典型（挤占上下文、规则互相稀释、迅速腐烂、无法机械校验）。改为约 100 行的 AGENTS.md 只当“目录”，结构化的 docs/ 是事实源，配合机械校验的 CI 和定期"文档园艺" agent——这正是报告 03 "最小高信号 token 集合"的团队级实践。
  • 把应用变得对 agent 可读：应用可按 git worktree 逐改动启动；Chrome DevTools 协议接入 agent 运行时（DOM 快照、截图、导航）；每个 worktree 配一套临时可观测性栈，agent 能用 LogQL/PromQL 查日志指标——于是"确保服务启动在 800ms 内完成"这类提示词变得可执行。单次 Codex 任务连续跑 6 小时以上是常态。
  • 约束不变量，而不是微管实现：自研 linter 强制分层架构与依赖方向，且 lint 报错信息本身会"向 agent 上下文注入修复指引"。原文的总结句可以直接当 harness 的定义读：纪律不再体现在代码里，而体现在脚手架上。
  • 熵与垃圾回收：agent 会复制仓库里已有的一切模式——包括坏模式。团队曾把每周五花 20% 时间清理“AI slop”，后来改为把"黄金原则"编码进仓库、由后台 Codex 任务定期扫描并开重构 PR，"像垃圾回收一样持续小额偿还技术债"。

一句话 takeaway：Anthropic 的报告写的是"harness 应该怎么设计"，OpenAI 这篇写的是"一个团队把全身心押在 harness 上之后，工程组织变成了什么样"。两份材料互为微观与宏观。

3.2 Lilian Weng《Harness Engineering for Self-Improvement》：理论化与"自改进"视角

业界回应 022026-07-04lilianweng.github.io

Harness Engineering for Self-Improvement ↗

定位：把 harness 工程理论化的第一篇系统长文，并推到"自我改进"的尽头。

前 OpenAI 安全研究副总裁 Lilian Weng 给出目前最完整的学术化定义：harness 是围绕基础模型的系统，负责编排执行、决定模型如何规划、调用工具与行动、感知和管理上下文、存储产物并评估结果。相比早期"agent = LLM + 记忆 + 工具 + 规划"的框架论，harness 工程额外多了循环工程、评估、权限控制与持久状态管理——她直接将其类比为操作系统[8]。

报告最有价值的贡献是一条"优化对象的递进阶梯"：

她同时记录了关键的警示结果：STOP 递归自改进在 GPT-4 上越改越好，但在 GPT-3.5 和 Mixtral 上反而退化——递归结构本身不够，底座模型必须足够强。结论克制而清晰：近期的"自我改进"更可能发生在 harness 层而非权重层，而许多 harness 改进最终会像提示工程史那样被内化进模型——"智能仍是核心"。

一句话 takeaway：如果说 Anthropic 和 OpenAI 在写"harness 怎么做"，这篇在写"harness 会变成什么"——一个可以成为优化目标本身、乃至通向自我改进回路的研究对象。

3.3 学术界：把 harness 变成可测量的变量

  • SWE-agent（普林斯顿，NeurIPS 2024）[9]：ACI 概念的出处。证明仅靠为模型重新设计工具接口（受限文件查看器、精简搜索结果、带 lint 防护的编辑），同样的 GPT-4 Turbo 就创下当时 SWE-bench 最高纪录 12.47%。Anthropic 报告 01、02 的工具观直接承继于此。
  • Stop Comparing LLM Agents Without Disclosing the Harness（arXiv 2026）[10]：同一个 Claude Opus，标准化 scaffold 上 45.9%、Claude Code harness 上 55.4%（SWE-bench Pro）——近 10 个百分点，约等于模型迭代一代。学术层面的主张：评测 agent 不披露 harness，数字就没有意义。
  • An Empirical Study of Harness Design for Coding Agents（arXiv 2026-09）[11]：把 harness 拆成规划、动作空间、上下文管理三组件，4 模型 × 176 组配置做消融：上下文管理在窗口预算紧张时最值钱（"先规则删减、再 LLM 摘要"最优）；规划对弱模型是提分脚手架、对强模型只是省钱；bash 能力强的模型只给 bash 接口反而更便宜。元结论：harness 与模型能力耦合，换一代模型就该重调 harness。
  • The Last Harness You'll Ever Build（arXiv 2026）[12]：提出 "Agent = Model + Harness" 的形式化，把 harness 定义为"模型之外的所有代码、配置与执行逻辑"，并给出两层自动演化框架（Harness Evolution Loop + Meta-Evolution Loop）——与 Lilian Weng 的"元 harness"互相印证。目前是框架论文，实验待发布。
  • 综述类：已有《A Survey on Agent System and Harness Design》等综述出现[13]，说明这个方向在学术建制化。

3.4 评测侧：另一种 harness

以上都是"干活的 harness"；评测侧的 harness 同样在演化。EleutherAI 的 lm-evaluation-harness 仍是事实标准（200+ 任务，Hugging Face 排行榜与 Mozilla 审计均采用）[14][15]；而它存在理由的最好注脚来自 ICLR 2024 的研究（Sclar et al.）——同一任务仅改动提示词格式（分隔符、空格、大小写等与语义无关的细节），LLaMA-2-13B 的成绩最多波动 76 个准确率点[16]。社区侧，Terminal-Bench 曾出现同一 Claude Opus 在统一口径约 42 分、而 Claude Code harness 加人工校验口径报出 95.5 分的著名对比[17]——两个数字口径不同本不该直接比，但"分数随 harness 天差地别"这件事本身，正是这个学科存在的理由。

04 / SYNTHESIS交叉验证：五条跨机构的共识

把 Anthropic 五份报告与 OpenAI、Lilian Weng、学术界的材料并排放，会看到五条被独立反复验证的结论——这比任何单一报告都更值得信任：

  • 瓶颈在 harness，不在模型。Anthropic 的四种失败模式全是 harness 层的（报告 04）；OpenAI 的环境欠规格论（0 行手写代码实验）；学术界换 harness 差近 10 个点的量化。三条独立证据链指向同一处。
  • 上下文是稀缺资源，要策展不要堆砌。Anthropic 的 context rot 与"最小高信号集合"（报告 03）；OpenAI 的"给地图不给千页说明书"；SWE-agent 的受限文件查看器——三家从三个角度撞出同一条原则。
  • 接口为模型设计，而非为人。ACI（普林斯顿 → Anthropic 报告 01/02）；OpenAI 的"对 agent 可读性"、lint 报错注入修复指引。工具是被评测驱动的工程对象，不是 API 的包装。
  • 验证闭环是 harness 的宪法。Anthropic 强制浏览器自测 + JSON 功能清单（报告 04）；OpenAI 的 agent 互审与机械强制的 linter；Lilian Weng 把"评估在自改进循环之外"列为安全底线。
  • harness 正在成为自动化与优化的对象。Anthropic 的 meta-harness 定位（报告 05）；OpenAI 的 agent 写 linter、文档园艺 agent；Lilian Weng 的优化阶梯与 DGM 的 20%→50%——harness 工程本身正在被 agent 接管。

深挖：这些原则落到生产，真正卡住人的六个地方 →

分歧同样值得记录：Anthropic 强调 harness 假设会随模型过时、因此要"对实现不持立场"；而 OpenAI 的实践展示了极端重度投资单一 harness（Codex + 特定仓库结构）可以走多远。这不是矛盾，而是同一枚硬币的两面——产品级 harness 要抽象稳定，团队级 harness 可以深度耦合。

05 / PLAYBOOK从报告里提炼的施工清单

  • 外部记忆先行：进度文件 + 小步 git 提交（Anthropic 04）；仓库即事实源，AGENTS.md 只做目录（OpenAI）；文件系统即持久记忆（Lilian Weng）——三家给出的是同一个模式。
  • 机器可校验的完成标准：JSON 功能清单、逐项 passes 验收、禁止 agent 改验收标准本身；用 linter 和 CI 把"品味"变成机械规则。
  • 自我验证闭环：浏览器自动化、测试运行器、agent 互审——"agent 说我做完了"不算做完。
  • 工具单独做评测：命名空间、返回自然语言、控制 token（Anthropic 02）；工具描述的迭代用评估驱动，而不是凭直觉。
  • 上下文分阶段管理：先规则化删减、再 LLM 摘要（arXiv 消融）；长任务在压缩、笔记、子代理三者中按任务形态选择（Anthropic 03）。
  • 为换模型而设计：不要把对当前模型缺陷的补丁写死在架构里（Anthropic 05 的 context reset 教训）；升级模型后重新审视 harness 的每个组件。
  • 评测必须披露 harness：引用任何 agent 成绩时，先问用的什么 harness、什么提示词模板（arXiv 2605.23950）。

结语：一条从原则到基础设施的演进线

把六份 Anthropic 报告连起来看，是一条清晰的路线：2024 年底定义 agent 是什么（原则）→ 2025 年中证明多 agent 值不值（实践）→ 2025 年秋把上下文与工具变成方法论（学科）→ 2025 年末正面承认长任务瓶颈在 harness（命名）→ 2026 年春把 harness 升格为可虚拟化的基础设施（架构）。几乎同一时期（2026-02），OpenAI 用一个"零行手写代码"的团队实验从工业侧汇合，Lilian Weng 和 arXiv 论文们把它推到自我改进的理论边界。

Harness engineering 已经不再是一个比喻，而是一门有定义、有方法论、有量化证据、有未决问题的工程学科。它最好的一句话总结，恰好来自这份报告里两位主角不约而同的表达——Anthropic 说，harness 是为尚未设想出的模型而设计的接口；OpenAI 说，纪律体现在脚手架，而不是代码里。模型是发动机，harness 是整辆车；而现在，全行业都在学怎么造这辆车。

01 / SYSTEMS开源与学术系统

案例 01Aider · 开源 AI 结对编程aider.chat/docs/repomap ↗

Repo Map：用图排序决定"哪 1k token 代表整个仓库"

场景：大仓库装不进窗口，整文件投喂又太浪费——"sending whole files is a bulky way to send code context, wasting the precious context window"。模型不需要看每个函数的完整实现，"只需要理解到能调用的程度"。

aider 的做法是在入窗之前先做一次全库重要性排序：tree-sitter 把源码解析成 AST，抽取所有类/函数/变量的定义与引用；以源文件为节点、依赖关系为边建图，在图上跑排序算法；最终只有被其他代码引用最多的标识符连同签名行进入 map。

  • token 预算由 --map-tokens 控制，默认 1k，并按聊天状态动态调整——用户还没添加任何文件时显著扩大，让模型先看"全仓库目录"，需要细节再点名具体文件；
  • 冷门符号不进窗口，但模型可以借 map 主动请求查看具体文件。

机制：入窗前排序。每个 token 名额都给了被引用最多的符号，而非事后删减。

案例 02SWE-agent · 普林斯顿 NLPswe-agent.com/background/aci ↗

ACI：从工具接口源头限制"能吐出来多少"

场景：agent 用 cat 读文件、用搜索命令找代码，返回内容完全失控。

SWE-agent 不做事后修剪，而是把工具造得"吐不出那么多"——这正是正文 3.3 节 ACI 概念的出处：

  • 文件查看器每轮只显示 100 行，配合上下滚动与文件内搜索命令使用；
  • 全目录搜索只列出有匹配的文件名，不给匹配行上下文——"Showing the model more context about each match proved to be too confusing for the model"；
  • 编辑命令执行前先跑 linter，语法不正确就不让编辑生效；命令无输出时返回"命令成功但无输出"提示，防止模型误判。

机制：接口级预防。窗口污染在工具层被物理堵住——同一版 GPT-4 Turbo 靠它创下当时 SWE-bench 纪录 12.47%。

案例 03MemGPT / Letta · UC BerkeleyarXiv:2310.08560 ↗

把窗口当主存、数据库当磁盘——分页决策交给模型自己

场景：多会话聊天与超窗口文档分析，记忆需要跨会话存活。

MemGPT 是"模型自我管理窗口"的代表：主上下文 = 只读系统指令 + working context（固定大小的可写文本块，只能通过函数调用修改，存用户偏好与关键事实）+ FIFO 消息队列（队首保留被逐出消息的递归摘要）；外部上下文 = recall storage（全部消息）+ archival storage（PostgreSQL + pgvector）。

  • 模型通过 core memory 写入、archival 检索（自带分页——"implement pagination to prevent retrieval calls from overflowing the context window"）、conversation_search 回捞历史等函数自我分页；
  • 用量到约 70% 时系统插入"即将驱逐"警告消息，让模型主动把重要信息搬进 working context 或档案库；到 100% 驱逐约一半并更新递归摘要；
  • 效果：深度记忆检索 GPT-4 从 32.1% 提到 92.5%；嵌套 KV 检索超过 2 层后只有 MemGPT 能稳定完成。

机制：模型自我分页。harness 只提供记忆层级与压力警告，"搬什么"由模型自己决定。

案例 04OpenHands · 开源 agent 平台docs.openhands.dev/sdk/arch/condenser ↗

Condenser：把"什么不进窗口"抽象成可替换组件

场景：长编码会话，历史无限增长。

OpenHands 把窗口管理做成可插拔的 Condenser 管线，策略可自由组合：RecentEventsCondenser 只保留最近 N 个事件、更早的直接丢弃；LLMSummarizingCondenser（SDK 默认）把旧历史替换成 LLM 摘要，固定捕捉四类信息——用户目标、已完成/待办任务、代码状态、错误历史。触发既可以是被动（抛 ContextWindowExceededError），也可以是主动预防。

机制：策略管线化。官方博客报告每轮 API 成本最多降低约 2 倍，长会话响应时间保持稳定。

02 / PRODUCTS生产级产品

案例 05Manus · 通用 agent 产品manus.im/blog/context-engineering ↗

生产级五件套：进出管理 + 缓存感知 + 反直觉的"保留错误"

场景：平均约 50 次工具调用的长任务，输入输出比约 100:1——缓存命中决定成本结构。

Manus（不造模型，用第三方底座）的生产复盘是目前最完整的一手材料，五个机制环环相扣：

  • KV-cache 感知的 append-only："the KV-cache hit rate is the single most important metric for a production-stage AI agent"。系统提示开头绝不放时间戳——"Sure, it lets the model tell you the current time, but it also kills your cache hit rate"；JSON 序列化必须确定，key 顺序不稳定会"silently break the cache"；
  • Mask, don't remove：任务中途增删工具会让前部缓存全失效，改用解码时 logits 掩码控制工具可用性；工具命名用统一前缀（browser_、shell_）即可整组约束；
  • Recitation 复述：维护 todo.md 每步重写勾选，把全局计划"推入模型近期注意力范围"，对冲 lost-in-the-middle——这是"该反复进窗口的东西"的案例；
  • Keep the wrong stuff in：错误轨迹不清理——"Erasing failure removes evidence. And without evidence, the model can't adapt."（决定什么不进窗口 ≠ 越激进越好）；
  • 可逆压缩：网页只留 URL、文档只留沙箱路径即可丢弃正文——"you can't reliably predict which observation might become critical ten steps later"。

机制：全链路管理。压缩永远留还原路径，错误是高信号要留下。

案例 06Codex CLI · OpenAIOpenAI Community ↗

从"压缩"走向"换窗"：不做摘要，直接开新窗口

场景：单次任务连续数小时的编码会话。

临近窗口上限触发自动 compaction：一次专门的 LLM 调用把旧历史摘要成替代上下文。工程细节很真实——如果压缩请求本身就会撑爆窗口，就丢掉最老的一条历史再重试，循环到装得下为止；/compact 可随时手动触发。

更新的实验性方案走得更远：不做摘要，直接切换到全新窗口，旧窗口的完整历史通过"历史工具"按需回捞——与正文 2.5 节 Anthropic Managed Agents 的 Session + getEvents() 构想互为镜像。

机制：压缩 → 换窗。窗口从"必须保住的工作记忆"变成"可丢弃的缓存"，事实源移到窗口之外。

案例 07Gemini CLI · Googlegemini-cli issue #12068 ↗

一个阈值数字：早期 70% 触发、保尾 30%

场景：长终端会话的通用兜底。

早期版本源码里 COMPRESSION_TOKEN_THRESHOLD = 0.7：用量达到模型窗口的 70% 即自动压缩，保留最近 30% 的历史；阈值可配置。后续版本调整过默认值——截至 2026-10，主分支为 DEFAULT_COMPRESSION_TOKEN_THRESHOLD = 0.5（保尾仍是 30%），即压得更早，牺牲一点容量换稳定性。

机制：阈值触发 + 保尾压缩。早期默认值与 MemGPT 的 70% 警告线相互独立却数值趋同（见 04 节）；它后来被下调，也说明阈值是随版本调整的工程参数。

案例 08Cline · VS Code 编码 agentdocs.cline.bot/features/auto-compact ↗

一块"行业演化化石"：从规则截断到 LLM 摘要

场景：IDE 内长会话。

旧版 Cline 是纯粹的规则截断——超限后删掉一半到四分之三的对话历史，结果"丢失重要上下文"；随后演进为 Auto Compact：临近窗口上限时改用 LLM 摘要，保留技术决策与关键细节（官方文档未给出具体触发百分比，社区说法从约 80% 到约 95% 不等）。

机制：先规则删减、再 LLM 摘要。这条演化路径与正文 3.3 节 arXiv 消融研究（176 组配置）的结论互相印证。

案例 09Cognition / Devincognition.com/blog/dont-build-multi-agents ↗

单线程 + 任务间压缩：只留"关键细节、事件与决策"

场景：长程软件工程任务；对并行子代理的系统性批评。

他们的出发点："上下文工程是构建 agent 的工程师的头号工作"。单线程 agent 的优势是 "the context is continuous"——所有决策都在同一条历史里。任务之间用专门模型把历史压缩成 "key details, events, and decisions"，难到他们甚至为此微调了一个小模型专职做压缩。

  • 原则一："Share context, and share full agent traces, not just individual messages"——共享完整轨迹，不是单条消息；
  • 原则二："Actions carry implicit decisions, and conflicting decisions carry bad results"——Flappy Bird 例子：一个子代理把背景做成超级马里奥风格、另一个做的鸟手感不对，因为隐含决策冲突；
  • 同时点名认可 Claude Code 子代理的设计：子代理只做定义明确的问题、不并行写码，"调查不占用主代理的历史，轨迹可以跑得更长"。

机制：决策蒸馏。压缩的目标不是"变短"，而是保住决策链。

03 / FRONTIER研究前沿

案例 10ACE · 斯坦福等（ICLR 2026）arXiv:2510.04618 ↗

换一个层次：进窗口的不是轨迹，而是蒸馏出的 playbook

场景：重复型任务的经验积累，全程无标注监督、只靠自然执行反馈。

前面九个案例都在管理"原始历史"，ACE（Agentic Context Engineering）把进窗口的内容换成不断演进的 playbook：Generator 执行、Reflector 反思、Curator 整理。Curator 只做结构化增量 delta 更新而非整体重写，防两个病："context collapse"（迭代重写侵蚀细节）与 "brevity bias"（为简洁丢掉领域洞见）。

机制：知识蒸馏式入窗。agent 任务 +10.6%、金融 +8.6%；在 AppWorld 上用更小的开源模型追平榜首生产级 agent。

01 / LADDER逐篇拆解

案例 01斯坦福 · COLM 2024 · 2023-10arXiv:2310.02304 ↗

STOP（Self-Taught Optimizer）：让“改进器”程序改进它自己

场景：递归自改进（RSI）最早的可运行原型——不碰权重，只改脚手架。

Schmidhuber 的哥德机要求“任何改动必须先证明更优”，而证明本身不可行；STOP 把证明换成实证：给出一个种子改进器 improve()——它调用 LLM，读入任意程序与效用函数、输出改进版；然后把 improve() 自己作为输入喂给它。每一轮产出的新改进器都要在下游任务上真刀真枪跑分，胜者进入下一轮。

  • 论文记录到 LLM 自主提出了束搜索、遗传算法、模拟退火等经典优化策略来改写改进器；
  • GPT-4 底座上，自改进后的改进器显著优于种子；但换上更弱的底座，递归反而退化——Lilian Weng 的梳理把这条写成了明确结论：递归结构本身不够，底座必须足够强；
  • 作者专门评估了生成代码“绕过沙箱”的频率，并说明这还不是完整 RSI——模型权重自始至终没动。

机制：自我引用的实证改进循环。它定义了这条研究线的实验范式，也第一次把“底座强度是自改进前提”写成结论。

案例 02Hu, Lu & Clune · 2024-08arXiv:2408.08435 ↗

ADAS：让元 agent 用代码“发明”新 agent

场景：CoT、Self-Refine、Toolformer……这些手工设计的 agent 组件，历史上都在被学习方法取代——agent 设计本身能不能也交给搜索？

ADAS（Automated Design of Agentic Systems）的答案是“代码即搜索空间”：编程语言图灵完备，所以“用代码定义 agent”理论上能表达任何可能的智能体系统。Meta Agent Search 让一个元 agent 基于不断增长的发现档案（archive）迭代编写新 agent，每一代都实测、入库、作为下一代的素材。

  • 在编程、科学、数学三类任务上，被发现的 agent 大幅超过当时最强的手工设计 agent；
  • 这些发现能跨领域、跨底座模型迁移——说明搜到的是可复用的设计模式，不是对单一评测的过拟合。

机制：开放式代码搜索 + 经验档案。DGM 的 archive 结构直接承继于此。

案例 03Zhang et al. · 2024-10arXiv:2410.10762 ↗

AFlow：用 MCTS 在“工作流代码”的版本树上搜索

场景：工作流是人肉编排的（提示链、路由、并行……），换一个任务就要重新编排——能不能把它变成搜索问题？

AFlow 把 agentic 工作流表示成“LLM 调用节点 + 边”的代码图，用蒙特卡洛树搜索（MCTS）在“修改这段代码”的动作空间里探索，每一步都以执行反馈（分数、成本）为信号，配合树状经验积累。

  • 六个基准上平均超过当时最强基线 5.7%；
  • 成本侧的反转更惊人：搜出的工作流让更小的模型在特定任务上反超基于 GPT-4o 的工作流，推理成本只有其 4.55%。

机制：树搜索 + 执行反馈自动设计工作流。“优化者写代码、被优化者执行”范式的代表作。

案例 04Sakana AI + UBC + Vector · 2025-05arXiv:2505.22954 ↗

Darwin Gödel Machine：agent 改写自己的 harness 代码

场景：前面几篇优化的都是“agent 用的东西”；DGM 让编码 agent 直接优化 agent 本身——它的工具、pipeline，乃至“负责修改它自己”的那段代码。

每轮从agent 档案中采样一个个体，用基础模型生成一个“有趣的”变体（修改自身代码），再到 SWE-bench 等基准上实证验收；改进与失败全部入档，长成一棵不断分叉的树——允许从“次优祖先”重新出发，避免单线进化困在局部最优。

  • SWE-bench 20.0% → 50.0%，Polyglot 14.2% → 30.7%；
  • 自主发现的改进包括：更好的代码编辑工具、长上下文窗口管理（与正文 2.3 的“什么不进窗口”撞车）、类同行评议的互查机制；
  • 名字里的“哥德”是致敬而非复刻：Schmidhuber 的 Gödel machine 要求“先证明后改动”，DGM 用实证验证替代不可行的证明；
  • 全程沙箱 + 人工监督——这也是 Lilian Weng 把“评估与权限控制在自编辑循环之外”列为安全底线的实证依据。

机制：开放式进化 + 实证验收的自我改写 harness。正文 3.2 表中 20%→50% 的出处。

场景：阶梯第一级——优化对象不是代码，而是窗口内容本身（深挖案例 tab 的案例 10 是它的机制详解，这里看它在阶梯上的位置）。

02 / SYNTHESIS三条护栏与一个判断

  • 护栏一：评测必须在循环之外。STOP 专门评估“绕过沙箱”的频率；DGM 全程沙箱 + 人工监督；Lilian Weng 把“评估器与权限控制不进自编辑回路”列为第一安全底线——一旦 agent 能改自己的考卷，分数就不再有意义。
  • 护栏二：底座必须足够强。STOP 在 GPT-4 上越改越好、在弱底座上退化——递归结构不产生能力，只放大已有能力。
  • 护栏三：档案与日志要可审计。ADAS/DGM 的 archive 让每一次进化都可回溯；开放式探索（允许从次优祖先重启）同时是对抗局部最优与多样性坍缩的手段。
  • 一个判断：近期“自我改进”将主要经由 harness 层而非权重层发生——因为 harness 就是代码，而代码是自改进的通用介质；但正如 Weng 的结语，许多 harness 改进最终会像提示工程史那样被内化进模型——智能仍是核心。

DEEP DIVE / COMPANION上下文为什么会腐烂：从注意力数学到账单

这是正文 2.3 节备注「上下文腐烂」与「什么不进窗口」背后的证据链专题，按机理层 → 位置层 → 基准层 → 任务层 → 产品层五层拆解，每层给出可溯源的原始研究。检索于 2026-10-02，摘要与数字均已对照原文核对。

01 / EVIDENCE五层证据链

证据 01Anthropic · 2025-09-29anthropic.com/engineering ↗

注意力预算：n² 个成对关系，腐烂的数学起点

层级：机理。为什么“token 越多、回忆越差”是架构性质，不是工程瑕疵。

transformer 的自注意力让每个 token 都能“看见”其他所有 token——n 个 token 就是 n² 个成对关系。上下文变长，固定的参数容量被摊薄；softmax 归一化下，每份注意力的“质量”被稀释。再叠加训练分布以短序列为主，长程依赖天然是欠拟合区。Anthropic 把这称为注意力预算：每进一个 token 都在花预算，而预算随消耗贬值。

  • 位置编码插值等技术能延长窗口，但会损害模型对 token 位置的理解——窗口变长与位置感变弱在互相抵消；
  • context rot 是“性能梯度”而非“悬崖”：表现为长上下文下检索与长程推理的精度缓慢下降，而非突然失败——所以它容易被忽视；
  • 指导结论因此是策展而非堆砌：找“最小的高信号 token 集合”。

含义：“什么不进窗口”是第一设计约束，不是性能优化项。

证据 02Xiao et al. · ICLR 2024arXiv:2309.17453 ↗

Attention sinks：softmax 强制分配注意力，开头 token 成了“下水道”

层级：机理。位置偏置的微观机制。

StreamingLLM（MIT Han Lab / Meta）发现：不管语义多无关，前几个 token 总是吸走超量注意力——softmax 要求注意力总量分配出去，模型就把多余的“倒”进开头，它们成了 attention sink。实验上，滑窗注意力一旦把开头 token 的 KV 缓存扔掉，性能立刻崩塌；保留最初 4 个 token 的缓存则大幅恢复，模型得以在 400 万 token 以上的流上稳定生成。

含义：序列开头是结构性重要位置，与内容重要性无关——这也是位置层证据的机理注脚。

证据 03Liu et al. · 斯坦福 · TACLarXiv:2307.03172 ↗

Lost in the Middle：U 形曲线，中间的信息“看得见但不记住”

层级：位置。腐烂不止“变长”，还有“放哪儿”。

在多文档问答与键值检索两类任务上系统改变“相关信息”的位置：放开头或结尾成绩最好，放中间显著下滑——连专攻长上下文的模型也不例外；GPT-3.5-Turbo 在相关文档位于中间时成绩下跌超过 20%。部分设定下，模型“闭卷硬答”的成绩甚至好于“相关信息就摆在中间”。

  • 对 harness 的直接推论：上下文的顺序本身就是信号——关键约束放首尾，参考材料放中间并辅以结构化标记；
  • 这也是 Manus “recitation 复述”（把计划反复推回近期注意力）的理论依据（见深挖案例 tab 案例 05）。

含义：同一段内容，换个位置就是另一个成绩——策展要管内容，也要管次序。

证据 04Hsieh et al. · NVIDIA · COLM 2024arXiv:2404.06654 ↗

RULER：标称 128K ≠ 有效 128K

层级：基准。“有效上下文长度”成为与标称窗口并列的指标。

经典“大海捞针”（NIAH）太简单——单根针、线性检索，参测模型几乎满分。RULER 把针换成 13 类任务（多针变体、多跳追踪、聚合），让难度随长度一起增长：17 个标称 32K+ 的模型中，只有约一半在 32K 处还能保持满意成绩；标称 200K 的 Yi-34B 同样露出巨大水分。

含义：为换模型而设计（正文 05 节）时，先重测有效窗口——宣传口径不可信，RULER 式自测才可信。

证据 05Modarressi et al. · ICML 2025arXiv:2502.05167 ↗

NoLiMa：不许字面匹配，窗口立刻“缩水”

层级：基准。任务越“语义”、越接近真实工作，有效窗口越短。

NoLiMa 把“针”与问题之间的字面重叠也去掉，逼模型靠潜在关联检索：13 个标称 ≥128K 的模型中，11 个在 32K 处跌破短序列基线的一半；GPT-4o 从 99.3% 掉到 69.7%。结论直指注意力机制——没有字面锚点时，长上下文的关联检索是软肋，推理能力与思维链提示也救不回来。

含义：用 NIAH 满分安慰自己最危险——真实工作几乎没有“字面针”。

证据 06Chroma Research · 2025-07-14trychroma.com/research ↗

《Context Rot》实测：18 个模型，连“机械任务”也随长度腐烂

层级：任务。“怎么呈现”与“是否在场”同等重要。

Chroma 用 19 万次调用测了 18 个模型：即便任务复杂度不变——比如“复述重复单词”这种对人类毫无难度的机械任务——性能也随输入变长非均匀下降。干扰项一出现就掉分；更反直觉的是：把 haystack 洗牌打散结构，成绩反而稳定变好——“结构连贯性本身在伤害模型”。检索 100% 准确也挡不住腐烂：它发生在“读”这一步，不是“找”这一步。

  • 针-问题相似度越低，随长度衰减越快——语义关联是腐烂的加速器；
  • Claude 系模型倾向弃答（幻觉率最低），GPT 系模型幻觉率最高——同一根腐烂曲线，不同模型长出不同的失败模式；
  • LongMemEval 对话 QA 上，“聚焦窗口”全面好于“全量窗口”——正是正文 2.3 策展原则的任务级实证。

含义：context engineering 存在的实验依据——呈现方式本身就是变量。

证据 07Manus · 生产复盘manus.im/blog ↗

KV-cache 经济学：腐烂的另一半是账单

层级：产品。不进窗口的不只是注意力预算，还有成本。

Manus 的生产复盘给了“什么不进窗口”一个财务版本：典型 agent 任务约 50 次工具调用，输入输出比约 100:1，而缓存命中的输入价格约为未命中的十分之一——“KV-cache 命中率是生产阶段 agent 最重要的单一指标”。于是三条铁律：append-only（只追加不改写）、稳定前缀（系统提示开头不放时间戳）、确定性序列化（JSON key 顺序稳定，否则 “silently break the cache”）。

含义：机理层与产品层在“append-only”上会师——少改历史，既是注意力卫生，也是财务纪律。

02 / DIFFICULTIES逐一拆解

难点 01 / 06oracle 问题对照正文 2.4 节

验证器的缺口：判定"完成"比完成任务更难

症状："agent 说我做完了"之后，没有人能便宜地反驳它。

报告 04 用"JSON 功能清单 + 浏览器自动化"把"过早宣告完成"挡了回去，容易让人以为自我验证闭环是通用解。它其实只覆盖了最幸运的情形——存在oracle（机械判据）的任务：有测试套件的代码、可执行的验收脚本、可逐项核对的清单。生成与验证的成本严重不对称：生成便宜，验证贵，于是可靠性的上限卡在验证那一侧，而不是模型那一侧。没有机械判据的领域——重构是否改变了行为、UX 是否"更好"、一段模糊需求是否被满足——测试全绿也不代表做对了，验证绕一圈最后还是回到人；人在环上，人就是吞吐量的瓶颈。

  • 实践症状：agent 的"90% 自主"发生在有测试覆盖的任务上；一旦进入无判据的长尾任务，自动化率断崖式下跌；
  • 部分对策：把模糊需求在开工前翻译成可核对的验收清单（报告 04 的 200+ 项 JSON 功能清单）；给验证设独立的"评估者"角色（报告 01 的评估者-优化者模式）；
  • 对策的代价：清单本身成为新的维护面——清单错了，agent 会坚定地做完一件错事。

含义：判定"完成"的依据从哪来，是 harness 设计的第一道主观题——没有 oracle 的任务，自主性没有意义。

难点 02 / 06删错与留错对照正文 2.3 节

压缩的损失会延迟显现，污染的方向会持续放大

症状：失败在离病因很远的地方冒出来，而且说不清是哪一步开始的。

正文 2.3 与深挖案例 tab 已给出压缩、笔记、子代理三条路线；实践中真正难的不是选路线，而是"删 / 留"两类错误都延迟暴露。删错：你在 t=100 无法知道哪些细节在 t=500 变成关键约束——被压缩掉的细节里，总有一部分后来被证明是要害。70% / 50% 阈值（Gemini CLI 早期 / 当前默认）、保尾 30%、"关键细节、事件与决策"（Cognition 甚至为压缩专门微调了小模型）都是对策，但没有一个可以照抄。留错：一条错误或带噪声的工具结果一旦进窗，模型把它当作事实反复引用，后续决策全部建在它上面——社区称之为 context poisoning（上下文污染）。它与 context rot 是两种病：rot 是精度随长度的衰减，poisoning 是方向性跑偏，模型对"错误的前提"几乎没有自我纠偏能力。正文 2.3 说的"保留错误"是保留真实失败让模型学到教训——前提是那个错误是真的；对假错误，保留等于投毒。

含义：压缩在赌"以后用不上"，不压缩在赌"现在装得下"——harness 每一轮都在下注，而输赢要很多步之后才揭晓。

难点 03 / 06归因与评估对照正文 3.1 节

归因考古：失败是几十万 token 里的遥远回声

症状："这是模型的锅、工具的锅，还是我的锅？"——没有捷径可问。

harness 出问题的第一问永远是归因，而非确定性让这问没有捷径：同一输入两次运行，一次成功一次失败，无法重放。排查因此变成考古——在一整条几十万 token 的轨迹里，找"错误信念在哪一步形成"。OpenAI 的应对是把这变成制度而非救火：程序化跑评估留下完整 transcript，再用 Claude Code 在工具设计层面批量归因（正文 3.1 节）；报告 02 的做法是先建评估、再动工具——评估先行不是美德说教，是因为没有它，归因根本无从下手。次序反过来（先改 harness 再补评估）的团队，每一次改动都是盲调。

  • 实践症状：改一行工具描述，三天后在另一类任务上出回归——紧耦合系统的经典表现（难点 06 的一半）；
  • 部分对策：评估先行 + held-out 防过拟合（报告 02）；逐步 tracing——每步记 token、工具结果与决策依据；
  • 对策的代价：评估本身贵且 flaky——同一任务多跑几次方差可观，"显著改进"需要多次重复，迭代速度被钱和时间封顶。

含义：没有 eval 套件与轨迹留痕的 harness 调优，等于闭着眼睛修表。

难点 04 / 06状态与世界对照正文 2.4 / 2.5 节

checkpoint ≠ restore：存档的是 agent，漂移的是世界

症状：续跑的 agent 把半成品当成自己的起点，或重做已完成的工作。

崩溃续跑的难点不在存档，而在恢复的那一刻，外部世界已经变了：文件被用户改过、git 前进了几个提交、端口被别的进程占了、依赖悄悄升级。checkpoint 里存的是 agent 的记忆，而 agent 的计划引用的是一个不再存在的世界。报告 04 的"会话启动仪式"（确认目录 → 读 git log → 读进度文件 → 冒烟测试）本质上是一套"重测世界"的仪式；报告 05 走得更彻底——Session 是窗口之外的只追加日志，harness 本身不留本地状态，崩溃后凭 wake(sessionId) 续跑：这是把数据库 WAL/journaling 的思想搬进 agent。剩下最难的部分报告没有展开：让工具调用幂等、可重入——"创建前先检查""改库前先探状态"，这些约束没有框架强制，全靠 harness 作者逐个补。还有一层报告不写的脏活：跑 5 小时撞上 429 限流或断流——瞬态基础设施故障的退避重试与断点续传，是纯工程耐力活。

含义：恢复的可靠程度，决定长任务敢不敢交给 agent——这是 OS 类比里最难兑现的部分。

难点 05 / 06信任边界对照正文 2.5 节

权限粒度是产品决策，不是工程参数

症状：要么人被"允许"按钮淹死，要么 agent 拿着 secrets 裸奔。

太细——人一天点 200 次"允许"，被训练成不看内容秒批的橡皮图章（permission fatigue），安全形同虚设；太粗——agent 能读环境变量里的 secrets、能通过工具参数把数据外传，沙箱逃逸是真实威胁（STOP 论文专门把"绕过沙箱的频率"列为评估项，DGM 全程沙箱加人工监督）。两端的失败方式完全不同，中间没有理论最优点，只有按任务组合调出来的信任边界：分级授权（只读免批 / 写入待批 / 危险动作人工复核）加事件触发升级。正文 2.5 的自主度阶梯与 MCP + OAuth vault（凭据进保险库、agent 只拿调用权）是这一层的两个代表答案。每家的 harness 长得都不一样，症状主要出在这一层——它是产品价值观的直接投影。

含义：权限系统没有工程最优解，只有"你愿意把多少信任交给一个不可靠的循环"这一个问题。

难点 06 / 06耦合与漂移对照正文 3.1 / 2.5 节

紧耦合回归与模型漂移：harness 是一个会随模型腐烂的系统

症状：没改坏的组件坏了一个；没动过的 harness 悄悄变差了。

harness 是紧耦合系统：工具描述、压缩阈值、权限规则、系统提示互相作用——改一处，往往三步之后在别处坏，而每次完整验证都要真金白银跑长任务，迭代极慢（难点 03 的代价在这里再次出现）。更深一层是时间维度的耦合：harness 里写满了关于"当前模型做不到什么"的假设。报告 05 的原案例：Sonnet 4.5 有"上下文焦虑"（临近窗口上限就提前收工），团队用 context reset 治好；换 Opus 4.5 后这个行为消失了，reset 反而成了累赘——为一个模型缺陷打的补丁，在下一代模型上变成负担。且这种退化是静默的：不报错，成功率掉几个点。跨模型更甚：工具调用纪律、报错恢复习惯的模型间差异，让"同一套 harness"基本不存在。实践者的结论收敛为报告 04/05 的那句设计纲领：为换模型而设计（design for model replacement）——把补丁做成可开关的假设，而不是焊死的规则。

含义：harness 不是一次性工程，而是随模型版本持续维护的"移植层"——它的半衰期由模型进步的速度决定。

「oracle（机械判据）」指什么？

定义：不需要另一个智能体参与、纯程序就能裁决成败的判据——测试套件、编译器、可执行的验收脚本、可逐项核对的清单。它是"自我验证闭环"能自动转起来的前提。

「context poisoning（上下文污染）」是什么？

定义：一条幻觉或错误的工具结果进入窗口后，被模型当作事实反复引用——agent "相信自己撒的谎"，后续规划全部建在错误前提上。出自 Dex Horthy（HumanLayer）提出的四分类：poisoning（污染）、distraction（过载分心）、confusion（干扰稀释）、clash（新旧冲突）。

与 context rot 的区别：rot 是精度随长度缓慢衰减的"梯度"，poisoning 是方向性跑偏的"拐点"——一条坏数据足以让整条轨迹改道，且模型几乎没有自我纠偏能力。

与"保留错误"的区别：正文 2.3 的"保留错误"指保留真实失败，让模型从教训中学习，前提是那个错误是真的；对假错误（幻觉、脏数据），保留等于持续投毒。

部分对策：工具返回带可信度信息；关键结论外置成文件而非只存窗口；用子代理隔离探索性搜索的原始噪声。

这也是"轨迹要留痕"的又一理由：没有 trace，你甚至不知道是从哪一条坏数据开始跑偏的。点击空白处或按 Esc 关闭。

「harness 必须主动决定什么不进窗口」为什么、怎么做？

「上下文腐烂（context rot）」是什么？

现象：token 越多，模型准确回忆和利用信息的能力越差——上下文不是越大越好，而是会"腐烂"的稀缺资源。

机理：注意力预算。transformer 中每个 token 与其他 token 形成 n² 个成对关系，而训练数据以短序列为主，长上下文能力天然被稀释。

指导原则：找到最小的高信号 token 集合——策展而非堆砌。这意味着 harness 必须主动决定什么不进窗口，而不是来者不拒。

落地手段：长任务在压缩（compaction）、结构化笔记、子代理三者中按任务形态选择；工具侧用精简返回档位（如 DETAILED / CONCISE）控制每次进窗口的内容。

「用 Claude Code 分析执行轨迹并自动重构工具」具体指什么？

执行轨迹：程序化跑评估留下的完整记录——agent 每一轮的推理、每次工具调用的参数与返回、报错、token 消耗，以及任务是否通过验证。几十个任务跑下来，就积累几十份 transcript。

「注意力预算」是什么？

定义：Anthropic 对“模型注意力是有限资源”的比喻——每个进入窗口的 token 都要占用一份注意力，而这份注意力的“质量”随总量增加被稀释，就像人类的工作记忆。

「MCP + OAuth vault」是什么？

“牛”而非“宠物”是什么梗？

出处：云运维圈的老格言（2000 年代末成型）——宠物式运维给每台服务器起名字、生病了开机抢救；牛式运维只给编号，坏了直接杀掉换一头，因为状态都在外部（镜像、配置、存储）。

「TTFT / p50 / p95」是什么？

TTFT（Time To First Token）：从提交任务到看到第一个响应 token 的时间——交互体感的决定指标，用户对“开始响应”远比对“响应完毕”敏感。

p50 / p95：百分位数。p50 是中位数（一半请求快于此）；p95 表示 95% 的请求快于此——尾部指标专门抓“最倒霉的那批请求”。

这里为什么重要：p50 降 60% 说明平均体感大幅改善；p95 降 90%+ 说明“偶尔卡几分钟”的尾延迟几乎消失——后者只有无状态架构（实例随起随用、不迁移状态）能做到。

「LogQL / PromQL」是什么？

「AI slop」是什么？

「消融（ablation）」是什么？

定义：控制变量实验——把系统拆成组件，逐一去掉或替换某个组件，量化它对整体成绩的贡献。名字来自神经科学的“切除研究”。

「tree-sitter / AST」是什么？

tree-sitter：增量语法解析器生成器（Neovim、GitHub 代码高亮的底层）——把源码解析成语法树，速度快到可以在每次击键后增量重析。

AST（抽象语法树）：源码的树状结构表示——类、函数、变量的定义与引用都是树上的节点。aider 借它拿到“全仓库的符号图谱”，而不需要真的“理解”代码。

repo map 的关键在于：排序发生在 AST 层（结构）而非语义层——便宜、确定、可复现。点击空白处或按 Esc 关闭。

「pgvector」是什么？

PostgreSQL 的向量检索扩展——在普通关系数据库里直接存 embedding、做相似度近邻查询。MemGPT 用它做 archival storage：历史消息与文档切块存进去，模型用检索函数按语义回捞。

在“数据库当磁盘”的比喻里，PostgreSQL 是磁盘，pgvector 是磁盘上的语义索引。点击空白处或按 Esc 关闭。

「KV-cache」是什么？

定义：推理时每个 token 的键值中间结果缓存——自回归生成的每一步都要“看”全部历史，缓存避免了逐 token 重算。前缀不变，缓存直接复用；前缀一变，从变动处开始全部作废。

为什么是生产指标：命中缓存的输入价格约为未命中的十分之一，而 agent 任务的输入输出比可达 100:1——命中率直接决定成本曲线。这就是“append-only、稳定前缀、确定性序列化”三条铁律的由来。

“KV-cache 感知”因此是“什么不进窗口”的财务镜像：改写历史不仅丢上下文，还烧钱。点击空白处或按 Esc 关闭。

「lost-in-the-middle」是什么？

「logits 掩码」是什么？

logits：模型输出层在 softmax 之前对每个 token 的原始打分。解码时把某些 token 的分数压到负无穷，模型这一步就“永远选不出”它们。

掩码 = 按步关工具：harness 每一步按任务状态生成“当前允许的工具”掩码——工具定义都还在上下文里（前缀不变、缓存不破），但模型此刻只能“说”允许的那几个。这就是 Manus “Mask, don't remove” 的实现。

「产品级抽象稳定、团队级深度耦合」是什么意思？

产品级 harness：服务成千上万个你无法预见的用法，而它依赖的模型还在持续换代——今天押注的假设（模型会规划、上下文多长、哪些工具可靠）可能半年后全部失效。所以接口要抽象、实现可替换：Anthropic 的“对实现不持立场”就是这一侧的表述——把赌注押在某个具体实现上，模型一升级，赌注就变成包袱。

团队级 harness：服务一个已知仓库、已知流程、已知的一群人，维护者就是受益者。Codex + 特定仓库结构那种“极端重度投资”正是靠深度耦合换效率：假设越具体，流程越锋利；假设过时了，团队自己改得起——耦合的维护成本有明确的人买单。

判断标准：不是“耦合好不好”，而是两个变量——假设多久过时一次（换模型/换任务的频率）、过时之后的维护成本由谁承担。产品级赌的是适应力，耦合越深死得越快；团队级榨的是确定性，耦合越深跑得越快。同一家公司对外抽象、对内耦合，并不矛盾。

一句话版：产品级 harness 为“未知”设计，团队级 harness 为“已知”优化。与 Codex 备注连读——深度耦合的团队级样本。点击空白处或按 Esc 关闭。
