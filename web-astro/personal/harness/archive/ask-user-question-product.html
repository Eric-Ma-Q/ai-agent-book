SECTION 00一句话与三条公理

一句话结论：这个产品的成功不取决于「问得多好」，取决于两件事——该不该问（门控）与问完有没有用（闭环）。中间那层「怎么问」，是这两件事的附属品；行业目前大部分精力花在中间层，而多数失败发生在这两端。

把它当成一个独立产品，是因为它有三个别的组件没有的性质：它消耗的是人的注意力（不可缓存、不可重试）、它的失败是隐性的（用户点了推荐，然后带着一个错误决定走了）、它会训练用户（被问多了会烦躁，被猜错了会不信任，两种学习都不可逆）。

公理 A1 · 问了不用，比不问更伤。用户选了 B、模型照 A 做，造成的不是一次错误，是一次「我在这个系统里说的话不算数」的认知。它比沉默的失败更贵。
公理 A2 · 推荐只是押注，不是指令。推荐的价值在于「模型先下注，人只做否决」，一旦推荐变成默认路径，人就不再否决——产品退化成确认按钮。
公理 A3 · 能查到的不要问人。事实型缺口用工具补，偏好型缺口才问人。把检索失败转嫁给用户，是最常见的提问失礼。

SECTION 01产品定义：它到底在卖什么

1.1 卖的是「返工前置」，不是「礼貌」

模型面对欠定请求只有两条路：猜（然后可能返工）或问（然后可能打扰）。这个产品卖的是第三条：把返工提前到动手之前，用一次几秒钟的确认换掉一次几分钟的重做。所以它的价值锚点不是「体验更友好」，而是「返工率下降」——所有设计决策最终都要回到这个数上。

问题是这个交换天然不对称：提问的成本是即时的、确定的、可见的（打断、等待、选择困难），收益是延迟的、概率的、不可见的（避免了一次你永远不会知道的返工）。人被要求在两个这样的选项中做选择时，系统性地低估后者。[理论]（Tversky & Kahneman, 1974；Johnson & Goldstein, 2003 的默认效应同源）

由此得到一条反直觉但正确的产品结论：默认策略必须偏保守——少问，直到有证据说该问。把「提问」设计成廉价、随手可得的动作，会让模型陷入问题轰炸；而问题轰炸的代价不是那几秒，是用户从此开始无视所有提问。

1.2 一次提问的完整成本结构

产品化的第一步是把「问一次」拆成可以被削减的分项，而不是笼统的「用户体验」：

成本项具体表现产品手段
打断思路被打断，重新进入状态要几十秒非阻塞提问；攒批；不在流式输出中插问
决策负担用户被迫做他本不想做、或没能力做的判断门控：只问「偏好型」，不转嫁「专业型」判断
阅读读题干 + 读 3 个选项 + 读描述选项描述写后果不写定义；单行可扫
后悔选完发现选错，要回退重来可撤销；preview 预告后果
信任折旧每问一次低质量问题，信任扣一点，可累积问题质量回归集；重复提问去重

1.3 判据：一个不等式

提问值不值得，可以写成一个期望收益不等式。它的作用不是精确计算，而是把「感觉该问」变成三个可以分别优化、也可以分别测量的人：

E[ask] = P歧义 × P问对 × C返工 − C打断  >  0

四项各自对应一个可优化的组件：

  • P歧义——模型自己的不确定性估计。可从「自评置信」「schema 校验失败」「工具返回多解」「历史返工信号」四处取。
  • P问对——问出来的问题是否真的能消解分歧。这是最容易被忽略、也最容易归零的一项：问了一个不相关的问题，前两项的乘积直接变成负数。
  • C返工——猜错的代价。可逆操作接近 0，不可逆操作（删数据、发邮件、改生产配置）极高。
  • C打断——人的注意力成本。与用户当前状态强相关：闲置时接近 0，正在输入时极高。

学术界已经把这套东西形式化为 Value of Information（VoI）：只有当「问一个问题带来的期望效用增益」大于「施加给用户的认知成本」时才开口。近年的工作把它做成了无需调参的推理时方法，并在 20 Questions、医疗诊断、订票、电商四类场景里稳定超过手工阈值。[论文]（2026-01，arXiv:2601.06407） 更激进的一条线是把 VoI 摊销进单次前向：模型一次输出同时给出决策分布与「每个缺失槽位值多少钱」，从而决定问哪个槽。[论文]（2026-09，arXiv:2609.30706）

SECTION 02四方用户，四种失败体验

这个产品最特殊的地方是：它的「用户」不是一个人。写这个工具的人、调这个工具的人、被这个工具问的人、以及事后看数据的人，四种角色对「好」的定义完全不同。设计时的取舍必须显式说明「这一条是照顾谁的」。

角色它是谁它要什么（JTBD）它最恨什么
第一调用者 模型自己 用最少的 token 表达最大的不确定性；问完能拿到可直接用的结构化答案 被迫用自由文本描述选项；答案回来是一段口语，还要自己解析
决策者 人类用户 在不该由他操心的地方不要被打扰；在该由他拍板的地方给他清晰可比的选项 被问「你想用哪个库」这种本该模型决定的事；点了推荐却发现被带偏
集成方 harness 开发者 / 产品经理 能控制提问频率；能定制渲染；能拿到可解释的数据 schema 不可校验、行为不可预测、埋点拿不到
评测运营 做质量与回归的人 问题质量可离线打分；提问策略可 A/B；失败可归因 只拿到一段自由文本，无法回放、无法聚类

一个由此推出的设计原则

  • 对模型：给它枚举，不给它散文。选项的类型系统（单选/多选/数字/日期）比让模型自由拼一句话更能保证下游可用。
  • 对人：给后果，不给定义。「会跳过测试直接部署」比「--no-verify 参数」有用得多。
  • 对集成方：把策略暴露成配置，而不是写死在提示词里。能配的东西才是产品，写死的是习惯。
  • 对评测：每一次提问都必须落成结构化事件。自由文本的「模型问了一句、用户回了一句」在离线分析里几乎不可用。

SECTION 03该不该问：VoI 门控

3.1 模型「知道自己不知道」，但不会主动说

这是整个产品的存在理由。2026 年的一项系统评测给了一个很干净的结论：模型在被明确要求判断歧义时往往能识别出歧义，但在正常问答场景里绝大多数情况仍然直接作答——识别与行为之间有一条稳定的鸿沟。检索到的上下文还会进一步扩大这条鸿沟——它让问题变得更「可答」，同时让模型更不倾向于问。[论文]（2026-05，arXiv:2605.25284）

这解释了为什么不能把「该不该问」写进系统提示词了事。提示词说「遇到歧义请提问」，模型仍然会答；只有当成可被强制调用的动作、并且有外部信号触发时，行为才会变。同理，已有工作证明「什么时候问」本身是可以训练的：用后续对话轮次的期望结果来给偏好打标，模型才学得会「先问再答」。[论文]（2024-10，arXiv:2410.13788）

3.2 三档门控，而不是一个开关

把「问不问」做成二值开关是错的，因为它没有表达「该问但可以先做」这个中间态。三档才对应真实决策：

档位条件行为典型场景
强制问
must		C返工 极高（不可逆、有外部副作用）且存在真实分叉停下，阻塞，等答案；不允许带假设继续删除/发布/转账/对外发送；跨库迁移方案
允许问
may		分叉真实存在，但猜错可回退非阻塞地问，同时按推荐值先做；答案到达后校正技术选型、文案语气、文件组织方式
禁止问
never		可查、可推断、或属于模型的专业判断自己解决；把假设写进输出，让人事后否决「这个库的 API 怎么用」「你想用哪个框架」

注意第三档的措辞：不是「不许问」，而是「用假设 + 明示」替代提问。即模型自己决定，但把「我假设你指的是 X，如果不是请纠正」写进正文。这比弹窗便宜得多，而且给了用户否决权。大量本应属于这一档的问题被错误地升级成了弹窗，是当前体验变差的主因。

3.3 触发信号从哪来

门控不能靠模型「感觉」，要给可计算的信号。四个来源按可靠性排序：

信号怎么取可靠性
操作不可逆性工具的 destructive / readOnly 元数据高（机器可判）
参数校验冲突schema 枚举冲突、必填缺失、多个合法解高（机器可判）
历史返工同类任务近期被用户改口的频率中（需统计）
自评置信模型对自身答案的显式打分低（易过自信，且不可校准）

把低可靠信号当主判据，是「问题轰炸」的第二大来源（第一是提示词催促）。正确做法是用高可靠信号兜底（must 档），用低可靠信号只做「may 档」的候选生成，再由模型自己决定是否调用。

SECTION 04设计空间：六个自由度

把「选项 + 推荐」当成一个整体来设计是粗糙的。它其实是六个独立可调的维度，每个维度都有明确的推荐值和不推荐的极端：

自由度可选范围推荐值为什么
① 触发 从「从不问」到「每步都问」 三档门控（§3） 二值开关无法表达「先做后校正」
② 选项数 2 – 7 3（硬上限 4） 选择过载：6 种果酱的购买率约为 24 种的 10 倍[经典]；超过 4 个说明问题没收敛，应先问「哪一类」
③ 结构 单选 / 多选 / 自由文本 / 混合 单选为默认，多选需显式声明，永远保留逃逸阀 多选会把「决策」退化成「收集」，用户倾向全选
④ 呈现 纯列表 / 带描述 / 带预览 / 带推荐语义 标签 + 一行后果 + 一个推荐 + 可展开预览 信息量与扫读速度的平衡点；预览折叠，不占默认视线
⑤ 时序 阻塞 / 非阻塞 / 定时过期 默认非阻塞，仅 must 档阻塞 阻塞把「问」变成「停」，代价从秒级升到分钟级
⑥ 闭环 答案仅入上下文 / 入上下文并校验 / 沉淀为偏好 入上下文 + 提交前校验；沉淀偏好需显式授权 公理 A1；偏好沉淀容易变成「一次误点终身生效」

4.1 为什么选项数要卡在 3

选项数不只是界面问题，它同时是三个约束的交点：

  • 认知：选项越多，「扫一遍做比较」的成本超线性上升，而决策质量并不上升。经典果酱实验里，展示 24 种时只有 3% 的人购买，展示 6 种时是 30%。[经典]（Iyengar & Lepper, 2000, JPSP 79(6):995–1006）
  • 生成：模型生成第 4、第 5 个选项时，往往开始制造「凑数的差异」——这正是伪选项的来源（§9）。
  • 空间：移动端一屏放得下的上限是 4 个带描述的选项，再多就要滚动，滚动会让最后一个选项（通常是「都不是」）被系统性忽略。

所以「超过 4 个」不是渲染问题，是信号：它说明模型还没想清楚要问什么。正确反应是让模型先问一个更上层的问题（「你想解决的是 A 类还是 B 类问题？」），而不是把 7 个选项塞进一张卡片。

SECTION 05对象模型与工具契约

契约层是这个产品的地基。下面是一份主张版本——和现在主流的「label + description 数组」相比，它多了三样东西：推荐的语义、逃逸阀、时序控制。

{
  "name": "ask_user_question",
  "description": "Ask the user to choose between concrete options, ONLY when a real fork exists AND the cost of guessing wrong exceeds the cost of interrupting. Never use it for facts you can look up, or for decisions you are authorized to make.",
  "inputSchema": {
    "type": "object",
    "required": ["header", "question", "options"],
    "properties": {
      "header":   { "type": "string", "maxLength": 12,
                    "description": "主题词，折叠态与通知里用" },
      "question": { "type": "string",
                    "description": "一句话说清要定什么，不复述背景" },
      "why":      { "type": "string", "maxLength": 80,
                    "description": "为什么要问——界面上作副标题" },
      "options": {
        "type": "array", "minItems": 2, "maxItems": 4,
        "items": {
          "type": "object",
          "required": ["label", "description"],
          "properties": {
            "label":       { "type": "string", "maxLength": 24 },
            "description": { "type": "string", "maxLength": 60,
                             "description": "选它会发生什么，不是它是什么" },
            "recommended": { "type": "boolean" },
            "reason":      { "enum": ["most_likely", "safest",
                                      "cheapest", "status_quo"] },
            "preview":     { "type": "string", "maxLength": 120 }
          }
        }
      },
      "multiSelect":  { "type": "boolean", "default": false },
      "allowOther":   { "type": "boolean", "default": true },
      "blocking":     { "type": "boolean", "default": false },
      "expiresInSec": { "type": "integer", "default": 0 }
    }
  }
}

三个关键字段的理由：

  • reason：把「推荐」从一个形容词变成一个枚举。理由见 §6，这是本文档最重要的一条主张。
  • allowOther：默认开。没有逃逸阀的多选题，本质是在三个坏选项里选一个最不坏的，用户会感到被操纵。
  • blocking：默认关。默认阻塞是把「询问」做成了「中断」，一个默认值就能让体感从「商量」变成「盘问」。

契约层的验收标准

  • 任何一条渲染路径（桌面卡片、命令行、语音）都能只凭这个 JSON 还原出完整界面，不需要额外上下文。
  • recommended 最多一个；多于一个应当是 schema 校验错误，而不是「模型的问题」。
  • 答案回传的 schema 与选项一一对应，且带 option_id——不能靠 label 字符串匹配（改一个字就断）。

SECTION 06推荐的四种语义（核心）

这一节的产品主张：「Recommended」这个词现在同时承担着四种互相冲突的语义。用户无法从中学到任何稳定的东西，于是它退化成装饰。把语义拆成四个枚举值，是这个产品从「好看」走向「可信」的分水岭。

6.1 同一个标签，四种意思

当模型给某个选项打上「推荐」时，它实际想说的是下面四件事之一。这四件事在大多数情况下指向不同的选项，而界面上它们长得一模一样：

语义它回答的问题什么时候用误用后的后果
most_likely
最可能		 「我猜你想要哪个」 用户有明确偏好但没说出口，模型有把握推断 把用户的偏好塑造成模型的先验——以为是预测，其实是引导
safest
最安全		 「选错代价最小的那个」 不可逆操作、对外副作用、有合规敞口 过度保守：功能永远停在最小改动，产品变成废纸
cheapest
最省		 「最省时间/最少 token/最少改动」 探索阶段、试错成本低的场景 省出了错误——省下的时间在返工时加倍偿还
status_quo
维持现状		 「什么都不改」 渐进式改造、有历史包袱的系统 现状偏见固化烂设计：每一次都「保持现状」，系统永远不演进

6.2 为什么必须拆开

三个理由，从弱到强：

  1. 可学性。用户要能建立稳定的预期，才谈得上信任。「推荐」如果能同时表示「最可能」和「最安全」，用户只能靠猜它这次是哪一种——猜错几次之后，就不再看它了。
  2. 可校准。「最可能」的推荐可以被事后验证（采纳后是否返工），「最安全」的推荐不能（你无法观测到没发生的事故）。混在一起，两类推荐的质量就无法分别度量。
  3. 可追责。当用户因为跟随推荐而出错时，需要能回答「模型当时以什么理由推荐它」。没有 reason 字段，这个复盘做不了。

6.3 视觉权重怎么配

语义拆开之后，视觉上也要分级——不是所有推荐都该用同一个高亮：

reason视觉处理是否默认选中
safest强高亮 + 「最安全」字样是（安全兜底值得默认）
most_likely强高亮 + 「推荐」字样否（默认选中会制造锚定）
cheapest中性标记否
status_quo不加标记，仅排序靠前否

「most_likely 不默认选中」这一条值得单独说：视觉高亮 + 默认选中 + 排在第一是三重锚定，会把「推荐」变成事实上的唯一选项。锚定效应在数值判断上的效应量早已被反复验证[经典]（Tversky & Kahneman, 1974, Science 185:1124–1131），而在「三选一」这种低信息量场景里，它的强度只会更大。保留高亮、放弃默认选中，是性价比最高的一次取舍。

SECTION 07状态机与闭环

大多数人只画了「问 → 答」两个状态。真实系统里至少有七个，漏掉的那几个正是体验崩坏的地方。

gated→ presented→ answered→ applied
presented 的其余出口： skipped expired superseded ignored ⚠
状态含义产品处理
gated通过了门控，但还没呈现可批量攒（攒 2–3 个一次问，减少打断次数）
presented已呈现，等待非阻塞时模型继续工作，UI 常驻不抢焦点
answered用户已答写入会话状态，生成一条结构化事件
applied答案真的影响了后续动作必须有这个状态；没有它就无法验证公理 A1
skipped用户主动跳过按 reason 降级执行（safest 或 status_quo），并明示「已按 X 继续」
expired超时同 skipped，但需在正文里说明「你没回，我先按 X 做了」
superseded模型在等待期间自己解决了主动撤回问题，置灰并标注「已不需要」——让用户答一个过期问题是设计事故
ignored ⚠用户答了，但后续动作没变这是 bug 不是状态，必须监控；它是 A1 的唯一可观测形式

7.1 答案怎么进入下一步

「答案写入上下文」是不够的，因为上下文是建议性的，模型可以无视。要做成硬约束，需要三件事：

  1. 注入成结构化事实，不是复述：「用户已选择 option_id=2（pytest 而非 unittest）」，而不是「用户好像倾向 pytest」。
  2. 提交前校验：在产生副作用的动作（写文件、发请求、执行命令）之前，检查该动作是否与已选答案冲突；冲突则拦下并回到 presented。
  3. 冲突可见：确实需要违背用户选择时（比如技术上不可行），必须显式说明理由，而不是悄悄改。

7.2 非阻塞到底怎么工作

非阻塞不等于「问完不管」。它有一个明确的协议：

  • 模型带上默认假设继续执行，并在输出里注明「我先按 X 做，你随时可以改」。
  • 答案到达时，如果该步骤尚未提交 → 直接替换；已提交 → 进入修正轮，只重做受影响的部分。
  • 修正轮的代价必须可控：这要求模型把工作切成「可局部重做」的单元，这本身是编排层的设计约束。

这也是为什么非阻塞不能无脑开：它把成本从「用户等待」转移到了「系统支持局部重做」。没有这个能力的 harness，只能老老实实阻塞。

SECTION 09失败模式目录

这个产品的失败很少是「崩了」，几乎全部是「看起来正常但有害」。下面十条按危害排序，每一条都给可观测的症状——因为它们大多没有报错。

三条从失败模式里长出来的硬规则

  • 推荐率与采纳率必须同时监控。前者防「全推荐」，后者防「三重锚定」，只盯一个都会失衡。
  • 「答而不用」是唯一需要 P0 告警的失败。它不出错、不报错、用户也不一定当场发现，但它直接摧毁公理 A1。
  • 选项的描述写「后果」，不写「定义」——这一条同时解决了阅读成本、伪选项和信息量三个问题。

SECTION 10度量：什么才算好

10.1 主指标只有一个

首次答案后的返工率。它直接对应产品定义（把返工前置），且不受「问得多不多」这种策略偏好的干扰。其余指标都是它的分解或护栏。

指标定义方向备注
返工率 主首答后需要用户实质性纠正的比例↓产品存在的理由
提问率每任务平均提问次数观察不是越低越好，取决于任务不确定性
推荐采纳率点推荐项 / 总回答60–80%100% 是警报，见下
偏离率选非推荐项的比例20–40%太低=没读，太高=推荐不准
推荐后悔率采纳推荐后又撤销/改口↓衡量推荐质量的真指标
跳过率未作答直接跳过的比例观察高跳过 = 问题不相关
决策耗时呈现到回答的中位时长↓含阅读成本
问题质量分离线 judge 打 1–5 分↑可参考 CrowdLLM 式多模型评审

10.2 采纳率不是越高越好

这是最容易被做错的一个指标。推荐采纳率 100%，通常不是「推荐很准」，而是「用户已经不读了」——系统退化成一键确认，推荐携带的信息量归零。健康区间大致是 60–80%：多数时候跟着推荐走（它确实准），但稳定有一部分人在做独立判断。

偏低 · 用户没在读
健康 60–80%
偏高 · 盲从失效
0%50%100%

同理，偏离率过低也是坏信号：它意味着没有人否决过模型，而模型的判断不可能永远正确。偏离率与后悔率要一起看——偏离多、后悔少，说明推荐确实不准；偏离少、后悔多，说明用户被带偏了。

SECTION 11评测方法

这个产品没法只靠线上指标调优，因为线上看不到「没问的那个问题」的代价。三层评测缺一不可：

11.1 离线：歧义集 + 问题质量评分

构造三类样本——真歧义、假歧义（看着模糊其实有唯一解）、完全不歧义——分别检查：该问的有没有问（召回）、不该问的有没有问（精确率）、问的问题能不能消解分歧（有效性）。后者可以交给多模型评审，学术界已有把众包判断用多个 LLM 实例模拟的做法，在 ClariQ 上验证过可行性。[论文]（2024-10，arXiv:2410.19692）

更进一步，问题质量是可以被「训练」出来的：STaR-GATE 用 25,500 条 persona–task 合成对话，让模型通过自我改进学会问「能提升后续回答质量」的问题。[论文]（2024-03，arXiv:2403.19154） TO-GATE 则指出自教式推理找不准提问轨迹，会用「澄清解析器 + 总结器」做轨迹优化，避免问出与任务无关的问题。[论文]（2025-06，arXiv:2506.02827） 对产品的启示：「别问无关问题」不是提示词能解决的，它需要专门的评测集和优化目标。

11.2 在线：A/B 提问策略，而不是文案

可实验的变量按杠杆大小排序：门控档位 > 阻塞/非阻塞 > 推荐语义 > 视觉权重 > 文案。前两个直接改变任务完成路径，后三个只改变点击分布。大多数团队从文案开始 A/B，是因为文案最容易改——这正是它们调不动的原因。

11.3 反事实：强制不问 vs 强制问

把同一批任务跑两条轨迹：一条禁止提问，一条强制提问，比较返工率与总耗时。这个实验很贵（要跑两倍），但它是唯一能回答「这个产品到底值不值得存在」的方法。它同时给出 §1.3 不等式里 C返工 与 C打断 的经验值——这两个数一旦测出来，门控阈值就不用再拍脑袋了。

SECTION 12边界：什么时候不该做

好产品的一半是「明确不做」。以下五种情况，正确的动作是不出现这个界面：

情况为什么不该问正确动作
模型把握很高提问是纯噪音，且每次噪音都在消耗信任额度直接做，把假设写进输出
操作可逆且便宜先做再改比先问再做快一个数量级做，提供一键撤销
用户已授权自主反复确认是对授权的不尊重只在 must 档（不可逆）破例
答案能查把检索失败转嫁给用户（公理 A3）调工具；查不到再说「我查不到」
时间敏感 / 流式中打断的代价高于猜错的代价延后，或攒到下一个自然停顿

还有一类更隐蔽的：「问题本身是对的，但用户没有能力回答」。比如让非技术用户选「用 RSA 还是 Ed25519」。这类问题的正确形态不是选项，而是把技术选择翻译成后果选择——「更安全但需要换证书」vs「兼容性好但安全性一般」。如果翻译不出来，说明这个问题本就不该问人。

SECTION 14开放问题

这些问题没有标准答案，但它们决定了这个产品最终长成什么样。列出来是因为：写下问题本身，比假装有答案更接近产品设计。

  1. 推荐该由模型给，还是由策略层给？策略层能用「这类问题用户 80% 选 X」的历史统计覆盖模型判断，但它看不到当前上下文；模型看得到上下文，但没有统计先验。也许正确形态是两者各自出价，取并集。
  2. 打断成本是线性的还是超线性的？如果 3 次提问的成本等于 1 次的 3 倍，就攒批；如果超过 2 次就急剧恶化，就该「只问最重要的一个」。这个函数形状决定了整个交互节奏。
  3. 用户跳过后，按推荐做还是按最安全做？推荐是「我猜你想要」，最安全是「我不让你出事」。跳过意味着用户放弃了表达偏好，但不等于授权冒险。
  4. 这次的选择要不要沉淀成长期偏好？沉淀能减少后续提问，但会制造「一次误点，终身生效」——尤其当用户当时是在赶时间随手点的。
  5. 多人共用同一个 agent 时，推荐代表谁？团队场景里「用户」是复数，推荐可能代表提交者的偏好，也可能是模型的平均值，这两者不该长得一样。
  6. 中文本地化会不会改变采纳率？「推荐」两个字的语义强度、以及它在中文界面里的社交含义（像不像「我给你做主」），可能显著不同于「Recommended」。这是一个可以直接做实验的问题。
