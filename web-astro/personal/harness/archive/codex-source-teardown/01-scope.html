第 01 章 · 先划清能证明什么

取证边界：官方仓库让哪些判断变硬，让哪些判断变软

Codex 不是泄露材料，而是官方 Apache-2.0 仓库。好处是客户端、协议和运行时能逐行复核；代价是桌面 App、云端服务与模型服务不在仓库里，很多「线上怎样」的问题只能标不可验证。这一章先把边界画出来，后面九章才不会越界。

30 秒版

  1. 能读到的是本地运行时与协议：CLI、TUI、exec、app-server、沙箱、工具、记忆、多 Agent。
  2. 读不到的是桌面 App、Codex Web / Cloud、模型服务与 IDE 扩展的内部实现；它们只能标 D 级。
  3. 「不在本仓库」不等于「源码状态已确认」或「没有」，更不等于「线上默认开启」；证据等级必须跟着材料走。
用户问题这份公开仓库，究竟能支撑哪些产品判断？
实现差异

材料从「泄露副本」换成「官方仓库」，证据更硬，但覆盖面更窄：本地运行时与协议可证，服务端与 App 不可证。

01三种入口，不是三种实现

README 把 Codex CLI、桌面 App、Codex Web 并列成三种入口。这个并列很容易被读成「同一套实现有三种壳」，但仓库实际只覆盖第一种：CLI 在本机跑，App 与 Web 是另外的入口。

README.md1-8 · 三种入口并列；仓库只覆盖 CLI
<p><strong>Codex CLI</strong> is a coding agent from OpenAI that runs locally on your computer.</p>
...
If you want the desktop app experience, run <code>codex app</code> or visit the Codex App page.
If you are looking for the cloud-based agent from OpenAI, Codex Web, go to chatgpt.com/codex.</p>

所以「Codex 怎么工作」这个问题必须先限定对象：本专题讲的是仓库里的 CLI / 运行时 / app-server，不把 App 与 Web 的行为算进来。

02仓库里真正能读到的四层

把仓库按职责切开，能看到四层不同的东西：本地运行时、交互表面、协议层、平台能力。它们不是同一个「产品壳」的四种写法。

层代表目录能回答的问题
运行时codex-rs/core一轮怎么跑、工具怎么执行、上下文怎么压缩、权限怎么裁
表面codex-rs/tui、exec、cli用户从哪个入口进来、事件怎么显示
协议app-server、app-server-protocol多端如何共享 thread / turn / item
平台能力sandboxing、network-proxy、memories跨平台隔离、网络策略、记忆管线

这四层都能在固定 SHA 里指到文件，因此可以写 A 级证据；但它们仍然只说明「代码这样组织」，不说明「某个账号一定开启」。

03仓库外：只能看到客户端行为

桌面 App 在仓库里只留下安装器与下载地址；Codex Web / Cloud 只有客户端；IDE 扩展只有外链；模型服务只有 API 客户端。对这些部分，页面只能写「客户端怎么调用」，不能写「服务端怎么实现」。

Reusable Rust client for native ThreadService gRPC over HTTP/2, with no TUI,

04取舍：更硬的证据，换更窄的覆盖面

官方仓库让「代码怎么组织」变得可复核，也让「线上怎么表现」更难回答。页面如果为了完整而补服务端细节，就会把 A 级材料写成 D 级猜测；反过来，如果只写仓库里有什么，又会变成代码导读。折中办法是每章都先限定问题，再给判断。

换来什么每条关键判断都能回到固定 SHA 的 path:line，读者可以自己复核。
付出什么桌面 App、Cloud、模型服务的内部行为无法验证；跨产品差异只能比较两边都有材料的部分。
