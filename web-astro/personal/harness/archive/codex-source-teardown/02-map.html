第 02 章 · 运行时与表面分开

产品地图：CLI 只是其中一个客户端

第一次读 Codex 仓库，最容易把 CLI 当成全部。实际上 CLI 只是入口之一：TUI 与 exec 在进程内使用 app-server 客户端，桌面与移动通过 daemon 连远程 app-server，TypeScript SDK 又走 CLI 的 JSONL。理解「运行时 / 协议 / 表面」三层，后面的循环、工具与权限才有位置。

30 秒版

  1. CLI 是入口，不是运行时；运行时在 codex-rs/core，协议层在 app-server。
  2. TUI 与 exec 用 in-process app-server 客户端；桌面 / 移动通过 daemon；TS SDK 走 CLI JSONL。
  3. 这套分层的收益是多端复用，代价是协议兼容、实验面与生命周期复杂度。
用户问题一个本地 CLI，为什么会长出 app-server、daemon 和 SDK 这么多入口？
实现差异

Codex 把「运行时」与「表面」拆开：core 负责 agent，app-server 负责协议，TUI / exec / App / SDK 只消费协议。

02CLI 的命令面：入口很多，职责不同

CLI 同时承担交互入口、非交互执行、会话管理、App 安装器和协议服务。把它们混成一个「大命令」，就会误以为所有能力都在同一个进程里。

04取舍：复用协议，还是让每个表面各跑一套

让 TUI、exec、桌面、移动、SDK 共用 app-server，能把「会话、工具、权限、压缩」集中在一处；代价是协议要背兼容债，实验能力要通过 capability 协商，daemon 还要处理重启、升级与远程控制。

换来什么多端共享同一套 thread / turn / item 语义，运行时只维护一份。
付出什么协议层要持续兼容；experimental 方法多，客户端要做能力协商；daemon 生命周期成为新的故障面。
不要把「有 app-server」写成「所有端都走同一个进程」。TUI / exec 是 in-process 客户端，桌面 / 移动才通过 daemon；TS SDK 又是 CLI JSONL。
