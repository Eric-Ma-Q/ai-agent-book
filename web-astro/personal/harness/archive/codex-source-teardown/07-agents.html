第 07 章 · spawn 不是难点，协调才是

多 Agent：角色、并发上限、消息板与受限 review

多 Agent 最容易写成「模型可以再叫一个模型」。真正难的是：子 Agent 用什么角色、最多开几个、怎么等、怎么传消息、什么时候回收。Codex 把这些问题拆成 role、spawn / wait / send / close / resume、并发上限与 message board；V1 与 V2 的上限还不是同一个数。

30 秒版

  1. V1 默认 6 线程、嵌套深度 1；V2 默认 4 个并发线程（含 root，spawn 槽位按代码折算为 3），且 V2 feature 默认关闭。
  2. spawn 只是入口；wait / send / close / resume 才是把子 Agent 变成可管理任务的部分。
  3. message board 提供频道 / 帖子 / 订阅；review 是受限子 Agent，禁 web search、禁 collab、approval=Never。
用户问题什么时候该开子 Agent，开了之后怎么不让它失控？
实现差异

多 Agent 的产品难点不在 spawn，而在角色、并发上限、消息与回收；Codex 把这些做成一组工具与一个消息板。

01先分清 V1 与 V2 的上限

两个默认值经常被合并成一个「6 线程」。实际代码里，V1 的 agent_max_threads 默认是 6；V2 的 max_concurrent_threads_per_session 默认是 4，且在折算 spawn 槽位时减 1（把 root 算进并发）。V2 feature 默认关闭。

03消息板：协作不只有 spawn

spawn 之后，子 Agent 需要收消息、发进度、被回收。message board 把频道、帖子、订阅与通知做成共享设施，支持本地、内存、远端三种后端；它不是「再开一个模型」，而是协作状态层。

codex-rs/agent-message-board-host/src/lib.rs1-6 · 消息板是 host 能力，不是 prompt 技巧
//! Supplies board host capabilities through the public Core runtime interfaces.
//!
//! The extension owns backend construction, storage and tool registration. This adapter
//! selects configuration and supplies host capabilities. It never starts or restores
//! recipients during lookup. Notifications use ordinary agent-message scheduling.
//! Permanent board deletion uses the thread store's existing host cleanup callback.
消息板是否启用、用本地还是远端后端，取决于 feature 与配置；代码里有能力，不等于某个账号默认开启。

04review：一个受限子 Agent

review 不是「再问主 Agent 一遍」。它启动一个子会话，禁 web search、禁 collab、禁 V2，把 approval 固定为 Never，再套 review rubric。这样 review 只能读代码、给结论，不能自己再开 Agent 或联网。

05取舍：并行收益，协调成本

多 Agent 能把「查资料、改代码、跑测试」并行；代价是 token 成本翻倍、消息顺序难保证、子 Agent 可能互相踩文件，还要处理超时、回收与权限继承。V1 与 V2 的默认值不同，也说明这不是一个已经稳定的产品面。

换来什么任务可并行、review 可隔离、长任务可拆给不同角色。
付出什么并发与成本上升；消息与文件冲突需要额外协调；V1/V2 两套语义增加理解成本。
