第 08 章 · 协议层为什么值得单独存在

产品表面：thread / turn / item 比 UI 更长寿

如果只有 CLI，UI 与运行时可以糊在一起。但 Codex 还要服务 TUI、exec、桌面、移动与 SDK，于是把会话抽象成 thread / turn / item，用 JSON-RPC 暴露成 app-server。协议层让多端共享运行时，也把「兼容」变成长期成本。

30 秒版

  1. app-server 协议有 186 个请求方法，其中 74 个是 variant 级 experimental；实验面很大。
  2. TUI / exec 用 in-process 客户端；桌面 / 移动通过 daemon；TS SDK 走 CLI JSONL，Python SDK 走 app-server。
  3. 协议把多端复用变成现实，也把「方法稳定性、能力协商、daemon 生命周期」变成新产品面。
用户问题为什么不能让每个表面直接调 core，而要单独维护一个 app-server？
本副本可证的新增面

在本副本里，app-server 是 TUI、exec、桌面、移动与 SDK 的共同协议层；这是 039 材料里没有展开的新增面，但不代表其他产品没有类似层。

01协议面：186 个请求，74 个 experimental

协议定义不是几个枚举，而是一整张请求表。静态计数得到 186 个请求方法，其中 74 个带 variant 级 experimental 标记。这个比例说明：它既要支撑稳定客户端，也承载大量仍在演进的会话能力。

方法多不是优点本身；它意味着客户端必须做能力协商，文档也要区分稳定与实验。

02thread / turn：会话不是一条日志

协议把会话拆成 thread、turn、item。turn 有明确的完成 / 中断 / 失败 / 进行中状态；客户端可以订阅事件，也可以按 thread 历史回读。这样 UI 不必理解 core 的内部状态，只需要消费协议对象。

codex-rs/app-server-protocol/src/protocol/v2/turn.rs34-41 · turn 的四种状态
pub enum TurnStatus {
    Completed,
    Interrupted,
    Failed,
    InProgress,
}
对象回答什么客户端怎么用
thread一段可持续的会话列表、恢复、归档、分裂
turn一次用户输入触发的执行订阅事件、取消、读 usage
item消息 / 工具调用 / 文件变更渲染时间线、定位审批

03连接方式：in-process、daemon、SDK 不是同一条路

TUI 与 exec 用 in-process app-server 客户端，省掉进程边界；桌面 / 移动通过 daemon 连远程 app-server；TypeScript SDK 拉起 CLI 交换 JSONL，Python SDK 则直接跑 app-server。把它们都说成「走同一个协议」会掩盖传输差异。

04取舍：协议复用，还是表面各自为政

协议层让多端共享 thread / turn / item，也让「会话恢复、审批、usage、文件变更」有一套共同语义；代价是协议要长期兼容，experimental 方法要协商，daemon 还要处理升级、重启与远程控制。

换来什么多端共享运行时与事件模型；新增表面不必重写 core 集成。
付出什么协议兼容成本高；实验方法多；daemon 生命周期成为新的故障面。
不要把「有 app-server」写成「所有端都走远程进程」。in-process、daemon、CLI JSONL、SDK 封装是四种不同传输。
