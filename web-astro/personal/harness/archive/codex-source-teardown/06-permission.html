第 06 章 · 权限是一套组合，不是一个弹窗

权限与安全：approval、sandbox、execpolicy、network 的组合

「能不能跑这条命令」不是一个 yes/no。Codex 把它拆成四层：approval 决定谁批、sandbox 决定能碰什么、execpolicy 决定规则、network proxy 决定能连哪。再往上还有 Guardian 自动审查与「不可信上下文」处理。产品判断是：权限要可组合、可审计，而不是把风险都推给一个确认弹窗。

30 秒版

  1. approval 有 untrusted / on-request / granular / never 四种；granular 还能细分 sandbox、rules、skill、permissions、MCP。
  2. sandbox policy 有 danger-full-access / read-only / external-sandbox / workspace-write；后端按平台选 Seatbelt、Seccomp、Windows 受限令牌或 MXC。
  3. execpolicy 给出 allow / prompt / prompt-user / forbidden；网络另有本地代理；Guardian 只有显式选 auto_review 才接管。
用户问题怎样让 Agent 能干活，又不越过文件、命令与网络边界？
实现差异

Codex 把权限拆成 approval、sandbox、execpolicy、network 与 reviewer 五个可组合面；任何一层都不能单独代表「安全」。

01approval：谁来决定

approval 不是「开 / 关」，而是四种策略。默认是 on-request，让模型在需要时请求；granular 把请求再拆成 sandbox 升级、规则、skill、request_permissions、MCP elicitation 五类，可以逐类允许或自动拒绝。

模式行为产品含义
untrusted除非规则显式允许，否则要批项目未受信；公开配置已不再支持该值
on-request模型决定何时请求默认策略
granular按类别细控适合托管 / 企业策略
never从不询问，失败直接回模型无人值守；风险最高

02sandbox policy：能碰什么

approval 决定「要不要问」，sandbox policy 决定「问了之后能做什么」。四种 policy 从完全放开到只读，再到只写 workspace；workspace-write 还会把 .git、.codex 等可提权的路径列为只读子路径。

codex-rs/protocol/src/protocol.rs1254-1266 · policy 从无限制到只读
pub enum SandboxPolicy {
    /// No restrictions whatsoever. Use with caution.
    #[serde(rename = "danger-full-access")]
    DangerFullAccess,

    /// Read-only access configuration.
    #[serde(rename = "read-only")]
    ReadOnly {
        /// When set to `true`, outbound network access is allowed. `false` by
        /// default.
        #[serde(default, skip_serializing_if = "std::ops::Not::not")]
        network_access: bool,
    },

同一份 WritableRoot 还带 read_only_subpaths 与 protected_metadata_names，用来防止 Agent 通过改 .git/hooks 或配置文件给自己提权。

03后端：同一 policy，不同 OS 实现

policy 是产品语言，后端是平台实现。macOS 用 Seatbelt，Linux 用 Seccomp / Landlock / bwrap 组合，Windows 用受限令牌或 MXC。没有对应后端时可能退化为 None，所以「有 sandbox policy」不等于「一定在沙箱里跑」。

04execpolicy：规则先于弹窗

规则文件把「哪些命令前缀可以跑」写成 allow / prompt / prompt-user / forbidden。它解决的是重复审批：同一类命令被允许后，不必每次再问；但 prompt-user 仍要求一次全新的人类决定，不能被自动审查或缓存替代。

codex-rs/execpolicy/src/decision.rs9-21 · 规则四种决策
pub enum Decision {
    /// Command may run without further approval.
    Allow,
    /// Request approval from the configured reviewer; rejected with `approval_policy="never"`.
    Prompt,
    /// Requires a fresh human decision, independent of the configured reviewer.
    #[serde(rename = "prompt-user")]
    PromptUser,
    /// Command is blocked without further consideration.
    Forbidden,
}

05network：本地代理也是一层权限

网络访问不是「sandbox 开了就随便连」。Codex 有本地 HTTP / SOCKS5 代理，按 allow / deny 名单与 limited 模式工作；默认监听 127.0.0.1:3128 与 127.0.0.1:8081。

codex-rs/network-proxy/README.md1-10 · 代理与默认端口
# codex-network-proxy

`codex-network-proxy` is Codex's local network policy enforcement proxy. It runs:

- an HTTP proxy (default `127.0.0.1:3128`)
- a SOCKS5 proxy (default `127.0.0.1:8081`, enabled by default)

On Windows, managed HTTP listeners prefer ports `3128-3159`, and SOCKS5 listeners prefer ports
`8081-8112`. An explicitly configured port is attempted first. If every preferred port is occupied,
the proxy preserves its existing ephemeral loopback fallback.

06Guardian：自动审查是 opt-in

Guardian 不是默认接管所有审批。路由函数要求 policy 是 on-request 或 granular，并且 reviewer 是 AutoReview；reviewer 默认是 user。所以「代码里有 Guardian」不等于「线上默认自动审查」。

codex-rs/ext/guardian-reviewer/src/routing.rs59-67 · 只有 auto_review 才路由
pub fn routes_approval_policy_to_guardian(
    policy: AskForApproval,
    reviewer: ApprovalsReviewer,
) -> bool {
    matches!(
        policy,
        AskForApproval::OnRequest | AskForApproval::Granular(_)
    ) && reviewer == ApprovalsReviewer::AutoReview
}
Guardian 的 feature 默认开启，但 reviewer 默认 user；这两个默认值不矛盾，一个是能力，一个是路由选择。

08取舍：可组合，但配置与平台差异大

五层组合能让企业做细粒度策略，也能让个人用户按项目放宽；代价是同一句「允许」在不同平台、不同 approval、不同 network 配置下含义不同。产品文档必须把「谁批、能碰什么、能连哪」分开写。

换来什么权限可审计、可逐类收紧；规则能减少重复审批；网络与文件边界分开治理。
付出什么组合多、默认值多；平台后端不一致；用户很难从一句「已允许」推断实际边界。
