单 Agent 循环什么时候把子 Agent 折回主循环

Anthropic 应用 AI 团队在 2026-10 给出一条反直觉建议：很多企业 Agent 并不需要一屋子专家子 Agent。一个主循环，加上按需加载的 skills 与 tools，常常质量更好、成本更低、延迟更短。但子 Agent 没有过时——它有且只有三个保留条件。本文把这份指南拆成可判断的信号、可执行的迁移和可验证的评测。

先统一七个词：主循环、子 Agent、渐进披露、skill、tool search、handoff、翻转
主循环
一个模型、一个上下文窗口，反复“发工具调用 → 收结果 → 决定下一步”，直到回答或触预算。
子 Agent
拥有独立上下文、工具与指令，由编排者调用的 Agent；它可以并行、隔离上下文，也可以拥有独立权限。
渐进披露
先只把名称与描述放进上下文，真正需要时才加载完整说明、参考文件或工具定义。
Skill
把团队流程、规则与判断写成可按需加载的文件；它不是一段更长的系统提示词。
Tool search
把大量工具定义移出上下文，模型按需搜索并只加载当前要用的几个工具。
Handoff
把对话或任务交给另一个 Agent。每次交接都可能丢状态，并增加一次嵌套模型循环。
翻转
同一道 eval 题在改动前通过、改动后失败，或反之。总分不变时，翻转仍可能发生。

01

30 秒结论

如果只记一段话：先把子 Agent 当成本，而不是能力。能用 skills 与 tools 在同一个上下文里解决的，不要新开一个上下文；只有当子 Agent 解决了单循环解决不了的问题，它才值得保留。

一句话

默认单循环，按需加载；子 Agent 是例外，不是默认架构。 Anthropic 在多个企业部署的对比中观察到：一个主循环加 skills，质量常高于“一个大提示词”和“按域拆子 Agent”，成本与延迟往往更低。[1]

证据类型：Anthropic 的企业部署观察与官方文档、Cognition 的反方原则、MAST 的论文分类。第 10 节逐条写清能支持与不能支持什么；不要把厂商数字当行业基准。

01 / DEFAULT

默认单循环

一个模型、一个上下文、开放式工具循环。不是把系统提示词写得更长，而是把顺序与领域流程移进 skills，把硬约束移进 tools，把预算与审批留在 harness。[1]

02 / EXCEPTION

三个条件才保留

单循环因上下文膨胀出现可测退化；任务真并行且上下文可丢弃；单 Agent 难以选工具或提示词有冲突指令。三条都不满足，先折。[1][4]

03 / DISPOSITION

四种处置，不是二选一

合并、折叠为 skill + tools、保留但作为工具调用、保留独立 Agent 接管对话。判错处置，比“多一个或少一个 Agent”更常见。

04 / MIGRATION

一次只改一件事

先审计，再建基线；先合并总是一起跑的，再折高频的；每折一个都跑同一套 eval。一次折三个，出问题不知道是谁。[2]

05 / EVAL

总分不够

同一套 10 题，基线 8/10、折叠后 8/10，仍可能有 3 题翻转。看逐题、看链路覆盖、跑 2–3 次，才知道改动有没有碰坏规则。

06 / READING

怎么读这一页

赶时间：做一次决策器，再看四个场景。要动手：读六步迁移与推演。要说服人：读成本账、评测与反方边界。

站内延伸：Anthropic 工作流程转变、Harness 上岗、Claude Code 产品设计 分别讲组织流程、岗位落地与产品拆解；本页讲架构决策。

02

问题不是 Agent 太少，是边界画错

企业想要一个统一入口，各团队拥有自己的能力，于是架构自然长成“每个团队一个子 Agent，再加一个编排器”。这看起来最省事，实际是把组织协调成本复制进了模型调用链。

Anthropic 文章描述的典型路径是：每个能力由不同团队拥有，各队先建自己的 Agent，中央平台团队再在上面加 orchestrator；或者把子 Agent 包装成 MCP 工具暴露给主 Agent。它立刻带来五个问题。[1]

上下文管理

要决定哪些上下文在 Agent 之间交换；来回几次，细节就丢了。每次 handoff 都是一次有损操作。[1][5]

子 Agent 蔓延

每个团队都发自己的子 Agent，最后出现数百个重叠能力，没有强制标准，也没有明确 owner。[1]

Frankenprompt

每个团队往系统提示词加一句，规则互相冲突，品牌语气无法统一。提示词成了跨团队谈判的产物。

局部 eval

每队只优化自己的子任务，分数很漂亮；没人维护端到端集合，管理层拿到的是一组被稀释的局部分数。[1]

延迟

多 Agent 的架构复杂度会加延迟。一个客户把多 Agent harness 与单循环对比，后者运行时约快 2 倍。[1]

谁在承担判断

很多结构是在模型能力不足时替模型做判断。模型变强后，固定流水线、用户分桶、独立推荐分支往往变成冗余。

Conway 定律

1968 年，Melvin Conway 观察到：设计系统的组织，受限于产出“组织沟通结构的复制品”。[13] 当 Agent 架构按团队切分，你得到的是组织图，不是任务图。原文把这种现象直接称为“Conway 定律在起作用”。[1]

站内延伸：第 10 章 · 多 Agent 协作 讲角色分工、消息与上下文边界；这一页补的是“什么时候不该拆、拆了怎么验”。

两个真实症状

一家公司的客服 Agent 里有十几个专家子 Agent，结果品牌语气很难保持一致，延迟也伤害了体验。另一类常见提案是“意图分类器 + 固定多步推理流水线 + 用户分群 + 独立推荐分支 + 多 Agent 编排”；Anthropic 的反馈是：其中大部分结构在做模型已经不需要做的工作，一个清晰的系统提示词、4–5 个薄数据工具和硬的输出护栏，就能覆盖多数场景。[1]

但不要读反

这不是说“结构越多越糟”。在模型能力不足、任务必须隔离、权限必须分域时，结构是必要的。原文的主张是：先把结构当成假设，用 eval 验证它是否还在创造价值；不是无条件拆除。

03

三个条件，决定子 Agent 是否还有必要

原文只给了三个保留条件。把它们翻译成可测信号，再做一个六问决策器；答案不是“永远单循环”，而是“这次该用哪种处置”。

CONDITION A

上下文膨胀，且可测退化

单循环在长任务后质量下降；某个子任务会产生 1,000 token 以上、且大部分与主任务无关的内容，需要先过滤再使用。[1][4]

  • 信号：同一任务，加入该子任务后主任务分数下降。
  • 反例：只是对话变长，压缩、记忆或更好的检索就能解决。
CONDITION B

真并行，且上下文可丢弃

多个方向可以同时探索，各自用一份干净上下文，结果压缩后交回；研究工作是最典型的例子。[1][3]

  • 信号：拆成 3–5 个独立分支后，覆盖明显变广，且分支之间不需要共享状态。
  • 反例：分支要共享购物车、工单、订单或用户偏好，交接会丢状态。
CONDITION C

工具选择困难，或指令冲突

工具超过 30–50 个后选择准确率下降；系统提示词里同时要求“同理心客服”和“严格合规”，模型难以稳定切换。[1][8]

  • 信号：加工具后旧任务变差；错误集中在“选错域”。
  • 反例：只是工具描述写不清，先改描述与 skill，不必拆 Agent。

四种处置：合并、折叠、作为工具、保留

“折回主循环”不是唯一动作。原文与配套迁移套件把判决分成四类；判错处置比“多一个或少一个 Agent”更常见。[1][2]

合并 · Merge

两个子 Agent 总是一起跑、共享同一份数据、前后依赖强，合成一个领域 Agent。

先合并，再谈折叠；从流量最高的一对开始。

折叠 · Fold

流程、规则、判断已知，且需要主循环里的完整上下文；提示词变 skill，API 调用变 tools。

默认处置；一次折一个，跑同一套 eval。

作为工具 · As tool

任务独立、可并行、需要新鲜上下文，但仍要保持与用户的同一段对话；子 Agent 作为工具返回结构化结果。

保留独立上下文，但把“对话所有权”留在主循环。

保留 · Keep / handoff

需要直接面对用户，或拥有独立权限、合规边界；让子 Agent 接管对话，直到任务完成。

只有在它必须成为用户对话对象时才用。

六问决策器

点“是/否”，即时给判决；不是替你做决定，而是把依据摆出来。

子 Agent 是否需要直接面对用户，或有独立合规/权限边界？例如持牌顾问、独立审核方、必须由另一实体承担责任的流程。

是否有多个子 Agent 总是一起跑、前后依赖强？例如订单查询与物流查询总在同一轮出现，共享同一份订单数据。

子任务是否共享同一段对话状态？例如购物车、工单、订单、用户偏好、已说过的约束。

子任务能否彼此独立并行，结果用一次就丢？例如多条互不依赖的检索、批量核查、独立验证。

单循环是否已经出现可测的上下文膨胀退化？同一任务在长对话后分数下降，而不是“感觉有点长”。

主 Agent 是否明显选错工具，或提示词里有冲突指令？例如同时要求“先安抚”与“直接拒绝”，或工具超过 30–50 个。

建议：折叠

先把提示词变成 skill，把 API 变成 tools

当前六个回答都指向“没有必须保留子 Agent 的理由”。先在主循环里做渐进披露，再决定是否需要隔离上下文。

  • 没有共享状态、并行、膨胀、冲突、接管或共现信号。
  • 默认单循环，用 eval 验证；不要一次折三个。
下一步：写 10 条端到端 golden tasks，先把其中一个子 Agent 折成 skill + tools；跑 3 次对比，再决定下一个。

这是基于六问的启发式，不是自动决策。真实系统还要看流量、合规、组织所有权与单位任务经济性。

04

目标不是一个更大的提示词，而是一个更干净的主循环

原文给的目标结构很克制：一个模型、一个上下文、开放式工具循环；计划写在上下文里，执行者就是计划者；顺序与领域流程进 skills，硬约束进 tools，预算与闸门留在 harness。

这六个部件里，最容易被误解的是“计划”。它不是编排器写一份计划再交给执行者，而是写计划的模型自己执行，所以可以在中途改计划。[1]

计划写进上下文

第一轮就让模型写下目标、约束、已知信息与下一步。之后每次工具结果回来，它都可以改计划；不需要一个外部的“计划器”再同步一次。

为什么计划者与执行者是同一个模型，才不会出现“计划在 orchestrator、执行在子 Agent”的信息断层。 失败模式把计划留在编排器里，执行者只收到一句任务描述；或者计划写成不能改的固定流水线。
多 Agent 编排与单循环的结构差异
维度多 Agent 编排单循环 + 渐进披露
计划者与执行者编排器计划，子 Agent 执行同一个模型，边做边改
领域流程写在各子 Agent 的提示词里写进 skills，按需加载
硬约束放在编排器或各子 Agent放在 tools 与 harness 的闸门
上下文按 Agent 切开，靠摘要交接一个窗口，靠渐进披露控制体积
交接每次 handoff 都可能丢细节没有 handoff；只有工具结果回填
成本复制上下文 + 嵌套循环一份上下文 + 元数据 + 按需加载

history = [task, plan]

for turn in range(MAX_TURNS):

    if not calls:

    results = run_parallel(calls)      # 原样回填，不先总结
    history += results
    if budget.exceeded(history):

answer = model.answer(history)
if verifier and not verifier.check(answer):
    answer = model.revise(history, verifier.reason)

Skill 的渐进披露通常分三层：元数据（名称与描述）、正文（SKILL.md）、参考文件与脚本；参考文件只在读取时进上下文，脚本只把输出放进上下文。早期技能文章给的是约 50 token 元数据，当前文档约 100 token，属于版本差异，不影响“按需加载”的结论。[6][7]

上下文为什么会膨胀、压缩与隔离的边界在哪里，见 第 2 章 · 上下文工程。

关键差别

原文特别指出：用代码重写计划的那一步不再需要，因为每一步由模型决定；顺序与领域 procedure 进 skills；硬限制（校验、审批）与对话中才出现的东西（记忆查询）进 tools；代码仍可做便宜且几乎总相关的加载（例如实体解析），以及工具内部的机械活（拼 payload、解析流、恢复澄清）。[1] 预算与闸门同理：任务预算可以是建议性的倒计时，硬上限仍是 max_tokens；写操作审批与危险工具拒绝必须是确定性的。[9]

05

三笔账：token、延迟与交接损失

多 Agent 的主要优势是“用更多 token 换更全面”，不是免费并行。先把三个最容易混用的数字对齐基线，再决定这笔钱花得值不值。

TOKEN / CHAT

15× 与 4×

Anthropic Research 的生产数据：Agent 约为普通聊天的 4 倍 token，多 Agent 约为 15 倍。[3]

基线是“一次普通聊天”，不是“单 Agent 完成同一任务”。

TOKEN / SINGLE AGENT

3–10×

另一篇官方指南的口径：多 Agent 完成等效任务，通常比单 Agent 多 3–10 倍 token，来自上下文复制、协调消息与交接摘要。[4]

与 15× 不是同一基线；两个数字可以同时为真。

LATENCY / SINGLE CASE

约 2×

一个客户把多 Agent harness 与单循环对比，后者运行时约快 2 倍。[1]

单案例、客户自评，不是受控实验；只能说明方向。

三个常见误读

90.2% 不是准确率，也不是速度。 它是 Anthropic 内部研究 eval 上，多 Agent 相对单 Agent Opus 4 的提升。[3]
15× 不是延迟。 它是 token；多 Agent 往往更全面，但总计算量更大，整体耗时可能更长。[4]
3–10× 与 15× 不能直接比较。 一个对单 Agent 等效任务，一个对普通聊天；写方案时要先写清基线。

成本不只在 token 单价

同一任务下，两种架构的成本项对照
成本项多 Agent 编排单循环 + 渐进披露备注
上下文复制每个子 Agent 一份一份 + skill/tool 元数据最容易被忽略的固定成本

延迟：少一层，不等于一定更快

任务完成延迟大致是“每轮 time-to-last-token + 工具处理”的总和。多 Agent 多一层嵌套循环、多几次序列化与等待；单循环少一层，但如果工具选错、轮次变多，也可能更慢。原文的建议是先把端到端延迟拆成轮次、工具、token 三段，再决定砍哪一段；先看 p50/p95，不要只看平均。[1]

产品判断

如果任务是“用户等着看结果”的强交互场景，延迟就是转化率；如果任务是“后台跑几分钟也无所谓”的研究，token 成本与覆盖度更重要。同一个架构选择，在两个场景里可能相反。

06

六步迁移：先量，再合并，再折，一次一个

配套的 single-agent-loop-kit 把迁移写成“measure → combine → fold”，并强调每一步都用同一套 eval 打分。[2] 下面是把它落成六步的版本。

00 · 审计：先给每个子 Agent 一个判决

读编排代码与生产 trace，列出每个子 Agent 的调用链、流量、owner 与失败模式；给每个判决：合并、折叠、作为工具、保留。不要只看代码结构，要看它实际被谁调用、和谁总是一起跑。

输入子 Agent 清单、调用链、最近 30 天流量、每个能力的 owner。 退出条件每个子 Agent 都有一个判决与一句理由；高风险项有复核人。 常见错误按团队边界而不是调用链判决；把“没人维护”误判成“可以删”。
提示：套件会在审计后、付费运行前、基线后、每次改动后停下来，让你确认再继续。[2]

最重要的回归案例

Anthropic 在样本客服 Agent 上折了一个子 Agent，延迟降了，但一个原本通过的流程坏了：主 Agent 手里有订单查询工具，就自己回答了配送日期，没有去问物流专家。这个回归在两次运行里只出现一次。[1] 所以：每个生产链路至少一条 eval，每条不能破的规则至少一条 eval，每道题跑多次。

配套工具怎么用

single-agent-loop-kit 是 Apache-2.0 的参考实现，官方明确“不维护、不接受贡献”。它先审计、再基线、再合并/折叠/作为工具，每次改动都跑同一套 eval；支持离线 smoke（19 题，无需 API key），并在付费运行前给出 token 估算。把它当检查清单，不要当自动迁移。[2]

07

四个场景的答案：折、折、不折、作为工具

同样是“多 Agent”，四个场景的答案不同。关键不是行业，而是：对话是否共享、子任务是否真并行、失败是否必须由独立上下文来发现。

CASE 01 · 客服中台

折叠：共享工单与订单，交接最伤

起始架构：12 个专家子 Agent，按售前、订单、物流、退款、会员等拆分。

判断：同一通对话里频繁跨域；用户说“这个订单能退吗，什么时候到”，一次就要跨订单、退款、物流三个 Agent。每次交接都丢上下文，品牌语气也难统一。[1][5]

处置：折成一个主循环；退款政策、配送时效、会员权益变成 skills；订单、物流、退款 API 变成 tools；高风险退款保留写闸门。

看什么：一次解决率、品牌语气一致率、p95 延迟、配送时效规则覆盖。

反例：把退款政策折进提示词，却不给退款工具，模型就开始猜日期。

CASE 02 · 电商导购

折叠：购物车是一段连续会话

起始架构：搜索、比较、推荐、退货、促销各一个 Agent，外加 orchestrator。

判断：购物车、偏好、已看过的商品、退货状态都共享；按品类或意图拆 Agent，用户每换一个问题就像换了一个人。Anthropic 的电商指南直接写：这类会话是“一段紧密耦合的跨意图会话”，应优先 skills 而不是子 Agent。[5]

处置：一个主循环持有购物车与偏好；搜索/排序、库存、促销、退货作为 tools；导购话术与品类知识作为 skills。

看什么：加购率、任务完成率、跨品类切换后的上下文保持、延迟。

反例：按品类拆 8 个 Agent，用户从“旅行箱”问到“登机规则”就换 Agent，前面选的型号丢了。

CASE 03 · 深度研究

不折：广度优先，子 Agent 仍然赢

起始架构：lead agent 拆问题，3–5 个研究子 Agent 并行搜索，各自压缩后交回。

判断：这是原文明确保留的场景：任务需要并行、每个分支要一份干净上下文、结果可以丢弃。Anthropic Research 的内部 eval 上，多 Agent 相对单 Agent Opus 4 提升 90.2%，代价是约 15 倍 token。[1][3]

处置：保留并行子 Agent；主循环负责拆题、验收与最终综合；子 Agent 以工具形式返回带出处的要点，不接管对话。

看什么：覆盖度、来源质量、单位任务成本、p95 延迟；不要用“单 Agent 更便宜”一刀切。

反例：为了省 token 折成单循环，结果只查了三个来源就收尾，覆盖面明显变窄。

CASE 04 · 代码评审

作为工具：独立审查需要新鲜上下文

起始架构：主 Agent 写代码，审查 Agent 在独立上下文里读 diff 与测试，给出问题清单。

判断：审查的价值来自“没有写过这段代码”的独立视角；把审查折进主循环，主 Agent 容易为自己的实现辩护。Cognition 也把“子 Agent 只回答一个明确问题、不并行写代码”作为 Claude Code 的克制做法。[11]

处置：保留审查 Agent，但作为工具调用：输入 diff、测试结果与验收标准，输出结构化问题清单；主 Agent 负责核实与修改，审查 Agent 不直接写代码。

看什么：缺陷检出率、误报率、审查延迟、修复后回归率。

反例：让审查 Agent 接管对话并直接改代码，责任边界消失，主 Agent 也不再核实。

不要当模板

四个案例给的是判断方法，不是行业模板。同一个客服系统，如果退款必须由持牌机构处理，退款就可能应该“保留/接管”；同一个研究系统，如果问题很窄、来源很少，单循环也可能更划算。

08

评测：总分一样，系统可能已经换了一个

原文建议的 eval 结构不复杂：一个中央团队拥有的共享端到端集，加上每个 skill 自带的小集；哪怕只有 10 条 golden examples 也可以开始。难的是克制——不要只看一个总分。

有 orchestrator 时，除了最终质量，还要看 routing accuracy（有没有选对子 Agent）。折叠之后，改看 skill/tool selection（有没有加载对的 skill、调对的工具），最终仍看 task completion。[1]

LAYER 1

端到端任务

少而全，覆盖用户真正会提的任务；由中央团队拥有，跨团队共用。

LAYER 2

链路覆盖

生产里每条会一起跑的 Agent 链，至少一条 eval；折叠后链路变短，也要防止漏掉中间步骤。

LAYER 3

Skill 小集

每个 skill 由所属团队带自己的小集；上线前跑，改动后跑。

LAYER 4

规则回归

每条“绝不能破”的规则单独一题；例如“报价必须来自承运商”“退款必须二次确认”。

Rubric 写法

把“通过/失败”写成三档，比二元更能抓边界。例如配送时效题：通过 = 给出日期且注明承运商与查询时间；不确定 = 只给区间但未说明来源；失败 = 未查配送或编造日期。评分理由要能回放到具体工具结果。

原文还提到一个很实用的内部做法：给重要事件打时间戳，之后回放成定向 eval；对于内部系统难以回放、用户参与难以模拟的环境，这比“造一个完美沙盒”更可行。[1] MAST 的研究也说明，多 Agent 的失败大量集中在系统设计、Agent 间错位与任务验证，而不是单点模型能力；这正好对应上面的三层 eval。[12]

如果每个团队继续拥有自己的子 Agent，折叠不会减少协调成本，只会把冲突搬进主循环。原文的建议是：中央小团队拥有系统提示词与端到端质量，领域团队把 ownership 从 Agent 转到 skill/tool，并对自己那部分 eval 负责。

四种反模式

  • 一个团队一个子 Agent：架构复制组织图，交接成本变成固定税。
  • 每个团队往系统提示词加一句：Frankenprompt，规则冲突、语气不一致。
  • 只维护局部 eval：每队分数都高，端到端没人负责。
  • skill 无 owner：skill sprawl 取代 subagent sprawl，只是换了一个文件夹。

让能力继续属于领域团队

折叠不是把权力收归中央，而是把“能力”从 Agent 变成可组合的 skill/tool：领域团队继续拥有知识与规则，中央团队拥有端到端结果与准入。[1][5]

原文提到的两个工具：/skill-creator 用来起草与审计 skill，/skill-doctor 用来看每个 skill 的成本与使用频率、删掉死重量。[1] 这比“再建一个 Agent 评审委员会”更可持续。

Conway 定律的第二次提醒

如果你保留 12 个子 Agent，是因为你有 12 个团队，而不是因为任务需要 12 份独立上下文，那你只是把组织图写进了模型调用链。折叠的真正难点不是代码，是让团队接受“能力还在，只是换了一个交付形态”。[13]

10

反方、证据与这条建议的边界

这不是一篇“多 Agent 已死”的文章。原文自己保留了研究前沿的子 Agent；Cognition 从另一条路径反对天真的多 Agent；MAST 则用失败分类说明“加 Agent”不能替代契约与验证。

COUNTERPOINT

Cognition：先共享完整轨迹

多 Agent 的根本风险是上下文不共享；动作携带隐含决策，两个子 Agent 的冲突假设会在合并时爆炸。除非能共享完整轨迹，否则默认排除这类架构；单线程线性 Agent 更可靠。[11]

它反对的是“天真并行”，不是所有上下文隔离；超长任务仍需要压缩历史。

EVIDENCE

MAST：失败常不在模型

1600+ 条轨迹、7 个框架、14 种失败模式，聚成三类：系统设计、Agent 间错位、任务验证；150 条人工标注，κ=0.88。[12]

这说明“多 Agent 更强”不是默认结论；失败往往来自契约、验证与协调设计。

研究前沿仍然需要多 Agent

Anthropic Research 在广度优先任务上用 3–5 个并行子 Agent，内部 eval 相对单 Agent 提升 90.2%，代价是约 15 倍 token；复杂查询研究时间最多缩短 90%。[3]

三个必须写进方案的限定

厂商证据的限制

原文没有公布企业案例名称、样本量、任务分布与评分 rubric；2 倍是单客户，90.2% 是内部 eval。它们能支持“值得试”，不能支持“必然更好”。

模型会移动边界

从 Opus 4.5 开始，模型能在单循环里管理更多；Opus 5.5 又把 Fable 5.1 级能力带到更低成本。[14] 今天的折叠结论，下一代模型可能反转；每次升级重跑同一套 eval。[10]

先简单，后复杂

Anthropic 更早的总体建议仍是：先用简单方案，简单方案不够再加多步系统。[16] 上下文是有限资源，压缩、隔离与检索都要有边界。[17]

不要把这篇读成

“子 Agent 无用”——研究、独立验证、权限隔离仍然需要它。
“单循环一定便宜”——如果工具选错、轮次变多，单循环也可能更贵。
“所有团队都该合并”——合规边界、对话所有权不能为了架构整洁而拆。
“提示词越短越好”——删的是过时的约束，不是删掉必要的安全与业务规则。

第三方分析也给出类似提醒：多 Agent 的收益主要集中在“读/研究”这类可并行的信息工作；多个 Agent 同时写代码或写内容时，冲突决策会产生难以合并的产物。[15]

行动清单：从明天能做的开始

不要从“画一张新架构图”开始，从“把今天的系统量出来”开始。下面八项可以在一到两周内完成第一轮。

进度
0/8
给管理层的一页纸

现状：我们有 N 个子 Agent，其中 M 个在生产里总是一起跑；端到端 eval 只有 K 条。
判断：先合并 M 个中最常用的两个，再折一个高频子 Agent；预期减少交接与上下文复制，风险是规则回归。
验收：同一套 eval 跑 3 次，质量不降、规则覆盖不降、p95 延迟下降；任何翻转题都要有解释。
所有权：中央团队拥有 prompt 与端到端分数；领域团队拥有 skill/tool 与局部 eval。
