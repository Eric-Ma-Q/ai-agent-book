01

从原业务切入，保留你的资历

优先寻找“你的原场景正在 Agent 化”的岗位；资历匹配要同时看产品年限、行业经验和 AI 实践要求。

推荐定位：「[原领域]产品经理，聚焦 [具体业务任务] 的 AI Agent 应用」。
简历中完整保留真实工作履历，把新的 Agent 实践作为独立项目呈现。没有正式 AI 工作经验，是一个需要补证据的缺口；原有产品经验仍然是可用的资产。
FIRST / 主投

同场景的 AI 应用岗

原来做客服、CRM、ERP、内容、增长，就优先看对应的业务 Agent。你对流程、用户和指标的理解可以直接进入面试讨论。M1

NEXT / 次投

业务落地与工作流岗

重视需求拆解、方案设计、跨团队交付的岗位。完整读 JD，确认是否接受产品经验迁移、是否有 AI 年限硬要求。J1

SELECT / 选择性投递

平台、策略、评测岗

需要更强的系统设计、评测方法或长期 Agent 实战证据。若明确要求相关工作年限，作品不能直接等价替代。J4 J5

按已有经验，选择第一条转岗叙事

以下是基于样本的建议，不是市场录用概率排序。选择最接近你真实经历的一项。

把复杂流程，变成可交付的业务 Agent

优先查找企业知识助手、客服工单、销售助理、财务审核、内部效率工具。搜索时保留原场景词，再加“AI / 智能体 / Agent”。

简历首页强调复杂流程梳理、角色权限、规则设计、系统集成、跨团队上线、效率与质量指标。代表项目可做“客服工单处理 Agent”。

把增长判断，带进内容与营销 Agent

优先查找广告素材、营销内容、用户运营、导购与推荐助手。游戏广告 Agent 社招样本直接体现了行业经验的价值。M1

简历首页强调用户分层、素材评判、实验设计、转化漏斗和归因。代表项目可做“素材 brief → 脚本方案 → 质检 → 人工发布”的工作流。

让行业约束，成为项目的深度

优先查找你熟悉的金融、汽车、制造、教育等领域的 AI 应用岗位。先核对该岗位是否真的需要你的业务经验。

简历首页强调特定用户、异常分支、风险等级、业务规则、验收口径。作品选择行业内一个窄任务，展示哪些动作需要人来确认。

把平台经验，转成 Agent 的使用与评估体验

优先查找Agent 工作台、工具接入、评测平台、知识库管理。平台类岗位差异大，重点核对是否要求模型或开发者工具从业经历。

简历首页强调API 接入、配置管理、数据质量、可观测性、平台活跃与任务完成情况。作品须展示真实运行记录，支撑“懂平台”的判断。

职级策略：按你已有的产品资历找相邻岗位；是否接受降级或薪资调整，需要结合具体机会判断。没有证据支持“转 AI 必须从实习做起”或“必然涨薪”。

拿到一份具体 JD，按这四步决定是否投

先圈出不能由关键词补齐的门槛

产品 / AI 年限、行业、学历、城市、职责级别。“优先”与“必须”分开读；若摘要缺信息，回完整岗位或向招聘方核实。

提取三个最核心的交付任务

例如“搭建客服 Agent—评估解决率—接入现有工单系统”。抽取真实业务动词，有助于判断你的经历是否对应。

每个任务找一条已完成的证据

对应原工作项目，或独立 Agent 项目。只有课程和概念时，标记为证据缺口，不把 JD 原句抄到技能栏。

调整首页排序，保留一致的事实

同一份经历，可以按场景、平台或增长价值调整重点。公司、任职时间、职责和数据在所有版本中保持一致。

04

包装的重点：重新组织事实

让招聘方快速看懂你有何资历、与岗位哪里匹配、Agent 实践进行到哪一步。以下是写法示范，尚不是你的个人简历。

TOP THIRD / 首页上部

前几屏必须看见的东西

  1. 求职方向：产品经理｜[场景] AI Agent 方向。
  2. 三行摘要：真实产品资历、代表成果、Agent 实践阶段。
  3. 一处作品入口：演示 + 两页案例 + 评测摘要。
  4. 最相关工作经历：展示你已完成过业务交付。

建议控制为 1–2 页、单栏可选中文字的 PDF。复杂资历可适当延长。作品集外链用于补充，不让关键事实藏在链接后。

EVIDENCE / 两种经历

工作经历与 Agent 项目分别写

工作经历：保留正式公司、岗位和时间，写你真实负责过的产品。

Agent 实践：标注“个人独立项目 / 内部试点 / 正式上线”及实际时间范围。使用低代码或 AI 辅助开发可以如实说明，并写清你负责的产品判断。

没有内部授权与实际使用，就不能标“内部试点”；没有上线、用户和经营数据，就写离线评测或用户测试。

三组改写：从职责描述，变成可追问的成果

原句：负责 CRM 产品需求分析，输出 PRD，推动研发上线。

改写示例：面向 [销售角色] 的 [商机流转问题]，梳理 [真实数量] 个流程节点，主导 [本人负责模块] 的规则与交互设计，协调 [实际团队] 上线；在 [时间与人群口径] 下，[真实业务指标] 从 [A] 变为 [B]。

迁移价值：流程建模、工具集成、跨团队交付。原项目没有使用 AI，就保留原技术事实；在独立项目里展示 AI 延伸。

原句：熟练使用 Dify、Coze、RAG、Prompt、MCP、多 Agent。

改写示例：针对 [用户] 的 [任务]，使用 [实际平台] 实现 [检索 / 工具调用 / 确认步骤]；本人负责场景定义、验收标准与迭代，基于 [N] 条 [数据来源] 测试用例记录 [任务成功率]、[耗时] 与 [成本]。

技能词放在对应项目里；MCP、微调、多 Agent 只在真正使用且能解释时保留。不靠堆叠架构增加项目分量。

原句：搭建智能客服，准确率达 95%，效率提升 80%。

改写示例：建立覆盖 [具体任务类型] 的 [N] 条固定评测集，以 [完整业务验收条件] 判定成功；对比 [基线] 和 [版本]，成功率由 [A/N] 提升至 [B/N]，记录 [P50 / P95] 耗时，并保留 [失败类型] 的复盘。

只填写实测值。没有数据时，先写已经完成的设计与验证范围；不能用计划目标、演示成功率替代真实结果。

可以用正面且准确的定位：“[X] 年 [领域] 产品经验，聚焦 [场景] Agent 应用，已完成 [真实实践阶段]。”这保留了已有资历，也没有虚构 AI 工作年限。

正式岗位名称按事实保留。求职方向写“AI Agent 产品经理”，不代表可以把过去的职位改为“资深 AI 产品经理”。

版式建议属于本报告的执行建议。没有证据证明某一页数、关键词数量或固定模板一定通过 ATS；关键是内容可解析、经历一致、相关证据清楚。

05

用一个代表项目，补上实践证据

你已经具备知识，下一步是形成可交付、可验证的作品。优先选原业务中的窄任务，完成需求、方案、评测、迭代与复盘。

推荐投入顺序：有条件时争取真实内部试点；否则做有目标用户参与的独立原型；暂时只有方案，也如实呈现。三者证明力不同，不能互相冒充。
B 端背景

客服工单 Agent

理解问题 → 检索政策 → 查询模拟订单 → 生成处理建议 → 人工确认 → 写入测试工单。

证明：流程、知识检索、工具调用、权限、转人工与闭环验收。查到资料只是一个环节。

增长 / 内容背景

广告素材策划 Agent

接收 brief → 检索品牌约束 → 生成脚本方案 → 质量检查 → 人工挑选。展示对冷启动素材的判断。

证明：内容标准、生成质量、用户采纳；没有真实投放实验，就不宣称 GMV 或 ROI 提升。

流程 / 行业背景

费用预审助手

抽取信息 → 校验政策 → 标示证据与缺项 → 人工审核 → 测试环境记录结果。

证明：业务规则、风险分级、异常处理。项目内已有 报销审核设计参考；阅读参考本身不算个人实施经历。

代表项目的六件交付物

01 / 两页项目案例

用户与痛点、业务基线、方案取舍、实际完成范围、结果与限制。第一页就能回答“你做了什么”。

02 / 一段可运行演示

展示一个正常任务和一个失败任务；说明模拟了哪些数据或接口。建议录 2–3 分钟视频并保留可打开的演示入口。

03 / 工作流与个人职责

标注输入、工具、确认点、退出条件、人工接管。说明哪些由你设计、哪些由同伴或现成平台完成。

04 / 固定评测集与报告

列明样本来源、任务覆盖、成功定义、评审者、基线、版本、耗时与成本。把用于调试的样本和留出的测试集分开。

05 / 失败案例与版本记录

保留问题复现、原因假设、改动、回归结果，以及仍未解决的案例。面试中用它解释你的取舍。

06 / 用户反馈或试点记录

记录实际参与者、任务、反馈与修改。方便测试的朋友反馈和真实目标用户反馈分别说明。

怎么评测，才有资格写“效果提升”

先固定一个业务成功定义：例如客服任务必须同时满足“政策依据正确、订单查询对象正确、处理建议符合权限、最终状态正确”，才算端到端成功。

再比较同一批任务：给基线和新版本相同输入、工具权限与评审标准，记录模型 / 提示词 / 工作流版本。重要失败要单独统计；模型有随机性时，视预算重复运行并报告波动。

样本规模按任务覆盖来定：可先从几十至上百条任务开始做诊断，但这只是项目实践建议，不构成统计充分性的保证。样本覆盖比漂亮的百分比更重要。

虚构算例 · 仅解释指标写法，不能当作个人成绩

62 → 79同一组 100 条任务的成功数
+17 pp成功率增加 17 个百分点
50 / 79总费用 ÷ 成功任务数

假设新版本执行这 100 条任务共花费 50 元（包含失败调用），则每个成功任务的调用成本约 0.63 元。它仍不包含人工复核、研发和运维成本。

离线任务成功率从 62% 到 79%，不等于线上客服解决率，也不直接等于人工效率提升。后两者需要真实使用范围、对照口径和人力时间记录。

如果短期做不出全套：至少交付一个窄任务、明确的基线、可复现的评测和一轮有根据的迭代。把已完成范围写清，比扩写成“企业级全链路平台”更容易讲透。

06

让简历里的每句话，都能展开

下列答法是练习框架，不是来自面经的标准答案。准备材料时，用自己的项目填充。

01　你没有正式 AI 工作经验，为什么适合这个岗位？

答法：“我的正式经历主要在 [原领域]，与这个岗位的 [业务任务] 重合。我曾负责 [真实交付]。为了验证在这个流程中引入 Agent 的可行性，我做了 [项目及真实阶段]，本人负责 [决策 / 验证]，目前证据是 [演示与记录]。生产规模与长期运营是我尚未覆盖的部分。”

把缺口讲清后，回到岗位任务与可验证能力。不要把“知道怎么做”说成“已在公司做过”。

02　为什么用 Agent，规则、RPA 或普通工作流不够吗？

先说任务中的不确定性：用户意图、信息获取路径、工具选择，哪一项需要动态决策？再给出规则 / 固定工作流基线。能被确定性流程稳定解决的部分，继续用确定性流程。

带到面试：一页方案对比，包含质量、成本、可控性与维护复杂度。选型要服务业务目标。准备方向对应 M4。

03　用了低代码或 AI 辅助开发，你的个人贡献是什么？

逐项区分“平台提供的能力”和“你的决策”：场景选择、流程边界、业务规则、工具输入输出、成功标准、失败归因、版本取舍。若实现由别人完成，就直接说明。

带到面试：需求草稿、决策记录和版本差异。自己没有做的技术实现不要认领。准备方向对应 M5。

04　这个成功率怎么来的，评测数据是谁判的？

说明分子分母、任务覆盖、数据来源、基线、公平比较条件、评审人员和分歧处理。若用模型评分，解释如何与人工抽查校准，哪些问题不能只靠模型判。

带到面试：脱敏样本、评分表、失败清单与复跑记录。仅有评测计划时，明确还没有结果。准备方向对应 M2、J5。

05　结果不好，怎么区分检索、模型、Prompt 和工具问题？

用一个实际失败任务复盘：检查检索内容是否含答案，再看模型输出与工具选择、参数、工具返回、最终业务状态。通过替换单个环节验证原因，记录修复后是否影响其他任务。

带到面试：可读的运行轨迹与一例反例。不要把所有问题都归为“模型幻觉”。准备方向对应 M4、M5。

06　准确率上去了，但速度和成本变差，怎么取舍？

按任务价值和错误代价分层。比较端到端成功率、等待时长、成功任务成本、转人工率；核算人工复核成本。提出可接受边界，再解释选择的版本与放弃的收益。

带到面试：两三个版本的对照表。没有真实收入和上线人力数据时，只讲估算及假设，不宣称商业 ROI 已验证。

07　个人 Demo 和生产系统之间，还差什么？

结合自己的任务说具体缺口：数据权限、真实系统接入、重复操作防护、监控回归、人工接管、用户培训与效果追踪。为其中最关键的两项设计验收条件。

带到面试：已实现 / 已设计 / 未覆盖三列范围表。识别差距体现判断力，不能用一张架构图宣称已完成规模化上线。

08　请在 90 秒内介绍最相关的项目。

建议节奏：20 秒讲用户与痛点 → 25 秒讲你的关键取舍 → 25 秒讲实施与验证 → 20 秒讲结果、限制和下一步。时间分配用于练习，不是固定面试规则。

优先讲一个能深挖的决定，例如“为什么保留人工确认”“为什么去掉多 Agent”“哪个指标变化后才决定继续迭代”。准备方向对应 M1、M3。

07

把投递当成一个可复盘的过程

目标是提升匹配与表达质量。现有公开证据无法量化这些修改会增加多少面试机会。

两种简历版本，分别突出重点

版本 A：原行业 / 场景 + Agent 应用。原业务成绩在前，Agent 项目紧随其后。

版本 B：Agent 工作流 / 评测 / 平台工具。把最强的相关项目证据前置，工作履历保持完整。

先选自己够得着的岗位池，再调整顺序。所有版本里的事实必须一致。

作品入口，降低阅读成本

简历中的链接直接指向代表项目概览：做什么、你做了什么、结果是什么、哪里能看演示。

无需登录即可查看是理想状态；提前验证权限。仓库或长文可以作为二级入口。

PDF 正文必须自足；不要只写“详情见作品集”。

您好，我有 [X] 年 [原领域] 产品经验，曾负责 [相关产品与可核实成果]。看到贵岗位重点是 [JD 的具体任务]，这与我的 [业务经验] 相近。我另完成了 [Agent 项目及真实阶段]，可提供 [演示 / 评测 / 复盘链接]。希望就 [岗位名称] 进一步沟通。

DAY 03–07

先建立基线与测试任务，再做原型和一次迭代。已有作品就查漏补缺，不必重新做一个更大的项目。

DAY 08–10

DAY 11–14

小批定向投递，记录反馈

记录岗位、来源、投递日期、简历版本、作品版本、回复和面试进展。可按 10–15 个相近岗位为一批复盘；这只是管理节奏，不是效果统计阈值。

观察到的现象先检查的假设下一次只改什么
几乎没有有效回复岗位硬门槛、投递渠道、岗位是否仍在招、首页相关性。收窄到同场景岗位，改摘要与第一段项目；保留修改前版本。
HR 愿聊，业务面很少项目是否只有概念、个人贡献是否模糊、作品是否打不开。补一个可核对的交付证据，并重写项目范围。
进入业务面，深挖后中断指标口径、方案取舍、失败案例、实践深度。根据真实追问补验证；不靠增加更多技术词解决。
同类岗位反馈差异很大行业匹配、职责级别、业务阶段与渠道差异。按岗位类型分组，避免把不同样本混成一个通过率。

漏斗口径建议：有效回复率 = 有实质沟通的岗位数 / 去重投递岗位数；业务面邀请率 = 获得业务面邀请的岗位数 / 去重投递岗位数。多轮面试仍算同一岗位。记录等待窗口与渠道，少量样本的变化只作线索，不做因果结论。
