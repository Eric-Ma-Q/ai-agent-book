### E2（4 分 · 第 4 章 · 工具 · 分析）

下面是一个工具定义。按书中的 ACI 与描述原则，它有哪些问题？

```text

```

### E4（4 分 · 第 2 章 · 上下文工程 · 分析）

下面用 LLM 维护“已拨打电话次数”的状态栏。问题出在哪里？

```text
history_text = render(trajectory)
count = LLM(f"数一数这段历史里 phone_call 出现了几次：\n{history_text}")
status = f"<agent_status>phone_call: {count} times</agent_status>"
messages.append({"role": "user", "content": status})
```

- A. 让 LLM 一次性批量统计长历史，计数容易出错
- B. 状态栏会被模型几乎无条件相信，错误计数会原样传导
- C. 计数应由代码维护，或让 LLM 逐条抽取后再由代码汇总
- D. 状态栏应该放进 system prompt，才能每轮都看到
- E. 状态栏应该删掉，模型自己会从历史里数清楚

### E7（4 分 · 第 7 章 · 评估 · 评价）

某退款 Agent 用下面的方式计算上线指标。它错在哪里？

```text
runs = [run_refund_task(task) for _ in range(5)]
success = any(run.succeeded for run in runs)
report(metric="success_rate", value=success)
deploy_if(value > 0.9)
```

- A. 退款有副作用且不可撤销，应报告 Pass^k（连续 k 次都不出错），而不是“至少成功一次”
- B. 不能在真实环境里“重试到成功”，应在沙盒或可回滚环境中采样，并把每次失败计入
- C. 只跑 5 次就上线，样本量不足，还需要置信区间或配对分析
- D. 应该把 k 调到 100，取最好的一次作为可靠性
- E. 应该只报告平均响应时间，成功率不重要

### E8（4 分 · 第 9 章 · 持续进化 · 评价）

一个自我进化脚本把网页摘要直接写成长期 Skill。哪些地方违背了书中的安全边界？

```text

```

- A. 把不可信网页内容当成了可执行指令，摘要不是“净化”
- B. 没有把证据与指令隔离，也没有保留原文、来源与采集时间
- C. 没有独立 reviewer、确定性检查与待验证区，直接进入正式能力
- D. 应该让写 Skill 的模型同时修改验证器，以便快速迭代
- E. 应该把网页全文直接塞进系统提示词，省去摘要

## 参考答案与解析

### A1

**答案**：第 1 空：上下文；第 2 空：工具

**解析**：这个公式只描述 Agent 边界之内的实现，不包含它交互的环境。更直观的说法是“大脑 + 眼睛 + 手脚”：LLM 决策，上下文决定它看到什么，工具决定它能做什么。

**出处**：[第 1 章 §现代 Agent = LLM + 上下文 + 工具](https://bojieli.github.io/ai-agent-book/book/chapter1/)

### A2

**答案**：错误

**解析**：恰好相反。Agent 与 Environment 是闭环交互的两方；Agent 边界内是 Model–Harness 结构，上下文和工具属于 Harness。Harness 可以创建、隔离或代理一个环境，却不因此包含环境自身的状态与转移规律。

**出处**：[第 1 章 §现代 Agent = LLM + 上下文 + 工具](https://bojieli.github.io/ai-agent-book/book/chapter1/)

### A6

**答案**：第 1 空：末尾；第 2 空：系统提示词

**解析**：动态信息放进系统提示词会让 token 序列从该位置开始不同，变动点之后的 KV 状态无法复用。正确做法是作为新消息追加到对话末尾，或只在需要时通过工具获取。

**出处**：[第 2 章 §KV Cache 友好的上下文设计](https://bojieli.github.io/ai-agent-book/book/chapter2/)

### A8

**答案**：第 1 空：单次推理 / 一次请求内；第 2 空：多次 API 请求之间

**解析**：KV Cache 是模型内部机制，加速单次请求内的逐 token 生成；Prompt Cache 是推理引擎的跨请求优化，复用相同前缀的计算结果。

**出处**：[第 2 章 §KV Cache 与 Prompt Cache：两个层级的缓存](https://bojieli.github.io/ai-agent-book/book/chapter2/)

### A9

**答案**：错误

**解析**：它会破坏前缀一致性导致缓存失效，更严重的是可能丢掉关键工具结果；实验中滑窗 Agent 经常陷入重复调用，因为它“忘记”了之前已经拿到的结果。控制长度应当用压缩，而不是无声丢弃。

**出处**：[第 2 章 §常见的错误上下文管理模式](https://bojieli.github.io/ai-agent-book/book/chapter2/)

### A10

**答案**：第 1 空：决策；第 2 空：约束；第 3 空：失败；第 4 空：引用

**解析**：这是书中的 preserve 列表：决策、约束、失败、引用。压缩是有损投影，丢掉的细节后来可能成为关键约束，所以保留的是“以后还要用来做判断”的结构化信息，而不是尽量多留原文。

**出处**：[第 2 章 §上下文压缩策略](https://bojieli.github.io/ai-agent-book/book/chapter2/)

### A12

**答案**：错误

**解析**：书里明确要求状态栏尽量用代码维护；实在要用 LLM，也只让它逐条抽取，再由代码汇总。模型几乎无条件相信状态栏，而 LLM 做数量统计很容易出错，错误会被原样传导。

**出处**：[第 2 章 §状态更新的两种实现与缓存代价](https://bojieli.github.io/ai-agent-book/book/chapter2/)

### A14

**答案**：错误

**解析**：用户长期记忆不是流水账。轨迹保留原始事件供追溯，长期记忆则要经过选择性、抽象化、结构化提取：丢掉短期细节，把“这次靠窗”归纳为“偏好靠窗”，并用可检索的字段保存。

**出处**：[第 3 章 §用户记忆系统](https://bojieli.github.io/ai-agent-book/book/chapter3/)

### A15

**答案**：第 1 空：recall@k

**解析**：recall@k 是包含正确答案的文档出现在前 k 个结果中的查询比例。MRR 关注“找到得够不够靠前”，nDCG 关注整个排序列表的质量。

**出处**：[第 3 章 §RAG 基础：构建 Agent 的知识获取管道](https://bojieli.github.io/ai-agent-book/book/chapter3/)

**答案**：第 1 章 ↔ Agent = LLM + 上下文 + 工具；Harness 是竞争力；第 2 章 ↔ KV Cache、结构化提示、Skills、状态栏与压缩；第 3 章 ↔ 用户记忆、RAG、结构化索引与知识更新；第 4 章 ↔ ACI、MCP、工具规模与执行安全；第 5 章 ↔ Coding Agent + 文件系统；代码是元能力；第 6 章 ↔ 异步事件、语音、Computer Use 与机器人；第 7 章 ↔ 评估环境、Pass@k / Pass^k、LLM-as-a-Judge；第 8 章 ↔ 预训练、Mid-training、SFT、RL 与奖励设计；第 9 章 ↔ 轨迹评价、四种更新载体与自我进化安全；第 10 章 ↔ 上下文共享、协作拓扑、失败模式与 A2A

**解析**：十章可以压成一条主线：先构建（1–6），再提升（7–10）。评估是分界线：没有可重复的测量，后训练与持续进化都只能靠感觉。

### D8

**答案**：Simple Notes ↔ 最小事实、O(1) 操作，但信息关联丢失；Enhanced Notes ↔ 完整段落、保留叙事结构，但冗余且更新复杂；JSON Cards ↔ 三层嵌套、支持部分更新，但结构较刚性；Advanced JSON Cards ↔ backstory + person + relationship，擅长消歧与跨会话关联

**解析**：四种格式是粒度与结构复杂度的递进。实践标准是混合：关键且少量的信息用 Advanced JSON Cards，海量非关键事实用 Simple Notes。

### D10

**答案**：Pass@k ↔ 给足 k 次机会，能否至少成功一次；Pass^k ↔ 连续 k 次执行是否一次都不出错；recall@k ↔ 该找的相关文档有没有出现在前 k 个结果里；MRR ↔ 第一个相关结果排得够不够靠前；nDCG ↔ 整个排序列表的质量如何

**解析**：Pass@k 看能力上限，Pass^k 看业务可靠性；recall@k、MRR、nDCG 分别看“找到没、靠前没、整体排序好不好”。报告任何指标都必须写清 k 与采样口径。

**出处**：[第 7 章 §评估指标：成功的定义](https://bojieli.github.io/ai-agent-book/book/chapter7/) · [第 3 章 §混合检索：两全其美的艺术](https://bojieli.github.io/ai-agent-book/book/chapter3/)

### G4

**参考思路**：参考骨架：先花小预算建 50–100 条留出任务与验证器，测 pass@k 和失败类型。新政策/话术属于事实与知识，优先 RAG；若模型连领域语言与基本操作都不熟，再做 Mid-training。SFT 只负责 JSON schema、工具调用与流程，增加示范多样性、混 20% 通用数据、按验证集早停。只有在模型偶尔能成功、奖励能稳定区分好坏时才上 RL；否则先做拒绝采样/在轨蒸馏。奖励以隐藏测试和数据库状态为主，路径违规用 RLVP 扣分；训练与评估可共享环境，但题目要分开。最后在边界集与保留集上一起验收，避免“修好新政策、弄坏旧流程”。

### G5

**参考思路**：参考骨架：先把“满意度”降级为质量指标，补上结果验证（退款是否真实发生）、过程验证（是否先确认、是否越权）与承诺—行动一致性。验证器逐维度输出结论、证据位置和失败标签，证据不足就拒评；高满意度但违规的轨迹不能进学习集。更新按最小 diff 提案：政策事实进知识库，判断原则进 Skill，硬门进程序；在边界集上改善、在保留集上不退化，由独立 reviewer 对照原始证据审查。新版本先进入不服务真实流量的待验证区，验证器与发布门槛不可被提案者修改；灰度、监控、回滚。最后同时看提案有效率、激活率、遵循率与保留集增益，不能只看端到端分数。

### G6

**参考思路**：参考骨架：先用新信息判据砍掉“让多个 Agent 辩论同一段摘要”这类无效协作，只保留并行搜索、工具核验、截图/执行反馈。搜索子 Agent 上下文隔离，通过共享工作区交换结构化结果；汇总 Agent 只读原始证据与结论，不读前序思考过程。拓扑用管理者模式，Manager 负责分解、预算与验收，拿最强模型。完成由独立验证器判定，取第一个已验证成功并幂等结算；成功后广播 terminate，子 Agent 在安全点清理退出；progress.md 超时检测卡住。失败模式上：共享文件用乐观锁/worktree，级联用独立交叉验证，同质趋同用差异化模型与来源，扯皮用目标优先级与人工裁决，失控用预算/独立 key。跨组织才引入 A2A。

### G7

**参考思路**：参考骨架：作者并不否认模型会持续内化 Harness，但强调节奏：训练以月计，模型无法一次吸收真实业务的全部约束与偏好。因此把 Harness 分成两层：补能力短板的适配层（格式修复、few-shot、部分规划）会随模型变强逐步卸下；让模型安全作用于真实世界的边界层（权限、沙箱、凭据、审计、回滚、数据层授权）不会自动消失，因为它们是业务约束与责任边界。判断依据是“模型是否已稳定做对且可验证”与“出错是否不可逆、是否需要审计”。Terminal Bench 上只改 Harness 就从 52.8% 到 66.5%，说明当前仍有明显工程空间；但也要为换模型而设计，别把临时补丁当成永恒架构。
