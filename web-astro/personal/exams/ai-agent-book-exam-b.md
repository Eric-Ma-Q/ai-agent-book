## E · 代码与实验诊断

### E1（4 分 · 第 1 章 · 入门与 Harness · 分析）

下面是一个最小 Agent 循环的伪代码。它缺少了哪些生产环境必需的防线？

```text
trajectory = [user_request]
while True:
    context = stable_prefix + trajectory
    decision = Model(context)
    trajectory.append(decision)
    if decision.tool_calls:
        for call in decision.tool_calls:
            result = Environment.execute(call)
            trajectory.append(result)
    else:
        return decision.content
```

- A. 没有最大迭代轮数等停止条件，任务无解时可能一直转
- B. 没有在 execute 前做权限校验与参数校验，危险调用会直接落地
- C. 没有对“工具名 + 参数”做重复调用指纹，无法识别无进展循环
- D. 没有把工具结果追加到轨迹
- E. 没有在每轮重新加载全部工具定义

### E3（4 分 · 第 2 章 · 上下文工程 · 应用）

某客服 Agent 这样构造请求。哪些做法会破坏 KV Cache，或违背上下文布局原则？

```text
system = f"You are a support agent. Current time: {now}"
tools = sorted(ALL_TOOLS, key=lambda t: usage[t.name], reverse=True)
messages = [{"role": "system", "content": system}] + history
messages += [{"role": "user", "content": user_text}]
```

- A. 把当前时间写进 system prompt，每次都让前缀从该位置起失效
- B. 按使用频率重排工具定义，会让缓存从首个变动的工具起失效
- C. 动态时间本应追加到对话末尾，或只在需要时通过工具获取
- D. history 应该每轮清空，以保证缓存命中
- E. 工具定义应该每轮随机打乱，避免模型形成固定偏好

### E5（4 分 · 第 3 章 · 记忆与知识库 · 应用）

这是一个最简 RAG 管道。它缺少了哪些在书中被认为重要的环节？

```text
chunks = split(document, size=512)
vectors = embed(chunks)
hits = vector_search(query, vectors, top_k=5)
answer = LLM(query, hits)
```

- A. 没有稀疏/关键词检索，精确术语、编号、专有名词容易漏
- B. 没有融合与重排序，候选排序质量没有二次校正
- C. 没有元数据过滤（来源、时间、权限），可能检索到过期或越权内容
- D. 没有为每个查询重新训练嵌入模型
- E. 没有把整篇文档直接塞进上下文

### E6（4 分 · 第 10 章 · 多 Agent 协作 · 分析）

两个子 Agent 并行写同一个交付文件。这段代码的主要风险是什么？

```text
a = spawn_subagent("分析数据并写 report.md")
b = spawn_subagent("补充结论并写 report.md")
wait(a); wait(b)
publish("report.md")
```

- A. 并发写入没有版本检查，后写者会覆盖先写者
- B. 即使文件级不冲突，也可能出现跨文件的语义冲突
- C. 应使用乐观锁，或给每个子 Agent 独立 worktree/工作副本，最后合并
- D. 只要让两个子 Agent 共享完整上下文，就不会冲突
- E. 增加第三个 Agent 来写同一个文件，可以投票解决冲突

### G1（12 分 · 第 2 章 · 上下文工程 · 创造）

为一个生产级客服 Agent 设计上下文布局。约束：可用工具约 500 个；需要实时知道当前时间、工单状态与已拨打电话次数；单次对话可能长达 50 轮；服务对首 token 延迟和成本敏感。请说明静态前缀、工具披露、状态栏、压缩与缓存之间的取舍，并给出验证方案。

### A3

**答案**：错误

**解析**：书里的判断相反：模型自主决策的空间越大，出错时的影响面越大，越需要约束、验证和纠正。模型厂商的优势是对模型与外围 Harness 做协同优化，而不是简单“让框架变薄”。

**出处**：[第 1 章 §模型即 Agent：当模型本身成为产品](https://bojieli.github.io/ai-agent-book/book/chapter1/)

### A4

**答案**：第 1 空：思考；第 2 空：行动；第 3 空：观察

**解析**：ReAct = Reasoning + Acting，但实际循环有三个环节：想 → 做 → 看。轨迹就是这三类消息按时间追加形成的消息历史。

**出处**：[第 1 章 §ReAct 循环](https://bojieli.github.io/ai-agent-book/book/chapter1/)

### A5

**答案**：第 1 空：静态前缀；第 2 空：轨迹

**解析**：静态前缀是系统提示词 + 工具定义；轨迹是用户消息、模型回复和工具执行结果，随交互不断增长。这个“前不动、后可压”的结构是 KV Cache 与压缩策略的基础。

**出处**：[第 2 章 §从 API 视角看上下文的构成](https://bojieli.github.io/ai-agent-book/book/chapter2/)

### A7

**答案**：错误

**解析**：缓存只认 token 字节序列。前缀里多一个空格，从该位置开始（包括其后全部内容）的 KV 状态都要重算；改动越靠前，重算和计费的 token 越多。

**出处**：[第 2 章 §KV Cache 的原理与约束](https://bojieli.github.io/ai-agent-book/book/chapter2/)

### A11

**答案**：第 1 空：user；第 2 空：末尾

**解析**：这是借用 user 消息槽位注入框架生成的元信息；放在末尾既接近模型即将生成的新 token，又保持前缀不变。内容用 `<agent_status>` 等标签与真实用户输入区分。

**出处**：[第 2 章 §Agent 状态栏在上下文中的具体位置](https://bojieli.github.io/ai-agent-book/book/chapter2/)

### A13

**答案**：第 1 空：Advanced JSON Cards；第 2 空：backstory

**解析**：四种格式是粒度和结构复杂度的递进。Advanced JSON Cards 不只记录事实，还记录“为什么存这条信息”的 backstory 和“为谁存”的人物关系，因此更适合关键且少量的记忆。

**出处**：[第 3 章 §用户记忆的四种存储格式](https://bojieli.github.io/ai-agent-book/book/chapter3/)

### A16

**答案**：第 1 空：工具；第 2 空：资源；第 3 空：提示模板

**解析**：工具对应“可执行的操作”，资源对应“可读取的数据”，提示模板对应“可复用的提示词”。MCP 用标准化的工具描述和传输层，把专用工具的接入从每家框架各写一遍变成一次开发、处处可用。

**出处**：[第 4 章 §工具生态：MCP 与 Skill Hub](https://bojieli.github.io/ai-agent-book/book/chapter4/)

### A18

**答案**：第 1 空：Computer；第 2 空：目标

**解析**：ACI 是对标 HCI 提出的概念：工具设计要让 Agent 好用，而不是把 API 直接包一层。粒度、描述、参数保真性都是 ACI 的具体展开。

**出处**：[第 4 章 §工具设计的通用原则](https://bojieli.github.io/ai-agent-book/book/chapter4/)

### A19

**答案**：错误

**解析**：默认取向确实是通用优于专用，但书里给了四种退回专用工具的理由：安全权限与审计、屏蔽平台差异并给出更好反馈、使用频率极高、参数结构复杂。支付、删除数据、生产部署属于高风险或强业务约束操作，应封装为参数明确、权限受限、全程可审计的专用工具。

**出处**：[第 4 章 §能力的表达形式：专用工具、通用执行器与 Skill](https://bojieli.github.io/ai-agent-book/book/chapter4/)

### A21

**答案**：第 1 空：API；第 2 空：工具

**解析**：四层分别是 API（限流、超时、截断）、工具（幻觉调用、参数畸形、反复失败）、上下文（溢出、压缩失败、轨迹损坏）和控制流（死循环、死亡螺旋）。先分类，再决定值不值得重试。

**出处**：[第 5 章 §故障与错误恢复](https://bojieli.github.io/ai-agent-book/book/chapter5/)

### A23

**答案**：第 1 空：99；第 2 空：7.8

**解析**：Pass@5 = 1 − 0.4^5 ≈ 99.0%，衡量“给足机会能不能成”；Pass^5 = 0.6^5 ≈ 7.8%，衡量“连续五次都不出错”。支付、退款、生产部署这类有副作用的场景要看后者。

**出处**：[第 7 章 §业务可靠性：关注 Pass^k](https://bojieli.github.io/ai-agent-book/book/chapter7/)

### A25

**答案**：错误

**解析**：同一个模型在不同 Harness 下可能差异悬殊，评估对象应是模型与 Harness 的组合体。引用成绩要先问：什么 Harness、什么提示词模板、什么采样与计分口径。

**出处**：[第 7 章 §引言](https://bojieli.github.io/ai-agent-book/book/chapter7/)

### A26

### G1

**参考思路**：参考骨架：系统提示词 + 七个核心工具构成稳定前缀；其余工具只放“名称 + 一句描述”的目录，模型需要时通过 tool_search 拉取完整 schema，schema 首次出现的位置固定，后续作为普通历史命中缓存。时间、工单状态、电话计数由代码维护成 <agent_status>，作为 user 消息追加在末尾；状态小、更新间隔长时保留旧状态，状态大或更新频繁时每轮替换并接受短后缀失效。历史只追加，接近窗口 80% 时批量压缩旧 tool results，保留决策/约束/失败/引用；探索型子任务交给子 Agent，只回传结论。验证上同时看首 token 延迟、缓存读取占比、溢出率、任务成功率与关键信息召回，避免“省了 token 但答错”。

### G2

**参考思路**：参考骨架：轨迹只追加、供审计；会话结束后由 LLM 提取“偏好/证件/关系/行程”，关键项写成 Advanced JSON Cards（记录为谁、为什么知道、何时验证），大量低价值事实写 Simple Notes。护照到期这类规则用可执行代码检查，不靠模型心算。冲突时保留来源与时间，按对象/条件分支；不确定就保留冲突待确认。检索侧用上下文感知前缀 + 混合检索，卡片常驻提供“概览”，细节按需召回。隐私上本地小模型脱敏、最小权限、敏感字段不进入上下文。评估用每层 20 例的三层次集，比较仅卡片、仅检索、双层三种配置，指标看主动提醒率与多跳/时间推理得分。

### G3

**参考思路**：参考骨架：主指标报 Pass^5=0.6^5≈7.8%，同时附 Pass@5 作为能力上限参考；k 的口径写成“同一任务在可回滚沙盒中的 5 次独立采样”。环境要能重置订单/退款状态，工具有原子操作，评分标准包含终态断言与信息告知断言。数据集从真实退款工单回流，另加“用户未确认/金额超限/政策不允许”的边界集。验证器以环境状态为主，LLM judge 只评表达与合规变通，并用 100–200 例人工金标测 kappa。统计上用 McNemar 或配对 bootstrap，报告置信区间与 3–5 个种子。上线后按首错归因固化为轨迹前缀回归，灰度发布并保留一键回滚。

### G8

**参考思路**：参考骨架：系统提示词 + 七个核心工具 + 项目指令文件构成稳定前缀；进度写入 progress.md 与状态栏，接近窗口阈值时批量压缩旧工具结果，保留架构决策、约束、失败与引用。工具层把部署、删除、改生产配置封装成参数明确、最小权限、可审计的专用工具；沙盒内不挂密钥，网络默认断网/白名单。约束层用语义解析识别危险 shell，而不是关键字黑名单。验证层跑测试、Lint、类型检查，并用 Agent 看不到的隐藏测试与状态断言判定完成；验证器与原始测试哈希放在 Agent 改不到的地方。纠正层先分类错误，再退避重试、降级接续、熔断，错误路径禁止再调用模型。最后用最大迭代/预算、重复指纹、优雅终止兜底，并在边界集与保留集上一起评估。
